## Стек

Целевой стек из концепции: Next.js 15 (App Router) + TypeScript strict, PostgreSQL, Prisma, Zod,
Vitest, Docker. Развёртывание — Yandex Cloud.

Если в репозитории уже есть фронт на другом фреймворке — не переписывай его. Зафиксируй в
PROJECT_AUDIT.md и предложи варианты интеграции до изменения кода.

Запрещено: Supabase, Vercel, Firebase и любые зарубежные облачные сервисы; Python в рантайме;
ML-модели и LLM в бизнес-логике; новые зависимости без объяснения, зачем они нужны.

## Архитектура — модульный монолит

    src/
      app/                         страницы фронта; app/api/**/route.ts — тонкие обработчики
        (auth)/login/              вход
        (app)/                     внутренние страницы внутри общего каркаса
      ui/                          дизайн-система: primitives, data, overlays, layout,
                                   search, notifications, hooks, lib (docs/FRONTEND.md)
      modules/<модуль>/
        <модуль>.schema.ts         Zod: входные данные и DTO ответа
        <модуль>.service.ts        бизнес-логика
        <модуль>.repo.ts           доступ к БД (Prisma только здесь)
        <модуль>.rules.ts          правила модуля
        <модуль>.test.ts
      shared/
        contracts/                 типы DTO, общие для фронта и бэка
        http/                      ok, fail, handle, parseBody, пагинация
        config/                    все коэффициенты и нормативы (analytics.config.ts и др.)
      integrations/                lms, site, market-data: интерфейс + mock + настройки из env
    prisma/                        schema.prisma, seed.ts
    scripts/smoke.ts               сквозной сценарий из ТЗ
    docs/                          обязательная документация

Модули: universities, programs, skills, products, cooperation, workflow, documents, meetings,
analytics, recommendations, data-sources, auth.

Поток вызовов строго route → service → repo. Фронт импортирует только из shared/contracts,
никогда не типы Prisma. Логика не дублируется между модулями.

Страницы обращаются к данным только через API теми же маршрутами, что описаны в контракте:
прямых вызовов сервисов и Prisma из страниц нет, иначе фронт перестанет быть отделяемым.
Оформление — переменные в `src/app/globals.css` и CSS Modules; UI-библиотек и Tailwind нет.

## Контракт API

- JSON в camelCase, в базе snake_case через `@map` / `@@map`. `TODO: PM DECISION` — подтвердить с фронтом.
- Даты — ISO 8601 в UTC. Идентификаторы — строки (cuid).
- Успех: `{ data }`. Список: `{ data: [...], meta: { page, pageSize, total } }`.
- Ошибка: `{ error: { code, message, details } }`.
  Коды: VALIDATION_ERROR 422, NOT_FOUND 404, FORBIDDEN 403, UNAUTHORIZED 401, CONFLICT 409,
  INVALID_TRANSITION 409, INTEGRATION_ERROR 502, INTERNAL 500.
- Тексты ошибок на русском.
- Эндпоинт сначала описывается в docs/API_CONTRACT.md, потом реализуется. Меняешь поле —
  обнови контракт и напиши в отчёте, что это затрагивает фронт.

## Принятые решения

1. **Cooperation** — связка «вуз - программа - IT-продукт». `productId` допускает null: продукт может
   быть не выбран на первых этапах. `TODO: PM DECISION` — обязателен ли продукт при создании.
2. **Workflow.** При создании связки создаются все 14 этапов из ТЗ. Этап 14 «Контроль выполнения»
   вычисляется автоматически: COMPLETED, когда этапы 1–13 в COMPLETED или CANCELLED. Вручную не меняется.
3. **Статусы этапа:** NOT_STARTED, IN_PROGRESS, BLOCKED, COMPLETED, CANCELLED. Переходы:
   - NOT_STARTED → IN_PROGRESS, CANCELLED
   - IN_PROGRESS → COMPLETED, BLOCKED, CANCELLED
   - BLOCKED → IN_PROGRESS, CANCELLED
   - COMPLETED → IN_PROGRESS только с комментарием (переоткрытие)
   - CANCELLED — конечный, переоткрывает только ADMIN
   Остальные переходы — ошибка INVALID_TRANSITION.
4. **Условия переходов.** COMPLETED требует непустой результат и закрытые обязательные задачи этапа,
   сохраняет completedAt и автора. BLOCKED требует blockingReason. Этап 5 можно отменить с комментарием
   «не требуется». Каждое изменение пишется в историю с автором и временем.
5. **Порядок этапов** не жёсткий: в реальности часть этапов идёт параллельно. Текущий этап — первый
   по номеру, который не COMPLETED и не CANCELLED. `TODO: PM DECISION` — нужен ли строгий порядок.
6. **Чек-лист** — сущность Task. Обязательные задачи каждого этапа — в конфиге с пометкой TEMP.
7. **Рейтинг программ** считается по трём показателям: заявки на обучение, количество обучающихся,
   количество параллельных групп (groupCount). Остальные факторы из ТЗ — востребованность навыков,
   skill gap, соответствие продукту, готовность вуза, просрочки — показываются отдельными
   объяснимыми сигналами и в итоговый балл не входят. Не смешивать.
8. **Нет данных — значит null и пометка «Нет данных»**, никогда не 0 и не случайное значение.
   Если показатель оценочный, в DTO поле `basis: "estimate"` и пояснение.
9. **Роли:** ADMIN, MANAGER, ANALYST, VIEWER из ТЗ плюс UNIVERSITY_REP из концепции.
   На P0 — mock-авторизация: демо-пользователь выбирается через cookie, весь доступ идёт через одну
   функцию `getCurrentUser()`. На P1 её реализация меняется на NextAuth.js с bcrypt, остальной код не трогается.
   **UNIVERSITY_REP (P1)** — кабинет представителя вуза, у пользователя есть universityId:
   - видит только свой вуз: его программы, связи, статусы этапов, переданные документы и материалы;
   - подтверждает получение материалов (задачи этапа 7);
   - вносит количество обучающихся и групп по своим программам;
   - подаёт заявки на обучение: сущность Application, applicationCount программы считается по заявкам.
     `TODO: PM DECISION` — поля заявки; персональных данных студентов в ней нет;
   - не видит аналитику, рейтинги, рекомендации, другие вузы и внутренние комментарии к этапам.
   Запрос к записи чужого вуза возвращает NOT_FOUND, а не FORBIDDEN, чтобы не раскрывать её существование.
10. **Разграничение доступа** в MVP — проверками в сервисах; для UNIVERSITY_REP фильтр по
    universityId накладывается в репозиториях через один общий хелпер, а не в каждом маршруте. Политики RLS в PostgreSQL (обещаны в
    концепции) — P2, до реализации честно указываются в SECURITY_LIMITATIONS.md.
11. **MarketDemand** — агрегированная таблица с происхождением: source, period, confidence, isMock.
12. **Источники рыночных данных** — интерфейс MarketDataProvider и реализации Mock, Csv, ExternalApi,
    FutureRtk. Активная выбирается через `MARKET_DATA_PROVIDER` в env.
13. **Интеграции** по умолчанию выключены через env. Сбой интеграции не ломает основную систему.
    Наличие конкретных API РТК не утверждать.
14. **Документы** в MVP — метаданные и ссылка (fileReference). Загрузка файлов — P2.

## Расхождения стартового каркаса с ТЗ

Текущий код — каркас, написан до получения ТЗ. Привести к ТЗ, сверив с аудитом:

- `Program` → `EducationalProgram`; `parallelStreams` → `groupCount`; добавить level, duration, status
- `ProgramSkill.coverage` → level, importance, source, confidence
- `Vacancy` и `VacancySkill` → `MarketDemand`
- `/api/analytics/market-demand`, `/api/analytics/skill-gap` → `/api/skills/demand`, `/api/skills/gaps`
- `src/lib/*` → `src/modules/*` и `src/shared/*`; `rules.ts` → `shared/config/analytics.config.ts`
- в формат ошибки добавить `code`

## Данные

- Демонстрационные данные никогда не выдаются за реальные: `isMock` и источник есть в каждом
  аналитическом ответе, фронт обязан это показать.
- Все коэффициенты — в shared/config с комментарием `// TEMP`. Формулы — в docs/ANALYTICS_METHODOLOGY.md.
- Персональные данные — минимум: ФИО, должность, рабочие email и телефон. Не писать их в логи.
  Реальные персональные данные в демо не использовать.
