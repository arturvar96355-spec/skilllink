## Коротко

Серверная часть закрыта полностью: приоритет P0, приоритет P1 и большая часть P2.
Работает демонстрационный контур API → backend → база. Фронту отдан машиночитаемый
контракт, по которому генерируется типизированный клиент.

| | |
| --- | --- |
| Модулей | 16 |
| Маршрутов / операций | 53 / 65 |
| Строк кода без сгенерированного | ~20 000, из них 2 900 тестов |
| Юнит-тестов | 543 |
| Проверок сквозного сценария | 327 |
| Проверок пробника | 144 |
| Документов | 18 |
| Коммитов | 56 |

Всё зелёное на чистом клоне, на промышленной сборке и в контейнере.

>

> к API по сети, ему нужен сам код. Одних документов недостаточно.
>

## Что сделано

### P0 — демонстрационный контур

- Реестры вузов, образовательных программ, навыков и IT-продуктов: поиск, фильтры,
  сортировка, пагинация, архивирование и возврат из архива.
- Связка «вуз — программа — IT-продукт» как единица учёта.
- **Workflow из 14 этапов** по разделу 8 ТЗ: машина состояний, чек-листы, нормативные
  сроки, история изменений с автором и временем, автоматический контрольный этап,
  просроченные и заблокированные этапы.
- Дашборд по разделу 7.1: у каждого показателя есть значение, единица, происхождение
  и признак демонстрационных данных.
- Демонстрационный набор данных.

### P1 — аналитика, роли, документы

- **Рейтинг программ** по трём показателям ТЗ с раскрытием вклада каждого.
- **Рейтинг вуза** (пункт 7.2 ТЗ) — агрегат рейтингов его программ, с фильтрацией
  и сортировкой реестра по нему.
- **Дефицит навыков** (skill gap): сопоставление спроса рынка с содержанием программ.
- **Рекомендации** — пять правил: просроченный этап, застой связки, связка без продукта
  на этапе оформления, недостающие показатели, критичный дефицит навыка при наличии
  подходящего продукта. У каждой рекомендации — основание, связанные данные, приоритет,
  уверенность и статус.
- **Документы**: жизненный цикл, история статусов, версионирование.
- **Встречи**: участники, результат, следующее действие со сроком.
- **Кабинет представителя вуза**: свой вуз и только он, подтверждение получения
  материалов, ввод численности и групп, подача заявок на обучение.
- **Аутентификация**: вход по паролю (NextAuth.js, сессии на JWT, пароли хешами bcrypt),
  ограничение перебора: пять неудач закрывают учётную запись на 15 минут.
- **Интеграционный слой**: интерфейсы источников рыночных данных, LMS и сайта,
  mock-реализации, настройки из переменных окружения.

### P2 — сверх обязательного

- **Журнал действий** и человекочитаемая **лента событий вуза**.
- **Групповые операции по IT-продукту**: выпуск новой версии одним действием ставит
  задачи во всех связках и переоткрывает закрытые этапы передачи материалов.
  С предпросмотром — видно, что изменится, до нажатия.
- **Сборка пакета документов из шаблонов** с автоподстановкой реквизитов.
- **Выгрузка и загрузка реестров в CSV** для Excel, с предпросмотром при загрузке.
- **Спецификация OpenAPI**, собранная из тех же схем, которыми API проверяет вход.
- **Защитные заголовки** в каждом ответе и ограничение перебора пароля.
- **Предупреждение о сроке**: этап помечается «вот-вот просрочится» за три дня —
  система создана, чтобы успевать, а не отчитываться о пропущенном.
- **Контейнеризация**: образ приложения, стек `docker compose`, непрерывная интеграция.
- **Проверка скорости на объёме** воспроизводится командой: `npm run volume` наполняет
  отдельную базу, `npm run bench` замеряет.

## Что проверено

- **543 юнит-теста** — правила переходов, расчёты, валидация, права.
- **327 проверок сквозного сценария** — демонстрационный сценарий раздела 18 ТЗ целиком.
- **137 проверок пробника** — то, чего система делать не должна: не пускать представителя
  вуза к чужим данным, не оставлять противоречивых состояний, не падать на кривом вводе,
  переживать двойной клик.
- **Развёртывание с нуля** — чистый клон, пустая база, промышленная сборка: всё проходит.
- **Путь нового человека пройден целиком** — от присланного архива до открытой
  страницы, на машине с выключенным локальным PostgreSQL. Дважды.
- **Вход проверен в браузере**, а не заголовками: `signIn`, `useSession`, `signOut`.
- **Промышленная сборка** — `npm run build` и `npm start` на чистой базе: сценарий
  и пробник проходят полностью, ровно как это делает непрерывная интеграция.
- **Контейнер** — образ собран и запущен, сценарий и пробник проходят против него.
- **Объём** — проверяется командой, а не на слово: `npm run volume` наполняет отдельную
  базу, `npm run bench` замеряет. На 1 000 вузов, 6 000 программ и 42 000 этапов самая
  медленная страница отвечает за 35 мс.

По ходу работы найдено и исправлено **37 ошибок**, из них 19 — уже после того,
как система «работала»: изоляция кабинета вуза, противоречивые состояния,
гонки при двойном клике, сборка образа, развёртывание с чистого клона, перенаправление
входа на несуществующую страницу.

Последняя проверка перед передачей нашла ещё шесть — все в том, что команда читает
и видит первым:

- Пять рабочих возможностей не были описаны в контракте API: лента событий вуза,
  журнал действий, выгрузка в CSV, групповая операция по продукту и сама спецификация.
  Фронт просто не узнал бы, что они есть.
- Документ связи экранов с API утверждал, что ленты событий и групповых операций
  **не существует**, хотя обе работали. По нему эти экраны не стали бы делать.
- Число маршрутов было написано в четырёх местах четырьмя разными значениями.
- Настройка частоты обращений к внешним сервисам читалась кодом, но нигде
  не упоминалась.
- Посев демо-данных не заполнял журнал действий: администратор открывал пустой
  раздел при трёх десятках завершённых этапов.
- Показатель «этапы, закрытые в срок» по построению равнялся 100 % — контроль
  сроков было нечем показать на защите.

### Сплошной разбор кода перед передачей

Отдельно прогнан многоагентный разбор кодовой базы по шести направлениям —
совместимость с Windows, разграничение доступа, логика расчётов, что сломается
у фронта, целостность данных, запуск и эксплуатация. Каждая находка проверялась
вторым агентом на воспроизводимость, затем я проверял её сам.

**Подтверждено и исправлено 24 находки.** Наиболее серьёзные:

- **Обёртка запроса к своему API отправляла cookie пользователя куда попросят.**
  Адрес брался из заголовка `X-Forwarded-Host`, который задаёт клиент. Открыл
  страницу с подделанным заголовком — сервер пошёл на чужой домен с сессией
  пользователя. Дыру я внёс сам за час до этого, починяя другую проблему.
- **Контейнер получал вход без пароля из хостового `.env`.** Первым шагом
  установки человек делает `cp .env.example .env`, а compose подставлял оттуда
  `DEMO_AUTH_ENABLED=true`. README при этом обещал обратное.
- **Без секрета подписи контейнер считался здоровым**, отдавая 500 на всё,
  кроме самой проверки живости. Оркестратор пустил бы на него трафик.
- **Рейтинг программ зависел от размера среза** и порядка строк: один и тот же
  балл мог быть 61,3 или 75,3 без изменения данных.
- **Закрытая связка требовала внимания вечно** — её просроченные этапы висели
  на дашборде, хотя менять их система запрещает.
- **Код из задания фронту не компилировался**: поля перечислений были объявлены
  как строки, и подписи не индексировались.
- **Загрузка CSV стирала поля**, которых нет в файле, и создавала двойников
  при повторе названия внутри одного файла.

Три находки оставлены осознанно — они относятся к тому, чего в MVP нет;
причины записаны в журнале работ.

Чтобы первые три не повторились, **три теста сверяют документы с кодом**: каждый
маршрут обязан быть описан в контракте, каждое число вида «N маршрутов» — совпадать
с действительностью, каждая читаемая переменная окружения — присутствовать
в `.env.example`. Все три проверены контрольным опытом: подложил лишний маршрут,
заведомо неверное число и убрал переменную — тесты упали с понятным сообщением.

### Осознанное решение исполнителя

**Политики доступа на уровне строк (RLS) в PostgreSQL.** Концепция их обещает.
Сейчас разграничение доступа работает проверками в сервисах и фильтром по вузу
в репозиториях — это проверено пробником и закрывает задачу функционально.

Полноценный RLS требует прогонять каждый запрос через транзакцию с установкой
переменной сессии, то есть переделать все репозитории. Делать такую переработку
перед самой передачей команде — значит рисковать работоспособностью ради строчки
в отчёте. Ограничение честно описано в `docs/SECURITY_LIMITATIONS.md`.

**Если решение неверное — скажите, сделаю отдельной задачей.**

### Отложено по согласованному решению

Загрузка файлов документов — решение 14 относит её к P2, в MVP хранятся метаданные,
ссылка и текст, собранный из шаблона.

## Границы, о которых сказано честно

- **Соответствие 152-ФЗ и приказу ФСТЭК № 117 не заявляется** — требования учитывались
  при проектировании, но без отдельного аудита утверждать соответствие нельзя.
- **Демонстрационные данные помечены** `isMock` и не выдаются за подтверждённую
  статистику. Интерфейс обязан показывать пометку.
- **Автоматический сбор рыночных данных не реализован** — используется подготовленный
  набор, как и сказано в ограничениях прототипа.
- **Перед выкладыванием наружу** обязательно: выключить демо-режим входа без пароля,
  задать стойкий секрет подписи, сменить демонстрационные пароли, включить HTTPS.
  Полный список — `docs/SECURITY_LIMITATIONS.md`.
