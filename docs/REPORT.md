## Коротко

Серверная часть закрыта полностью: приоритет P0, приоритет P1 и большая часть P2.
Работает демонстрационный контур API → backend → база. Фронту отдан машиночитаемый
контракт, по которому генерируется типизированный клиент.

## Что сделано

### P0 — демонстрационный контур

- Реестры вузов, образовательных программ, навыков и IT-продуктов: поиск, фильтры,
  сортировка, пагинация, архивирование и возврат из архива.
- Связка «вуз — программа — IT-продукт» как единица учёта.
- **Workflow из 14 этапов** по разделу 8 ТЗ: машина состояний, чек-листы, нормативные
  сроки, история изменений с автором и временем, автоматический контрольный этап,
  просроченные и заблокированные этапы.
- Дашборд по разделу 7.1: у каждого показателя есть значение, единица, происхождение
  и признак демонстрационных данных.
- Демонстрационный набор данных.

### P1 — аналитика, роли, документы

- **Рейтинг программ** по трём показателям ТЗ с раскрытием вклада каждого.
- **Дефицит навыков** (skill gap): сопоставление спроса рынка с содержанием программ.
- **Рекомендации** — пять правил: просроченный этап, застой связки, связка без продукта
  на этапе оформления, недостающие показатели, критичный дефицит навыка при наличии
  подходящего продукта. У каждой рекомендации — основание, связанные данные, приоритет,
  уверенность и статус.
- **Документы**: жизненный цикл, история статусов, версионирование.
- **Встречи**: участники, результат, следующее действие со сроком.
- **Кабинет представителя вуза**: свой вуз и только он, подтверждение получения
  материалов, ввод численности и групп, подача заявок на обучение.
- **Аутентификация**: вход по паролю (NextAuth.js, сессии на JWT, пароли хешами bcrypt).
- **Интеграционный слой**: интерфейсы источников рыночных данных, LMS и сайта,
  mock-реализации, настройки из переменных окружения.

### P2 — сверх обязательного

- **Журнал действий** и человекочитаемая **лента событий вуза**.
- **Групповые операции по IT-продукту**: выпуск новой версии одним действием ставит
  задачи во всех связках и переоткрывает закрытые этапы передачи материалов.
  С предпросмотром — видно, что изменится, до нажатия.
- **Сборка пакета документов из шаблонов** с автоподстановкой реквизитов.
- **Выгрузка и загрузка реестров в CSV** для Excel, с предпросмотром при загрузке.
- **Спецификация OpenAPI**, собранная из тех же схем, которыми API проверяет вход.
- **Контейнеризация**: образ приложения, стек `docker compose`, непрерывная интеграция.

## Что проверено

- **382 юнит-теста** — правила переходов, расчёты, валидация, права.
- **311 проверок сквозного сценария** — демонстрационный сценарий раздела 18 ТЗ целиком.
- **60 проверок пробника** — то, чего система делать не должна: не пускать представителя
  вуза к чужим данным, не оставлять противоречивых состояний, не падать на кривом вводе,
  переживать двойной клик.
- **Развёртывание с нуля** — чистый клон, пустая база, промышленная сборка: всё проходит.
- **Контейнер** — образ собран и запущен, сценарий и пробник против него проходят.
- **Объём** — на базе со 120 вузами, 360 связками и 5040 этапами страницы отвечают
  быстрее 40 мс.

По ходу работы найдено и исправлено **29 ошибок**, из них 11 — уже после того,
как система «работала»: изоляция кабинета вуза, противоречивые состояния,
гонки при двойном клике, сборка образа, развёртывание с чистого клона.

## Что не сделано

### Зависит от других

| Что | От кого |
| --- | --- |
| Подключение интерфейса к API | Ваня и Серёжа: нужен их код и макеты |
| Рейтинг вуза как отдельный показатель | Артур: пункт 7.2 ТЗ требует фильтрацию вузов по рейтингу, но рейтинг считается у программ |
| Уведомления | Артур: не определён канал — почта или в интерфейсе |
| Тексты шаблонов документов | юридическая служба: сейчас это болванки с пометкой TEMP |

### Осознанное решение исполнителя

**Политики доступа на уровне строк (RLS) в PostgreSQL.** Концепция их обещает.
Сейчас разграничение доступа работает проверками в сервисах и фильтром по вузу
в репозиториях — это проверено пробником и закрывает задачу функционально.

Полноценный RLS требует прогонять каждый запрос через транзакцию с установкой
переменной сессии, то есть переделать все репозитории. Делать такую переработку
перед самой передачей команде — значит рисковать работоспособностью ради строчки
в отчёте. Ограничение честно описано в `docs/SECURITY_LIMITATIONS.md`.

**Если решение неверное — скажите, сделаю отдельной задачей.**

### Отложено по согласованному решению

Загрузка файлов документов — решение 14 относит её к P2, в MVP хранятся метаданные,
ссылка и текст, собранный из шаблона.

## Что требуется от команды

### Ване и Серёже (интерфейс)

1. **Положить экспорт макетов в `docs/design/`** — это самое срочное. Сейчас связь
   экранов с API составлена по экранам ТЗ, а не по вашим. Расхождения вскроются
   при подключении, в самое дорогое время.
2. Начать можно уже сейчас: `docs/openapi.json` → типизированный клиент,
   `docs/API_CONTRACT.md` → поля ответов, `docs/HANDOFF.md` → правила и подводные камни.
3. Учесть, что в макетах, скорее всего, нет экранов: **входа**, **кабинета
   представителя вуза**, **рекомендаций**, **ленты событий**, **выгрузки**.
   API под них готов.

### Тиграну (база данных)

Согласовать три добавки к схеме — обоснование каждой в `docs/DATABASE_SCHEMA.md`:

1. Таблица `contacts` — контактных лиц у вуза бывает несколько.
2. `recommendations.resolution_comment` — комментарий сотрудника отдельно от
   обоснования системы.
3. `documents.content`, `documents.template_key` — текст, собранный из шаблона.

Плюс два вопроса: расчёт рейтинга сейчас в приложении, а не представлениями СУБД;
уникальности на тройку «вуз — программа — продукт» намеренно нет.

Для загрузки реальных данных есть `POST /api/import` — вузы и программы из CSV
с предпросмотром, без ручного SQL.

### Артуру (приёмка)

**10 решений**, полный список в `docs/PROGRESS.md`. Главные:

1. Веса рейтинга программ — сейчас 0,4 / 0,4 / 0,2.
2. Нормативные сроки 14 этапов и состав обязательных пунктов чек-листов.
3. Пороги правил рекомендаций — 7 и 21 день просрочки, 14 дней застоя.
4. Тексты шаблонов документов.
5. Нужен ли рейтинг вуза отдельным показателем.

Все значения вынесены в настройки и меняются без правки логики.

**Завести репозиторий на GitHub** — непрерывная интеграция настроена и заработает сама.

## Границы, о которых сказано честно

- **Соответствие 152-ФЗ и приказу ФСТЭК № 117 не заявляется** — требования учитывались
  при проектировании, но без отдельного аудита утверждать соответствие нельзя.
- **Демонстрационные данные помечены** `isMock` и не выдаются за подтверждённую
  статистику. Интерфейс обязан показывать пометку.
- **Автоматический сбор рыночных данных не реализован** — используется подготовленный
  набор, как и сказано в ограничениях прототипа.
- **Перед выкладыванием наружу** обязательно: выключить демо-режим входа без пароля,
  задать стойкий секрет подписи, сменить демонстрационные пароли, включить HTTPS.
  Полный список — `docs/SECURITY_LIMITATIONS.md`.
