# Развёртывание на сервере

Стенд поднимается одной командой на любой Ubuntu с доступом по SSH: Yandex Cloud,
Timeweb Cloud, VDS у другого российского провайдера. Провайдер ничем не зашит.

На сервере в контейнерах работают три вещи: PostgreSQL, приложение и Caddy.
Наружу открыты только 80 и 443 — база и приложение слушают `127.0.0.1`.
Caddy сам получает и продлевает сертификат, если у стенда есть домен.

---

## 1. Что купить

| | Что брать | Почему именно так |
| --- | --- | --- |
| Процессор | 2 ядра, доля не ниже 50% | Образ собирается на самом сервере; на доле 20% сборка тянется очень долго |
| Память | 4 ГБ | На 2 ГБ сборка Next.js падает в середине. Развёртывание включает подкачку, но 4 ГБ спокойнее |
| Диск | 20–30 ГБ SSD | Образы и база — единицы гигабайт |
| ОС | **Ubuntu 24.04 LTS** | На ней всё проверено |
| Адрес | Публичный, **статический** | При перезапуске адрес не меняется: иначе слетают и вход, и сертификат |

Прерываемая (preemptible) машина не подходит: провайдер выключает её в любой момент.

**Домен** — 200–300 ₽ в год. Без него стенд работает только по `http`, и пароли
идут открытым текстом. С доменом сертификат выпускается сам.

Зона `.ru` требует подтверждения личности у регистратора и может ждать днями —
на это наткнулись. Международные `.site`, `.online`, `.tech` начинают работать
через минуты после оплаты. Сертификат выдаёт Let's Encrypt — это удостоверяющий
центр, а не облако: данные стенда туда не уходят, только имя домена.

## 2. Создать машину

1. Создайте виртуальную машину с Ubuntu 24.04 по характеристикам выше.
2. Укажите логин (например, `skilllink`) и **публичный ключ SSH** — содержимое
   `~/.ssh/id_ed25519.pub`. Нет ключа: `ssh-keygen -t ed25519`.
3. В группе безопасности (файрволе провайдера) откройте входящие **22, 80, 443**.
   Порт 22 разумно ограничить своим адресом. Больше ничего открывать не нужно:
   база и приложение наружу не смотрят.
4. Проверьте вход: `ssh skilllink@<адрес>` — дальше всё делает скрипт.

Если берёте домен: в его DNS заведите запись **A** на адрес машины и дождитесь,
пока `ping <домен>` покажет этот адрес. Пока запись не разошлась, Caddy не сможет
получить сертификат.

## 3. Развернуть

```bash
scripts/deploy/deploy.sh skilllink@<адрес> <домен>   # с HTTPS
scripts/deploy/deploy.sh skilllink@<адрес>           # только http, по адресу
```

Первый раз — с демонстрационными данными:

```bash
SEED=1 scripts/deploy/deploy.sh skilllink@<адрес> <домен>
```

Что происходит:

1. **Подготовка сервера** — Docker и подкачка, если их ещё нет. Повторный запуск
   ничего не переставляет.
2. **Секреты** — при первом развёртывании создаются на сервере в `~/skilllink/.env.cloud`:
   пароль базы, секрет подписи сессий и пароль демо-пользователей. Каждый случайный,
   в git не попадает. Дальше они переиспользуются.
3. **Код** — уходит через `git archive`: только то, что лежит в git, текущий коммит.
   Доступ к GitHub на сервере не нужен, `.env` и личные файлы не уезжают.
4. **Запуск** — база, затем миграции, затем приложение и Caddy. Порядок важен:
   приложение без применённых миграций не проходит проверку живости, а Caddy ждёт
   здорового приложения.
5. **Проверка снаружи** — тем же `check.sh`, см. ниже.

В конце печатается адрес стенда и пароль демо-пользователей. **На стенде пароль
не `skilllink`**: он записан в документации, и по нему вошёл бы любой её читатель.

### Обновить стенд

Та же команда. Данные в базе остаются, миграции применяются, приложение
пересобирается. Демонстрационные данные перезаписываются только с `SEED=1` —
это полная очистка и заполнение заново.

Образ для миграций собирается заново при каждом развёртывании. До 23.09.2026
он собирался один раз: `docker compose run` берёт уже имеющийся образ и сам его
не обновляет. Стенд жил с приложением от 23-го и миграциями от 22-го — новая
миграция не дошла бы до базы, а `SEED=1` залил бы старый набор.

### Перезалить демо-данные перед показом

```bash
scripts/deploy/reseed.sh skilllink@<адрес> <домен>
```

Только данные: приложение не пересобирается и не перезапускается. Команда
спрашивает подтверждение, заливает набор заново и сразу сверяет стенд
со сценарием показа (`npm run demo:check`, см. ниже).

**Зачем.** Даты демо-набора отсчитываются от момента заливки. Через двое суток
у первого этапа УрФУ выходит срок, и на главной вместо четырёх проблемных этапов
становится пять. Докладчик говорит «четыре», а на экране другое число. Поэтому перезаливка — накануне вечером или утром
в день показа, и ещё раз после генерального прогона, чтобы убрать всё,
что на нём нажимали.

**Что учесть.**

- Стирается всё, что вносили руками, включая пользователей.
- Открытые вкладки попросят войти снова: пользователи создаются с новыми
  идентификаторами. Входить — после перезаливки.
- Сборка образа — от секунд до семи минут, если кэш сборки вычищен.
  Не запускать за пять минут до показа.
- `DRY_RUN=1` — всё, кроме самой заливки: так проверяется команда без
  изменения данных.

### Сверить стенд со сценарием показа

```bash
SEED_DEMO_PASSWORD=<пароль стенда> npm run demo:check -- https://<домен>
npm run demo:check -- http://localhost:3100      # запасной ноутбук, пароль skilllink
```

Только чтение, запускать против живого стенда можно. Входит менеджером
и представителем вуза и сверяет со сценарием показа (числа — в `scripts/demo-check.ts`) каждое число, которое
докладчик произносит вслух: показатели главной, четыре проблемных этапа,
баллы вузов по порядку, состояние этапов 6 и 7 у СПбГУТ (на них держатся
оба отказа), верх ленты рекомендаций, кабинет представителя и его запреты.

## 4. Проверить

```bash
DEMO_PASSWORD=<пароль> scripts/deploy/check.sh https://<домен>
```

Проверяется то, что не видно по «сайт открывается»:

- приложение видит базу и миграции применены;
- вход без пароля выключен (`/api/me` без сессии отвечает 401);
- ответы API несут заголовки ограничения частоты `RateLimit-*` (решение 117) — один
  запрос, предел не исчерпывается. Caddyfile для этого не менялся, перезапуск Caddy
  не нужен;
- защитные заголовки на месте;
- у страниц полная Content-Security-Policy: скрипты только по nonce, без `unsafe-eval`,
  за HTTPS — с `upgrade-insecure-requests` (решение 112);
- `http` перенаправляется на `https`, сертификат принимается без оговорок;
- порты базы (5432) и приложения (3000) закрыты снаружи;
- после входа пользователь остаётся на адресе стенда, а не уезжает на `localhost`;
- страница входа открывается и с устаревшей сессией — иначе после перезаливки
  демо-данных у всех, кто входил раньше, стенд показывал бы пустой экран
  (решение 48);
- страницы не кэшируются браузером без проверки.

Последнее — не теория: без переменной `AUTH_URL` именно это и происходит
(`TECHNICAL_DECISIONS.md`, решение 36).

**Про порты.** Проверка сначала стучится в заведомо пустой порт. Если и он
«отвечает», значит между вами и сервером посредник, принимающий любое
соединение: так ведут себя корпоративные сети, часть VPN и мобильные
операторы. Тогда проверка портов пропускается с предупреждением — в такой
сети она показала бы открытым всё подряд, и настоящую дыру никто не заметил бы.
Проверить наверняка можно с сервера:

```bash
ssh skilllink@<адрес> "ss -tlnp | grep -E '3000|5432'"
```

Строки должны начинаться с `127.0.0.1:` — значит, порты доступны только
изнутри машины.

## 5. Если что-то не так

Первым делом — `/api/health`: он называет причину, а не «ошибка».

| Ответ | Что случилось | Что делать |
| --- | --- | --- |
| `database: auth-failed` | Пароль в настройках разошёлся с тем, с которым создана база | Развёртывание чинит это само: приводит пароль базы к `.env.cloud` |
| `database: unreachable` | Контейнер базы не запущен или не отвечает | `docker compose -p skilllink ps`, журнал базы |
| `database: database-missing` | Сервер отвечает, базы с таким именем нет | Проверьте `POSTGRES_DB` |
| `schema: missing` | Миграции не применены | Повторите развёртывание |
| `status: misconfigured` | Не задан `AUTH_SECRET` или `DATABASE_URL` | Проверьте `~/skilllink/.env.cloud` |

Журналы:

```bash
ssh skilllink@<адрес> "cd ~/skilllink/app && docker compose -p skilllink logs --tail 50 app"
ssh skilllink@<адрес> "cd ~/skilllink/app && docker compose -p skilllink logs --tail 50 caddy"
```

**Сертификат не выпускается.** Смотрите журнал Caddy. Обычные причины: запись A
ещё не разошлась по DNS, закрыт порт 80 (он нужен для проверки владения доменом),
домен указывает на другой адрес.

**Не скачиваются образы.** Если провайдер или Docker Hub недоступны, `docker`
останавливается на `pull`. Тогда нужен доступный реестр-зеркало — настраивается
в `/etc/docker/daemon.json`, после чего `systemctl restart docker`.

**Соединение оборвалось посреди сборки** («Connection closed by remote host»).
Работает прежняя версия: новая поднимается только в самом конце. Подождите,
пока на сервере закончится начатая сборка (`ps aux | grep "docker-compose compose"`),
и повторите команду — слои возьмутся из кэша. Отметка `DEPLOYED_COMMIT` пишется
только после того, как стенд поднялся, поэтому обновление по расписанию тоже
повторит попытку, а не сочтёт стенд свежим.

**Кончилось место.** `docker system prune -af` удаляет неиспользуемые образы
и кеш сборки. Тома с данными эта команда не трогает.

### Проверка «стенд жив»

`.github/workflows/stand-uptime.yml` каждые 30 минут открывает `/api/health` и страницу
входа (три попытки). Стенд не ответил — открывается задача «Стенд недоступен» с меткой
`stand-down` (письмо владельцу и наблюдающим за репозиторием), следующие неудачи дописываются
в неё; стенд поднялся — задача закрывается сама. Запустить руками: Actions → «Стенд жив» →
Run workflow. Адрес — переменная репозитория `STAND_URL`, по умолчанию `https://skilllink.site`.

### Роль базы для приложения (решение 89)

Приложение ходит в базу отдельной ролью `skilllink_app` без прав суперпользователя:
только данные таблиц, журнал действий — только читать и дописывать. Миграции,
перезаливка и сроки хранения идут ролью-владельцем через сервис `migrate`.

Включение (один раз; пароль — только `[0-9a-f]`, он встаёт в строку подключения):

```bash
ssh skilllink@<адрес>
cd ~/skilllink/app
C="docker compose -p skilllink -f docker-compose.yml -f deploy/yandex-cloud/compose.cloud.yml --env-file ~/skilllink/.env.cloud"
pw=$(openssl rand -hex 24)
$C exec -T -e APP_DB_PASSWORD="$pw" postgres psql -U skilllink -d skilllink < deploy/yandex-cloud/create-app-role.sql
echo "APP_DATABASE_URL=postgresql://skilllink_app:$pw@postgres:5432/skilllink?schema=public" >> ~/skilllink/.env.cloud
$C up -d app
```

Проверка: `$C exec -T postgres psql -U skilllink -d skilllink -c "select usename, count(*) from pg_stat_activity where datname='skilllink' group by 1"` —
у приложения `skilllink_app`; `npm run demo:check -- https://<домен>` — всё как в сценарии.

Откат: удалить строку `APP_DATABASE_URL` из `.env.cloud` и `$C up -d app` — приложение
вернётся к роли-владельцу. Сама роль ничему не мешает.

Скрипт можно запускать повторно: после новой миграции он не нужен (права на новые
таблицы выдаются автоматически), но и не повредит.

### Сроки хранения журнала (docs/PRIVACY.md, решение 88)

Журнал действий хранится год, адрес клиента в нём — 90 дней. Применяет скрипт:

```bash
ssh skilllink@<адрес> 'cd ~/skilllink/app && docker compose -p skilllink -f docker-compose.yml \
  -f deploy/yandex-cloud/compose.cloud.yml --env-file ~/skilllink/.env.cloud \
  --profile migrate run --rm migrate npm run db:retention'
```

Образ `migrate` — тот же, что у перезаливки (`reseed.sh`): в нём есть `scripts/` и `tsx`.

Без флага он только показывает, что удалит и где сотрёт адрес. Применить — добавить
`-- --apply`. **На демо-стенде до защиты не применять:** демо-набор начинается 400 дней
назад, и журнал завершённой связки уйдёт — изменится «Операций на связку».
Расписание (cron владельца сервера) пока не включено.

### Сводка в Telegram по расписанию (решение 102)

Бот личных уведомлений подключается по docs/SETUP.md, «Бот уведомлений в Telegram»
(токен, `setWebhook`, `TELEGRAM_API_IP=149.154.167.220` — из Yandex Cloud
`api.telegram.org` по имени не отвечает). Сводку «что горит у меня» по расписанию шлёт
скрипт — через тот же сервис `migrate`, что и перезаливка: в рабочем образе `scripts/`
и `tsx` нет.

Проверить, что уйдёт, ничего не отправляя:

```bash
ssh skilllink@<адрес> 'cd ~/skilllink/app && docker compose -p skilllink -f docker-compose.yml \
  -f deploy/yandex-cloud/compose.cloud.yml --env-file ~/skilllink/.env.cloud \
  --profile migrate run --rm migrate npm run telegram:digest -- --dry-run'
```

Строка для cron владельца сервера (`crontab -e` под `skilllink`) — по будням в 09:00 МСК
(на машине UTC, поэтому 6:00); `flock` не даёт двум запускам наложиться, в журнал
пишется только итог, без текста сводок:

```cron
0 6 * * 1-5 cd ~/skilllink/app && flock -n /tmp/skilllink-digest.lock docker compose -p skilllink -f docker-compose.yml -f deploy/yandex-cloud/compose.cloud.yml --env-file ~/skilllink/.env.cloud --profile migrate run --rm -T migrate npm run telegram:digest >> ~/skilllink/telegram-digest.log 2>&1
```

**Сам cron пока не поставлен** — решение владельца сервера. Без токена бота скрипт
пишет «Бот не настроен — рассылки нет» и выходит с кодом 0, так что строка безвредна
и до подключения. Код 1 — ни одно сообщение не ушло (Telegram недоступен): смотреть
`telegram-digest.log` и `TELEGRAM_API_IP`. Пустые сводки («ничего не горит») не шлются.

## 6. Чего в этом развёртывании нет

Сказано честно, чтобы не выглядело промышленным контуром:

- **Резервные копии — на той же машине.** С 25.09.2026 cron владельца сервера
  каждую ночь в 03:15 МСК кладёт копию в `~/backups` и удаляет копии старше 14 суток;
  с решения 137 следом пишет отметку `~/backups/last.json` для метрик
  (`backup_last_success_timestamp_seconds`, `backup_last_size_bytes` — раздел 10):

  ```bash
  15 3 * * * cd ~/skilllink/app && docker compose -p skilllink exec -T postgres pg_dump -Fc -U skilllink skilllink > ~/backups/skilllink-$(date +\%F).dump 2>>~/backups/errors.log && find ~/backups -name "skilllink-*.dump" -mtime +14 -delete && printf '{"timestamp": %s, "sizeBytes": %s}' "$(date +\%s)" "$(stat -c%s ~/backups/skilllink-$(date +\%F).dump)" > ~/backups/last.json
  ```

  **На уже развёрнутом стенде эту строку нужно переставить владельцу вручную**
  (`crontab -e`) — правка файла в git существующий `crontab` сама не трогает.

  От ошибки и порчи данных копии спасают, от потери всей машины — нет. Копирование
  вне сервера (Object Storage) подготовлено, включает владелец — раздел 9
  «Копии вне сервера». Там же на сервере с 25.09.2026 включены
  файрвол ufw (22, 80, 443), fail2ban для SSH, в `/etc/ssh/sshd_config.d/10-skilllink.conf`
  запрет входа root и `MaxAuthTries 3`; пакеты Docker придержаны
  (`apt-mark hold`) до конца проверки экспертами, чтобы автообновление не перезапустило
  стенд. После 14.10: `sudo apt-mark unhold docker.io containerd runc docker-compose-v2`.

  Снимок вручную:

  ```bash
  ssh skilllink@<адрес> "cd ~/skilllink/app && docker compose -p skilllink exec -T postgres \
    pg_dump -U skilllink skilllink" > dump.sql
  ```

  `-T` обязателен: без него `exec` выделяет терминал и портит файл переводами строк.

  Восстановление в новую базу (проверено: 0 ошибок, все таблицы совпали,
  русская сортировка колонок уцелела):

  ```bash
  ssh skilllink@<адрес> "cd ~/skilllink/app && docker compose -p skilllink exec -T postgres \
    psql -U skilllink -d postgres -c 'create database restored'"
  ssh skilllink@<адрес> "cd ~/skilllink/app && docker compose -p skilllink exec -T postgres \
    psql -U skilllink -d restored" < dump.sql
  ```
  **Проверено целиком 23.09.2026.** Дамп со стенда развёрнут в отдельную базу,
  приложение поднято на ней, и по восстановленной копии полностью прошли
  сквозной сценарий (327 проверок) и пробник (161). Все двенадцать колонок
  сохранили правило сравнения `ru-x-icu` — русская сортировка после
  восстановления работает.

  Если пароль демо-пользователей на стенде свой (а он свой), проверки нужно
  запускать с ним:

  ```bash
  APP_BASE_URL=http://localhost:3200 SEED_DEMO_PASSWORD=<пароль> npm run smoke
  ```

  Без этого пять проверок входа падают так, будто сломалась авторизация.

- **Метрики и правила оповещений есть (решение 137, раздел 10), Prometheus и
  Grafana на стенде не включены.** `GET /api/metrics` и правила
  (`deploy/monitoring/alert-rules.yml`) готовы; кто их читает и куда шлёт
  оповещения при срабатывании — решает владелец, включив профиль `monitoring`.
  До этого — по-прежнему только `/api/health` и перезапуск контейнера при падении.
- **Машина одна.** Её перезагрузка — простой стенда; контейнеры поднимутся сами.
- **Соответствие 152-ФЗ и приказу ФСТЭК № 117 не заявляется** — см.
  [SECURITY_LIMITATIONS.md](SECURITY_LIMITATIONS.md).

## 7. Что проверено

Развёртывание прогонялось целиком на настоящей Ubuntu 24.04: подготовка сервера,

## 9. Копии вне сервера (решение 114)

**Состояние: подготовлено, не включено.** Скрипты в репозитории; бакета, ключа и строки
cron на сервере ещё нет, ночные копии лежат только в `~/backups` на той же машине.

Как устроено: в 03:15 cron снимает ночную копию (раздел 6), в 03:45
`scripts/deploy/backup-offsite.sh` берёт её, проверяет, шифрует на сервере и кладёт
в приватный бакет Yandex Object Storage (регион `ru-central1`). Итог каждой ночи —
строкой в `~/backups/offsite.log`.

- **В облако уходит только шифр.** Копии содержат персональные данные, поэтому шифруются
  до отправки (AES-256, пароль `BACKUP_ENCRYPTION_PASSPHRASE`). Провайдер и тот, кто
  получит доступ к бакету, видят только шифр.
- **Пароль шифрования хранится и вне сервера** — в менеджере паролей владельца. Если
  машина потеряна, вместе с ней потерян `.env.cloud`; без пароля копии в бакете бесполезны.
- **Ключ доступа не может удалять.** У сервисного аккаунта одна роль — `storage.uploader`
  на один бакет: загружать и читать. Ключ, украденный с сервера, копии не сотрёт.
  Старые копии удаляет правило жизненного цикла бакета через 30 суток; скрипт каждую ночь
  проверяет, что оно работает.
- **На сервер ничего не ставится.** aws-cli запускается docker-образом `amazon/aws-cli`
  (≈700 МБ на диске, скачивается при первом запуске; после глубокой чистки диска
  при развёртывании — заново), `pg_restore` — в контейнере базы.
- **Копия проверяется до отправки целиком.** Ночной cron пишет в файл перенаправлением,
  и если `pg_dump` упал, файл всё равно есть — пустой или оборванный. `pg_restore -l`
  такой пропускает, если оглавление в начале цело; скрипт дочитывает все данные
  (`pg_restore -f /dev/null`) и ещё до загрузки проверяет, что зашифрованное расшифровывается
  в тот же файл.

Код выхода `backup-offsite.sh`: `0` — загружено; `1` — сбой, копии вне сервера за эту
ночь нет (причина — строкой `СБОЙ:` в журнале); `2` — загружено, но в бакете лежат копии
старше срока: правило жизненного цикла не настроено или не работает.

### 1. В консоли Yandex Cloud

В том же облаке и каталоге, где стоит машина стенда (console.yandex.cloud).

1. **Бакет.** Object Storage → «Создать бакет»:
   - имя — любое свободное, например `skilllink-backups-<ваше слово>` (имена бакетов
     общие на всё облако);
   - чтение объектов, списка объектов и настроек — **«С авторизацией»**, не «Для всех»;
   - класс хранилища по умолчанию — **«Холодное»**: копии читают редко, хранение
     дешевле. Скрипт и сам загружает в холодное (`STANDARD_IA`);
   - максимальный размер — например 5 ГБ: ночная копия демо-стенда — сотни килобайт, предел
     не даст случайно набрать счёт.
2. **Правило жизненного цикла.** Бакет → «Жизненный цикл» → «Настроить» → добавить правило:
   - префикс **`skilllink/`**;
   - «Удаление» (истечение срока) — через **30** дней;
   - если есть пункт про незавершённые составные загрузки — удалять через 1 день.
3. **Сервисный аккаунт.** «Сервисные аккаунты» → «Создать»: имя `skilllink-backup`,
   **ролей на каталог не давать**.
4. **Роль на бакет.** Бакет → «Права доступа» (в некоторых версиях консоли —
   «Безопасность» → «Права доступа») → «Назначить роли» → аккаунт `skilllink-backup` →
   роль **`storage.uploader`**. Только на этот бакет — не на каталог: иначе ключ
   увидит все бакеты каталога.
5. **Статический ключ.** Открыть аккаунт → «Создать новый ключ» → «Создать статический
   ключ доступа». Консоль покажет **идентификатор ключа** и **секретный ключ** —
   секрет один раз. Не закрывайте окно до шага 2 на сервере; в чат и в git не вставляйте.
6. **Пароль шифрования.** Сгенерируйте в менеджере паролей (или `openssl rand -base64 32`
   на своём компьютере) и **сохраните там**: он понадобится при восстановлении на новой
   машине. Не короче 20 символов, без `$` и кавычек.

### 2. На сервере: настройки

Строки дописываются в `~/skilllink/.env.cloud`; развёртывание их не трогает. Секреты
вводятся скрыто — не появляются на экране и в истории команд:

```bash
ssh skilllink@<адрес>
read -rp  'Имя бакета: ' b
read -rp  'Идентификатор ключа: ' k
read -rsp 'Секретный ключ: ' s; echo
read -rsp 'Пароль шифрования: ' p; echo
printf 'YC_S3_BUCKET=%s\nYC_S3_ACCESS_KEY_ID=%s\nYC_S3_SECRET_ACCESS_KEY=%s\nBACKUP_ENCRYPTION_PASSPHRASE=%s\n' \
  "$b" "$k" "$s" "$p" >> ~/skilllink/.env.cloud
unset b k s p
chmod 600 ~/skilllink/.env.cloud
```

Скрипты приезжают на сервер с кодом: если `ls ~/skilllink/app/scripts/deploy/backup-offsite.sh`
не находит файл, сначала обновите стенд (`deploy.sh`, раздел 3) — вне тихих окон показа.

### 3. Проверить до включения расписания

```bash
bash ~/skilllink/app/scripts/deploy/backup-offsite.sh; echo "код $?"
```

Первый запуск скачивает образ aws-cli — минута-другая. Ждём строку
`ГОТОВО: skilllink-<дата>.dump → s3://<бакет>/skilllink/skilllink-<дата>.dump.enc` и код 0.
В консоли в бакете, в папке `skilllink/`, появятся два объекта: копия `.dump.enc`
и её контрольная сумма `.dump.enc.sha256`.

Что может пойти не так — строка `СБОЙ:` скажет:

| В журнале | Что делать |
| --- | --- |
| `не заданы: …` | Не дописаны строки шага 2 |
| `старше 26 ч — ночная копия (cron 03:15) не отработала` | Смотрите `~/backups/errors.log` и `crontab -l` |
| `копия … оборвана или повреждена` | Ночная копия испорчена — её и не отправили; разобраться с `pg_dump` |
| `AccessDenied`, `SignatureDoesNotMatch`, `InvalidAccessKeyId` | Ключ введён с ошибкой или роль выдана не на тот бакет |
| `NoSuchBucket` | Имя бакета с опечаткой |
| `Could not connect to the endpoint URL` | Нет выхода в интернет с машины; повторите позже |

Сразу проверить обратный путь — скачать, сверить, расшифровать, прочитать, базу не создавая:

```bash
CHECK_ONLY=1 bash ~/skilllink/app/scripts/deploy/restore-offsite.sh
```

### 4. Включить расписание

Через полчаса после ночной копии (строка cron ночной копии — раздел 6):

```bash
(crontab -l; echo '45 3 * * * bash ~/skilllink/app/scripts/deploy/backup-offsite.sh') | crontab -
crontab -l
```

Утром после первой ночи: `tail -5 ~/backups/offsite.log` — строка `ГОТОВО` с сегодняшней
датой. Предупреждения о правиле жизненного цикла появятся не раньше чем через 33 дня,
если оно не работает.

**Когда включили** — поменять состояние в документах, по одной строке:
здесь («Состояние» в начале раздела), в PRIVACY.md (раздел 5, строка «Резервные копии
вне сервера») и в SECURITY_LIMITATIONS.md (раздел 2, строка «Резервной копии вне сервера»).

### 5. Восстановить

**Проверка восстановления** — раз в месяц и после изменений схемы. Скрипт восстанавливает
в **новую** базу рядом с рабочей; в рабочую он восстанавливать откажется:

```bash
bash ~/skilllink/app/scripts/deploy/restore-offsite.sh               # самая свежая → restored_ГГГГММДД
bash ~/skilllink/app/scripts/deploy/restore-offsite.sh 2026-09-25    # за дату
```

Он скачивает копию, сверяет контрольную сумму, расшифровывает, проверяет копию целиком,
восстанавливает без владельцев и прав (роль приложения к проверочной базе доступа
не получает) и печатает число строк каждой таблицы. Расшифрованный файл удаляется сам.
**В восстановленной базе персональные данные** — проверили, удалите её: команду
скрипт печатает последней строкой.

**Машина потеряна.** Проверено на копии локально, на живом стенде не прогонялось:

1. Новая машина и `deploy.sh` (разделы 2–3) — стенд поднимется с пустой базой.
2. Шаг 2 этого раздела на новой машине; пароль шифрования — из менеджера паролей.
3. `restore-offsite.sh <дата>` — копия встанет в базу `restored_<дата>`.
4. Поставить её на место рабочей и выдать права роли приложения:

   ```bash
   cd ~/skilllink/app
   C="docker compose -p skilllink -f docker-compose.yml -f deploy/yandex-cloud/compose.cloud.yml --env-file ~/skilllink/.env.cloud"
   $C stop app
   $C exec -T postgres psql -U skilllink -d postgres \
     -c 'alter database skilllink rename to skilllink_empty' \
     -c 'alter database restored_20260925 rename to skilllink'
   $C --profile app up -d
   ```

   Если приложение ходит ролью `skilllink_app` (раздел 5, «Роль базы для приложения») —
   перед `up` повторить `create-app-role.sql` с тем же паролем, что в `APP_DATABASE_URL`.
5. `scripts/deploy/check.sh` и `npm run demo:check` снаружи; пустую `skilllink_empty` удалить.

Без сервера копию можно открыть на любом компьютере с `openssl` и PostgreSQL 16: скачать
объект из консоли и расшифровать теми же параметрами, что у скрипта:

```bash
openssl enc -d -aes-256-cbc -pbkdf2 -iter 200000 -md sha256 \
  -in skilllink-2026-09-25.dump.enc -out skilllink-2026-09-25.dump   # спросит пароль
pg_restore -l skilllink-2026-09-25.dump | head
```

Расшифрованный файл — персональные данные: только на зашифрованном диске и в России
(PRIVACY.md, раздел 4), удалить после работы.

### Проверка без облака

`scripts/deploy/offsite-selftest.sh [база]` снимает копию локальной базы и прогоняет оба
скрипта по-настоящему, заменив aws-cli заглушкой (бакет — папка), а контейнер —
локальными `pg_restore` и `psql`: загрузка, восстановление со сверкой строк всех таблиц,
отказы (оборванная, пустая, устаревшая копия, чужой пароль, испорченный объект,
недоступное хранилище, рабочая база как цель) и отсутствие секретов в журнале.

## 10. Метрики, мониторинг и ворота выкладки (решение 137)

### Метрики сервера

### Мониторинг: Prometheus и Grafana

Подробности, как включить и проверить — `deploy/monitoring/README.md`. Коротко:

часть. Включает владелец осознанно:

```bash
export GRAFANA_ADMIN_PASSWORD=$(openssl rand -hex 12)
cp deploy/monitoring/metrics-token.example deploy/monitoring/metrics-token

docker compose --profile app --profile monitoring up -d
```

Правила оповещений — `deploy/monitoring/alert-rules.yml`: доля 5xx, время ответа,
живость базы, свежесть ночной копии, всплески отказов 429 и неудачных входов,
задержка цикла событий. У каждого правила — что посмотреть первым делом. Само
срабатывание правил никуда не шлётся, пока владелец не подключит получателя
(Alertmanager или любой другой) — это следующий шаг, не часть решения 137.

### Ворота выкладки: схема и миграции

CI (`ci.yml`) отклоняет пуш, если `schema.prisma` разошлась с `prisma/migrations`
(`prisma migrate diff --exit-code`). `scripts/deploy/deploy.sh` повторяет ту же
проверку локально перед тем, как код уйдёт на сервер — быстрее увидеть ошибку, чем
через несколько минут сборки; `scripts/deploy/remote-up.sh` на сервере проверяет
`prisma migrate status` перед накатом (останавливается на «failed» или изменённой
после применения миграции) и `_prisma_migrations` после — что накатилась именно
последняя папка. Подробности и причины — docs/TECHNICAL_DECISIONS.md, решение 137.

### Лимит тела запроса

Caddy режет тело раньше приложения — `deploy/yandex-cloud/Caddyfile`,
`request_body { max_size … }`, с запасом над самым большим пределом кода (2 МиБ,
импорт CSV). `scripts/deploy/check.sh` проверяет границу на развёрнутом стенде: чуть
меньше — обычный ответ, чуть больше — ровно 413.
