# Развёртывание на сервере

Стенд поднимается одной командой на любой Ubuntu с доступом по SSH: Yandex Cloud,
Timeweb Cloud, VDS у другого российского провайдера. Провайдер ничем не зашит.

На сервере в контейнерах работают три вещи: PostgreSQL, приложение и Caddy.
Наружу открыты только 80 и 443 — база и приложение слушают `127.0.0.1`.
Caddy сам получает и продлевает сертификат, если у стенда есть домен.

---

## 1. Что купить

| | Что брать | Почему именно так |
| --- | --- | --- |
| Процессор | 2 ядра, доля не ниже 50% | Образ собирается на самом сервере; на доле 20% сборка тянется очень долго |
| Память | 4 ГБ | На 2 ГБ сборка Next.js падает в середине. Развёртывание включает подкачку, но 4 ГБ спокойнее |
| Диск | 20–30 ГБ SSD | Образы и база — единицы гигабайт |
| ОС | **Ubuntu 24.04 LTS** | На ней всё проверено |
| Адрес | Публичный, **статический** | При перезапуске адрес не меняется: иначе слетают и вход, и сертификат |

Прерываемая (preemptible) машина не подходит: провайдер выключает её в любой момент.

**Домен** — 200–300 ₽ в год. Без него стенд работает только по `http`, и пароли
идут открытым текстом. С доменом сертификат выпускается сам.

Зона `.ru` требует подтверждения личности у регистратора и может ждать днями —
на это наткнулись. Международные `.site`, `.online`, `.tech` начинают работать
через минуты после оплаты. Сертификат выдаёт Let's Encrypt — это удостоверяющий
центр, а не облако: данные стенда туда не уходят, только имя домена.

## 2. Создать машину

1. Создайте виртуальную машину с Ubuntu 24.04 по характеристикам выше.
2. Укажите логин (например, `skilllink`) и **публичный ключ SSH** — содержимое
   `~/.ssh/id_ed25519.pub`. Нет ключа: `ssh-keygen -t ed25519`.
3. В группе безопасности (файрволе провайдера) откройте входящие **22, 80, 443**.
   Порт 22 разумно ограничить своим адресом. Больше ничего открывать не нужно:
   база и приложение наружу не смотрят.
4. Проверьте вход: `ssh skilllink@<адрес>` — дальше всё делает скрипт.

Если берёте домен: в его DNS заведите запись **A** на адрес машины и дождитесь,
пока `ping <домен>` покажет этот адрес. Пока запись не разошлась, Caddy не сможет
получить сертификат.

## 3. Развернуть

```bash
scripts/deploy/deploy.sh skilllink@<адрес> <домен>   # с HTTPS
scripts/deploy/deploy.sh skilllink@<адрес>           # только http, по адресу
```

Первый раз — с демонстрационными данными:

```bash
SEED=1 scripts/deploy/deploy.sh skilllink@<адрес> <домен>
```

Что происходит:

1. **Подготовка сервера** — Docker и подкачка, если их ещё нет. Повторный запуск
   ничего не переставляет.
2. **Секреты** — при первом развёртывании создаются на сервере в `~/skilllink/.env.cloud`:
   пароль базы, секрет подписи сессий и пароль демо-пользователей. Каждый случайный,
   в git не попадает. Дальше они переиспользуются.
3. **Код** — уходит через `git archive`: только то, что лежит в git, текущий коммит.
   Доступ к GitHub на сервере не нужен, `.env` и личные файлы не уезжают.
4. **Запуск** — база, затем миграции, затем приложение и Caddy. Порядок важен:
   приложение без применённых миграций не проходит проверку живости, а Caddy ждёт
   здорового приложения.
5. **Проверка снаружи** — тем же `check.sh`, см. ниже.

В конце печатается адрес стенда и пароль демо-пользователей. **На стенде пароль
не `skilllink`**: он записан в документации, и по нему вошёл бы любой её читатель.

### Обновить стенд

Та же команда. Данные в базе остаются, миграции применяются, приложение
пересобирается. Демонстрационные данные перезаписываются только с `SEED=1` —
это полная очистка и заполнение заново.

Образ для миграций собирается заново при каждом развёртывании. До 23.09.2026
он собирался один раз: `docker compose run` берёт уже имеющийся образ и сам его
не обновляет. Стенд жил с приложением от 23-го и миграциями от 22-го — новая
миграция не дошла бы до базы, а `SEED=1` залил бы старый набор.

### Перезалить демо-данные перед показом

```bash
scripts/deploy/reseed.sh skilllink@<адрес> <домен>
```

Только данные: приложение не пересобирается и не перезапускается. Команда
спрашивает подтверждение, заливает набор заново и сразу сверяет стенд
со сценарием показа (`npm run demo:check`, см. ниже).

**Зачем.** Даты демо-набора отсчитываются от момента заливки. Через двое суток
у первого этапа УрФУ выходит срок, и на главной вместо четырёх проблемных этапов
становится пять. Докладчик говорит «четыре», а на экране другое число. Поэтому перезаливка — накануне вечером или утром
в день показа, и ещё раз после генерального прогона, чтобы убрать всё,
что на нём нажимали.

**Что учесть.**

- Стирается всё, что вносили руками, включая пользователей.
- Открытые вкладки попросят войти снова: пользователи создаются с новыми
  идентификаторами. Входить — после перезаливки.
- Сборка образа — от секунд до семи минут, если кэш сборки вычищен.
  Не запускать за пять минут до показа.
- `DRY_RUN=1` — всё, кроме самой заливки: так проверяется команда без
  изменения данных.

### Сверить стенд со сценарием показа

```bash
SEED_DEMO_PASSWORD=<пароль стенда> npm run demo:check -- https://<домен>
npm run demo:check -- http://localhost:3100      # запасной ноутбук, пароль skilllink
```

Только чтение, запускать против живого стенда можно. Входит менеджером
и представителем вуза и сверяет с `docs/DEMO.md` каждое число, которое
докладчик произносит вслух: показатели главной, четыре проблемных этапа,
баллы вузов по порядку, состояние этапов 6 и 7 у СПбГУТ (на них держатся
оба отказа), верх ленты рекомендаций, кабинет представителя и его запреты.

## 4. Проверить

```bash
DEMO_PASSWORD=<пароль> scripts/deploy/check.sh https://<домен>
```

Проверяется то, что не видно по «сайт открывается»:

- приложение видит базу и миграции применены;
- вход без пароля выключен (`/api/me` без сессии отвечает 401);
- защитные заголовки на месте;
- `http` перенаправляется на `https`, сертификат принимается без оговорок;
- порты базы (5432) и приложения (3000) закрыты снаружи;
- после входа пользователь остаётся на адресе стенда, а не уезжает на `localhost`;
- страница входа открывается и с устаревшей сессией — иначе после перезаливки
  демо-данных у всех, кто входил раньше, стенд показывал бы пустой экран
  (решение 48);
- страницы не кэшируются браузером без проверки.

Последнее — не теория: без переменной `AUTH_URL` именно это и происходит
(`TECHNICAL_DECISIONS.md`, решение 36).

**Про порты.** Проверка сначала стучится в заведомо пустой порт. Если и он
«отвечает», значит между вами и сервером посредник, принимающий любое
соединение: так ведут себя корпоративные сети, часть VPN и мобильные
операторы. Тогда проверка портов пропускается с предупреждением — в такой
сети она показала бы открытым всё подряд, и настоящую дыру никто не заметил бы.
Проверить наверняка можно с сервера:

```bash
ssh skilllink@<адрес> "ss -tlnp | grep -E '3000|5432'"
```

Строки должны начинаться с `127.0.0.1:` — значит, порты доступны только
изнутри машины.

## 5. Если что-то не так

Первым делом — `/api/health`: он называет причину, а не «ошибка».

| Ответ | Что случилось | Что делать |
| --- | --- | --- |
| `database: auth-failed` | Пароль в настройках разошёлся с тем, с которым создана база | Развёртывание чинит это само: приводит пароль базы к `.env.cloud` |
| `database: unreachable` | Контейнер базы не запущен или не отвечает | `docker compose -p skilllink ps`, журнал базы |
| `database: database-missing` | Сервер отвечает, базы с таким именем нет | Проверьте `POSTGRES_DB` |
| `schema: missing` | Миграции не применены | Повторите развёртывание |
| `status: misconfigured` | Не задан `AUTH_SECRET` или `DATABASE_URL` | Проверьте `~/skilllink/.env.cloud` |

Журналы:

```bash
ssh skilllink@<адрес> "cd ~/skilllink/app && docker compose -p skilllink logs --tail 50 app"
ssh skilllink@<адрес> "cd ~/skilllink/app && docker compose -p skilllink logs --tail 50 caddy"
```

**Сертификат не выпускается.** Смотрите журнал Caddy. Обычные причины: запись A
ещё не разошлась по DNS, закрыт порт 80 (он нужен для проверки владения доменом),
домен указывает на другой адрес.

**Не скачиваются образы.** Если провайдер или Docker Hub недоступны, `docker`
останавливается на `pull`. Тогда нужен доступный реестр-зеркало — настраивается
в `/etc/docker/daemon.json`, после чего `systemctl restart docker`.

**Соединение оборвалось посреди сборки** («Connection closed by remote host»).
Работает прежняя версия: новая поднимается только в самом конце. Подождите,
пока на сервере закончится начатая сборка (`ps aux | grep "docker-compose compose"`),
и повторите команду — слои возьмутся из кэша. Отметка `DEPLOYED_COMMIT` пишется
только после того, как стенд поднялся, поэтому обновление по расписанию тоже
повторит попытку, а не сочтёт стенд свежим.

**Кончилось место.** `docker system prune -af` удаляет неиспользуемые образы
и кеш сборки. Тома с данными эта команда не трогает.

### Сроки хранения журнала (docs/PRIVACY.md, решение 88)

Журнал действий хранится год, адрес клиента в нём — 90 дней. Применяет скрипт:

```bash
ssh skilllink@<адрес> 'cd ~/skilllink/app && docker compose -p skilllink -f docker-compose.yml \
  -f deploy/yandex-cloud/compose.cloud.yml --env-file ~/skilllink/.env.cloud \
  --profile migrate run --rm migrate npm run db:retention'
```

Образ `migrate` — тот же, что у перезаливки (`reseed.sh`): в нём есть `scripts/` и `tsx`.

Без флага он только показывает, что удалит и где сотрёт адрес. Применить — добавить
`-- --apply`. **На демо-стенде до защиты не применять:** демо-набор начинается 400 дней
назад, и журнал завершённой связки уйдёт — изменится «Операций на связку».
Расписание (cron владельца сервера) пока не включено.

## 6. Чего в этом развёртывании нет

Сказано честно, чтобы не выглядело промышленным контуром:

- **Резервные копии по расписанию не делаются.** База живёт в томе Docker
  на одной машине. Снимок вручную:

  ```bash
  ssh skilllink@<адрес> "cd ~/skilllink/app && docker compose -p skilllink exec -T postgres \
    pg_dump -U skilllink skilllink" > dump.sql
  ```

  `-T` обязателен: без него `exec` выделяет терминал и портит файл переводами строк.

  Восстановление в новую базу (проверено: 0 ошибок, все таблицы совпали,
  русская сортировка колонок уцелела):

  ```bash
  ssh skilllink@<адрес> "cd ~/skilllink/app && docker compose -p skilllink exec -T postgres \
    psql -U skilllink -d postgres -c 'create database restored'"
  ssh skilllink@<адрес> "cd ~/skilllink/app && docker compose -p skilllink exec -T postgres \
    psql -U skilllink -d restored" < dump.sql
  ```
  **Проверено целиком 23.09.2026.** Дамп со стенда развёрнут в отдельную базу,
  приложение поднято на ней, и по восстановленной копии полностью прошли
  сквозной сценарий (327 проверок) и пробник (161). Все двенадцать колонок
  сохранили правило сравнения `ru-x-icu` — русская сортировка после
  восстановления работает.

  Если пароль демо-пользователей на стенде свой (а он свой), проверки нужно
  запускать с ним:

  ```bash
  APP_BASE_URL=http://localhost:3200 SEED_DEMO_PASSWORD=<пароль> npm run smoke
  ```

  Без этого пять проверок входа падают так, будто сломалась авторизация.

- **Мониторинга и оповещений нет.** Есть только `/api/health` и перезапуск
  контейнера при падении.
- **Машина одна.** Её перезагрузка — простой стенда; контейнеры поднимутся сами.
- **Соответствие 152-ФЗ и приказу ФСТЭК № 117 не заявляется** — см.
  [SECURITY_LIMITATIONS.md](SECURITY_LIMITATIONS.md).

## 7. Что проверено

Развёртывание прогонялось целиком на настоящей Ubuntu 24.04: подготовка сервера,
отправка кода, сборка образа, миграции, демонстрационные данные, Caddy с HTTPS.
Отдельно проверено поведение при сбоях:

- пароль базы намеренно разведён с настройками — развёртывание поймало `P1000`
  и починило само;
- приложение до миграций — поймано, порядок исправлен;
- вход через прокси с HTTPS: сессия в cookie с приставкой `__Secure-`,
  после входа остаёмся на адресе стенда;
- `skilllink` как пароль демо-пользователей на стенде **не подходит**;
- настоящий стенд в Yandex Cloud с доменом `skilllink.site`: сертификат выпущен
  сам, все 12 проверок снаружи пройдены;
- перезагрузка машины — стенд поднимается сам, без вмешательства;
- резервная копия восстанавливается без ошибок, все таблицы совпадают,
  русская сортировка колонок сохраняется.

**Архитектура процессора.** Облачные машины — x86, а проверочная Ubuntu работала
на ARM. Поэтому образ отдельно собран под x86 (`linux/amd64`) и запущен
под эмуляцией: сквозной сценарий — 327 из 327, пробник — 148 из 148.

## Автовыкладка фронта (24.09.2026)

`.github/workflows/deploy-frontend.yml`: после зелёных «Проверок» на `main` стенд
обновляется сам — если с выложенного коммита (`DEPLOYED_COMMIT` на сервере) менялся
только фронт: `src/app/` кроме `src/app/api/`, `src/ui/`, `public/`, `docs/`,
`package.json` и `package-lock.json`. Есть изменения в базе, API, серверной логике,
скриптах или сборке — выкладка пропускается и перечисляет их в итоге запуска: такое
выкладывается вручную после проверки. После выкладки — сверка со сценарием показа
(`demo:check`), при сбое — откат на прежний коммит. Тихие окна (МСК), когда выкладки
нет ни автоматической, ни ручной: генеральный прогон 26.09 14:00–18:00 и защита — с перезаливки
29.09 12:00 до конца дня. Сплошной заморозки нет. Секреты репозитория: `DEPLOY_SSH_KEY` (отдельный ключ,
на сервере помечен `github-actions-frontend-deploy`), `DEPLOY_KNOWN_HOSTS`,
`SEED_DEMO_PASSWORD`. Отозвать доступ — удалить строку ключа из
`~/.ssh/authorized_keys` на сервере.
