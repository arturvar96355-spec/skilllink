# ARCHITECTURE.md — архитектура SkillLink

## Форма системы

Модульный монолит на Next.js 15 (App Router). Клиент и серверная логика — один проект,
один язык, один репозиторий. Серверная часть живёт в маршрутах `app/api/**/route.ts`,
бизнес-логика — в `src/modules`.

Выбор обоснован объёмом MVP: разделение на отдельные сервисы дало бы стоимость эксплуатации
без выигрыша. Модульность сохраняется на уровне каталогов, поэтому вынести модуль в отдельный
сервис позже можно без переписывания бизнес-логики.

## Стек

| Слой | Технология | Почему |
| --- | --- | --- |
| Приложение | Next.js 15.5, React 19, TypeScript strict | целевой стек концепции |
| Валидация | Zod 4 (русская локаль) | одна схема на вход и на типы |
| База | PostgreSQL 16 | целевой стек концепции |
| Доступ к базе | Prisma 7 + `@prisma/adapter-pg` | в Prisma 7 подключение идёт через драйверный адаптер |
| Тесты | Vitest 4 | быстрый прогон правил без поднятия базы |
| Контейнеризация | Docker Compose | Postgres локально и в контуре заказчика |

Запрещены и не используются: Supabase, Vercel, Firebase, любые зарубежные облачные сервисы,
Python в рантайме, ML-модели и LLM в бизнес-логике.

## Каталоги

```
src/
  app/
    api/**/route.ts        тонкие обработчики: разбор запроса → сервис → ответ
    (auth)/, (app)/        страницы: вход и всё внутри общего каркаса (docs/FRONTEND.md)
  ui/                      дизайн-система: примитивы, таблицы, окна, каркас, хуки
  modules/<модуль>/
    <модуль>.schema.ts     Zod: входные данные
    <модуль>.rules.ts      чистые правила предметной области, покрыты тестами
    <модуль>.repo.ts       единственное место, где вызывается Prisma
    <модуль>.service.ts    бизнес-логика и сборка DTO
    <модуль>.test.ts       тесты правил и схем
  shared/
    contracts/             типы DTO для фронта и бэка
    http/                  ok, okList, fail, handle, parseBody, parseQuery, пагинация
    config/                коэффициенты и нормативы (все помечены TEMP)
    auth/                  getCurrentUser, права ролей
    audit/                 журнал критичных действий
    db/                    клиент Prisma, условие поиска по тексту
    utils/                 даты и числа
    openapi/               реестр эндпоинтов и сборка спецификации
    zod.ts                 Zod с русской локалью
  generated/prisma/        сгенерированный клиент Prisma (не в репозитории)
prisma/                    schema.prisma, migrations/, seed.ts
scripts/smoke.ts           сквозной сценарий против запущенного сервера
docs/                      документация
```

## Поток вызова

```
HTTP-запрос
   ↓
app/api/**/route.ts        handle() ловит любые ошибки
   ↓                       parseQuery / parseBody валидируют вход
   ↓                       getCurrentUser() определяет пользователя
modules/*/service.ts       assertCan() проверяет право
   ↓                       rules.ts решает, допустимо ли действие
modules/*/repo.ts          Prisma: единственный слой, знающий про базу
   ↓
PostgreSQL
```

Обратно тем же путём: repo отдаёт строку Prisma, сервис превращает её в DTO из
`shared/contracts`, маршрут заворачивает в `{ data }` или `{ data, meta }`.

Правила:

- маршрут не обращается к Prisma и не содержит бизнес-логики;
- сервис не знает про `Request` и `Response`;
- фронт импортирует типы только из `@/shared/contracts` и **никогда** из `@/generated/prisma`;
- одна и та же логика не повторяется в двух модулях: правила workflow лежат в
  `modules/workflow/workflow.rules.ts` и переиспользуются модулем cooperation.

## Модули

| Модуль | Состояние | Отвечает за |
| --- | --- | --- |
| `universities` | готов | реестр и карточка вуза, контакты, архивирование |
| `programs` | готов | программы, показатели набора, привязка навыков |
| `skills` | готов | справочник навыков, востребованность, skill gap |
| `products` | готов | реестр IT-продуктов |
| `cooperation` | готов | связка «вуз — программа — продукт», создание 14 этапов |
| `workflow` | готов | машина состояний этапов, чек-листы, история, просрочки |
| `analytics` | готов | дашборд, рейтинг программ, приоритетные действия |
| `recommendations` | готов | пять правил генерации, объяснимость, работа сотрудника с предложением |
| `documents` | готов | метаданные, жизненный цикл, история статусов, версионирование |
| `meetings` | готов | встречи, участники, результат и следующее действие |
| `portal` | готов | кабинет представителя вуза, заявки на обучение |
| `data-sources` | готов | состояние интеграций, загрузка рыночных данных |
| `auth` | готов (mock) | текущий пользователь, права, справочник пользователей |
| `ai-assist` | готов, по умолчанию выключен | черновики текста по фактам правил: сводка по связке, письмо вузу, дела на сегодня (решение 90) |
| `telegram` | готов, по умолчанию выключен | личная сводка «что горит у меня» в Telegram: привязка чата, вебхук бота, рассылка (решение 102) |

Каталог `src/integrations` — интерфейсы внешних систем: рыночные данные (Mock, Csv,
ExternalApi, FutureRtk), LMS, сайт, языковая модель ИИ-помощника (YandexGPT, GigaChat)
и Telegram Bot API для личных уведомлений.
Бизнес-логика знает только интерфейсы.

Модуль `ai-assist` решений не принимает: что рекомендовать и в каком порядке, считают
`recommendations` и `workflow`, помощник лишь пересказывает их факты читаемым текстом —
моделью или шаблоном, если модели нет (решение 90).

Модуль `portal` в списке `CLAUDE.md` не значился: он добавлен, потому что логика кабинета
вуза отличается от логики сотрудника (другой состав полей, другие права, другой набор
действий). Держать её внутри `universities` и `programs` означало бы смешать два разных
пользовательских сценария в одних сервисах. Зафиксировано в
[TECHNICAL_DECISIONS.md](TECHNICAL_DECISIONS.md).

## Обработка ошибок

Единственная точка — `handle()` в `shared/http/handle.ts`. Оборачивает каждый маршрут и
превращает в ответ контракта:

| Что произошло | Код ответа |
| --- | --- |
| `AppError`, брошенный сервисом или правилом | свой код и статус |
| `ZodError` | `VALIDATION_ERROR` 422 с разбором по полям |
| Prisma P2002 (уникальность) | `CONFLICT` 409 |
| Prisma P2003 (внешний ключ) | `VALIDATION_ERROR` 422 |
| Prisma P2025 (записи нет) | `NOT_FOUND` 404 |
| Что угодно ещё | `INTERNAL` 500, наружу без подробностей |

Внутренняя ошибка логируется только типом и сообщением: персональные данные в логи не попадают.
Сбой одного модуля не роняет остальные — каждый маршрут изолирован своей обёрткой.

## Объяснимость аналитики

Требование раздела 10 ТЗ: пользователь должен видеть, на основании каких данных получен
показатель. Реализовано типом `Metric` в `shared/contracts/common.ts`: любое число приходит
вместе с `unit`, `basis` (`actual` / `estimate` / `none`), текстовым `explanation`, источником
и признаком `isMock`.

Отсутствие данных — это `value: null` и `basis: "none"`, никогда не ноль.

Формулы и коэффициенты вынесены в `shared/config/analytics.config.ts` и описаны в
[ANALYTICS_METHODOLOGY.md](ANALYTICS_METHODOLOGY.md). Ни одно число не зашито в код модулей.

## Разграничение доступа

Права проверяются в сервисах через `assertCan(user, 'WRITE')`. Для роли `UNIVERSITY_REP`
видимость сужается до своего вуза общим хелпером `universityScope(user)`, который репозитории
подмешивают в `where`, — а не отдельной проверкой в каждом маршруте.

Запрос к записи чужого вуза возвращает `NOT_FOUND`, а не `FORBIDDEN`: существование записи
не раскрывается.

Политики RLS в PostgreSQL (обещаны в концепции) — P2. Ограничение зафиксировано в
[SECURITY_LIMITATIONS.md](SECURITY_LIMITATIONS.md).

## Интеграции

Каталог `src/integrations` по разделу 14 ТЗ:

```
integrations/
  config.ts              все настройки из env, секретов в коде нет
  http-client.ts         таймаут, повторы, ограничение частоты, журналирование
  market-data/           MarketDataProvider: Mock, Csv, ExternalApi, FutureRtk
  lms/                   LmsClient: mock и HTTP-реализация
  site/                  SiteClient: заявки с сайта
  llm/                   LlmProvider: YandexGPT, GigaChat, выключен (AI_ASSIST_PROVIDER)
  telegram/              TelegramClient.sendMessage — Bot API, выключен без TELEGRAM_BOT_TOKEN
  https-transport.ts     POST через node:https: свой сертификат (GigaChat), подключение
                         к запасному IP с прежним именем в TLS (Telegram из Yandex Cloud)
```

Активный источник рыночных данных выбирается переменной `MARKET_DATA_PROVIDER`.
Интеграции с LMS и сайтом по умолчанию выключены; обращение к выключенной интеграции
возвращает `INTEGRATION_ERROR` 502 с понятным текстом, а не роняет систему.

Повторяются только сетевые сбои и временные ошибки сервера (5xx, 408, 429). Тело ответа
внешнего сервиса в журнал не пишется: в нём могут быть персональные данные.

Наличие конкретных внутренних API РТК не утверждается: провайдер `future-rtk` честно
сообщает, что спецификация не предоставлена, и ничего не выдумывает.

## Спецификация OpenAPI

`src/shared/openapi/registry.ts` описывает каждый эндпоинт и ссылается на **те же** Zod-схемы,
которыми маршруты проверяют вход. `build.ts` превращает их в OpenAPI 3.1 через
`z.toJSONSchema`, поэтому описание параметров и тел запросов не может разойтись с кодом.

Полнота реестра проверяется тестом: он обходит `src/app/api`, собирает экспортированные
методы и падает, если появился маршрут без описания — или описание без маршрута.

Схемы ответов описаны обобщённо: DTO заданы типами TypeScript в `shared/contracts`, и выводить
из них JSON Schema означало бы держать вторую систему описаний. Точные поля ответов — в
[API_CONTRACT.md](API_CONTRACT.md).

## Масштабирование

- Рейтинг и skill gap считаются в приложении. При росте объёма переносятся в представления и
  агрегирующие запросы PostgreSQL без изменения контракта API.
- Модуль выносится в отдельный сервис заменой `repo` — сервисы и маршруты не меняются.
- Новый источник рыночных данных добавляется реализацией интерфейса, без правки бизнес-логики.
