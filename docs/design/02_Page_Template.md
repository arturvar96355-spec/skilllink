# SkillLink --- Application Shell и шаблон страниц

## 1. Назначение

Этот документ задаёт **единый шаблон приложения и структуру страниц
SkillLink**.

Главная задача --- чтобы при генерации новых страниц нейросеть не
придумывала новый layout с нуля.

Все страницы должны выглядеть как части одного продукта.

Базовая структура:

**Sidebar → Header → Page Content → Footer**

------------------------------------------------------------------------

# 2. Общий Application Shell

Каждая внутренняя страница SkillLink использует единый shell.

## Desktop

Слева: - Sidebar.

Сверху: - Header.

По центру: - основной контент текущей страницы.

Внизу: - стандартный Footer.

Справа снизу: - Floating Search Button.

------------------------------------------------------------------------

# 3. Sidebar

Sidebar находится слева и является постоянной частью application shell.

В верхней части:

**SkillLink** подзаголовок: **Вузы × IT-компании**

Логотип должен быть единым на всех страницах.

------------------------------------------------------------------------

# 4. Две основные группы Sidebar

Sidebar разделён на две логические группы:

## Рабочее пространство

Содержит основные рабочие разделы продукта:

-   Главная
-   Университеты
-   Программы
-   Рекомендации
-   Сотрудничество

## Инструменты

Содержит дополнительные рабочие инструменты:

-   Аналитика
-   Документы
-   Настройки

Дополнительные пункты могут добавляться только при наличии
соответствующей функциональности/permissions.

------------------------------------------------------------------------

# 5. Поведение групп Sidebar

Пользователь должен видеть две основные категории:

-   Рабочее пространство
-   Инструменты

При наведении на категорию раскрывается связанный набор пунктов.

Важно:

-   раскрытие должно быть плавным;
-   структура не должна прыгать;
-   активный пункт должен оставаться видимым;
-   при переходе на страницу соответствующая категория автоматически
    остаётся раскрытой;
-   состояние раскрытия не должно ломать layout.

На desktop можно использовать hover + возможность закрепить/открыть
группу.

На keyboard navigation раскрытие должно работать через focus.

------------------------------------------------------------------------

# 6. Поведение пунктов Sidebar

Каждый пункт:

-   имеет иконку;
-   имеет текст;
-   является полностью кликабельным;
-   имеет hover;
-   имеет active state.

При hover:

-   текст становится немного ярче;
-   текст визуально немного увеличивается;
-   иконка становится ярче;
-   появляется мягкая подсветка.

Эффект должен быть очень аккуратным, в духе современных спортивных/game
UI интерфейсов.

Не использовать сильный scale.

Active:

-   приглушённая фиолетовая surface;
-   более яркий текст;
-   яркая иконка;
-   тонкая граница;
-   лёгкий glow.

------------------------------------------------------------------------

# 7. Header

Постоянная строка поиска из старых wireframes удаляется.

Вместо неё header содержит:

слева/по центру: **активную кнопку с логотипом SkillLink и названием
текущего application context**

справа: - Notifications; - User Profile.

------------------------------------------------------------------------

# 8. Главная кнопка Header

В верхней центральной/левой части header вместо прежней надписи
«Главная» и строки поиска должна находиться активная кнопка.

Кнопка содержит:

-   логотип SkillLink;
-   название SkillLink;
-   при необходимости короткий текущий контекст.

Главное поведение:

**клик → переход на Главную.**

Эта кнопка является постоянной навигацией домой.

Hover: - мягкая подсветка; - logo glow; - текст становится ярче.

------------------------------------------------------------------------

# 9. Header Notifications

Справа сверху находится Notification Button.

Он всегда активен.

При клике:

→ открывается Notification Feed.

Feed появляется вниз от кнопки.

Повторный клик: → закрывает Feed.

Также Feed закрывается: - Escape; - кликом вне popover.

------------------------------------------------------------------------

# 10. Notification Feed

Каждое уведомление является ссылкой на конкретный объект.

Примеры:

-   уведомление о документе → Documents;
-   уведомление о сотрудничестве → Collaboration;
-   уведомление о рекомендации → Recommendations;
-   уведомление о программе → Program;
-   уведомление об университете → University;
-   уведомление о задаче → соответствующий workflow.

Нельзя отправлять пользователя просто на Dashboard, если существует
более точная целевая страница.

------------------------------------------------------------------------

# 11. User Profile Trigger

Справа сверху:

-   Avatar;
-   Имя;
-   Фамилия;
-   должность/роль, если используется.

Вся область активна.

Клик:

→ **Личный кабинет**

------------------------------------------------------------------------

# 12. Личный кабинет

Личный кабинет должен быть проще, чем остальные страницы.

Не использовать стандартные рабочие tabs из остальных страниц.

Оставить только три основные области:

## 12.1. Личные данные

Показывать:

-   ФИО;
-   должность;
-   отдел;
-   город;
-   email;
-   телефон;
-   другие доступные профильные данные.

## 12.2. Статистика

Показывать:

-   активные сотрудничества;
-   вузов в работе;
-   программ под управлением;
-   этапы в срок;
-   другие релевантные KPI пользователя.

## 12.3. Настройки

Показывать пользовательские настройки.

Например: - уведомления; - предпочтения интерфейса; - параметры
аккаунта; - безопасность, если поддерживается backend.

Не добавлять вкладки без реальной функциональности.

------------------------------------------------------------------------

# 13. Основной Page Container

Все страницы имеют одинаковую структуру основного контента.

Рекомендуемая последовательность:

1.  Breadcrumbs, если нужны.
2.  Page title.
3.  Краткое описание.
4.  Основные действия.
5.  Filters/Search, если нужны.
6.  Main content.
7.  Secondary content.
8.  Footer.

Не каждая страница обязана иметь каждый блок.

------------------------------------------------------------------------

# 14. Page Header

Page Header:

### Breadcrumbs

Используются на вложенных страницах.

Пример:

`Университеты / НИУ ВШЭ`

или:

`Программы / Программная инженерия`

или:

`Сотрудничество / НИУ ВШЭ / Платформа ML`

Breadcrumbs должны быть кликабельными.

Текущий элемент --- ярче остальных и не должен быть ссылкой.

------------------------------------------------------------------------

# 15. Page Title

Заголовок страницы:

-   крупный;
-   яркий;
-   короткий.

Под ним: - description; - при необходимости metadata.

Не делать длинные заголовки в несколько строк без необходимости.

------------------------------------------------------------------------

# 16. Page Actions

Основные действия располагаются рядом с Page Header.

Например:

-   Добавить вуз;
-   Создать программу;
-   Создать сотрудничество;
-   Загрузить документ;
-   Экспортировать.

Главное действие: → Primary Button.

Второстепенные: → Secondary/Ghost Button.

------------------------------------------------------------------------

# 17. Filters

Если страница содержит список:

Page Header ↓ Filters ↓ Content

Filters:

-   статус;
-   регион;
-   рейтинг;
-   уровень;
-   ответственный;
-   другие поля из API.

Каждый filter --- единый Select/Dropdown component.

------------------------------------------------------------------------

# 18. Списковые страницы

Для реестров использовать стандартный шаблон:

**Page Header** ↓ **Actions** ↓ **Filters** ↓ **Table/List** ↓
**Pagination** ↓ **Footer**

Не создавать уникальную структуру таблицы на каждой странице.

------------------------------------------------------------------------

# 19. Таблица

Единый компонент Table.

Каждая строка: - hover; - интерактивна, если ведёт на объект; - имеет
понятную визуальную иерархию.

Для действий: - отдельная action area; - dropdown/ellipsis.

Не перегружать таблицу большим количеством кнопок.

------------------------------------------------------------------------

# 20. Страница списка университетов

Структура:

### Header

**Университеты**

Description: **Реестр вузов, с которыми ведётся работа**

### Actions

Primary: **+ Добавить вуз**

### Filters

-   Статус сотрудничества
-   Регион
-   Рейтинг

### Main

Таблица университетов.

Колонки должны соответствовать доступным API данным.

Минимально:

-   Университет;
-   Статус;
-   Рейтинг;
-   Программы;
-   Связи/сотрудничества;
-   Обновлено;
-   Actions.

### Footer

Стандартный.

------------------------------------------------------------------------

# 21. Страница программы

Структура:

Breadcrumbs ↓ Program Header ↓ Tabs ↓ Main content

Program Header:

-   icon;
-   название;
-   уровень;
-   длительность;
-   университет;
-   рейтинг/score.

Tabs:

-   Обзор;
-   Навыки;
-   Рынок труда;
-   Сотрудничества;
-   Документы.

Tabs использовать только там, где есть соответствующие данные/функции.

------------------------------------------------------------------------

# 22. Страница университета

Структура:

Breadcrumbs ↓ University Header ↓ Tabs ↓ Main Content

Header:

-   logo/icon;
-   название;
-   город;
-   статус;
-   рейтинг;
-   контактное лицо/контакты, если доступны.

Tabs:

-   Обзор;
-   Программы;
-   Сотрудничества;
-   Документы;
-   Встречи;
-   История.

------------------------------------------------------------------------

# 23. Страница рекомендаций

Структура:

Page Header ↓ Filters ↓ Tabs ↓ Recommendation List ↓ Footer

Tabs:

-   Программы;
-   Вузы;
-   Навыки.

Каждая рекомендация должна показывать:

-   название;
-   тип;
-   score/confidence, если есть;
-   краткое объяснение;
-   связанные навыки;
-   источник/основание;
-   действие.

------------------------------------------------------------------------

# 24. Страница сотрудничества

Структура:

Breadcrumbs ↓ Collaboration Header ↓ Workflow Stepper ↓ Tabs ↓ Main
Content

Header:

-   университет;
-   программа;
-   IT-продукт;
-   статус;
-   ответственный;
-   дедлайн.

Workflow Stepper:

1.  Привлечение
2.  Оформление
3.  Внедрение
4.  Эксплуатация
5.  Контроль

Внутри этапов используется информация реального workflow backend.

------------------------------------------------------------------------

# 25. Dashboard

Dashboard является основной страницей.

Структура:

Page Header ↓ KPI ↓ Main Grid ↓ Priority Actions ↓ Footer

Dashboard должен отвечать:

1.  Что происходит?
2.  Где проблема?
3.  Что мне делать?
4.  Почему система это рекомендует?

Использовать реальные API данные.

------------------------------------------------------------------------

# 26. Footer

Внизу каждой стандартной страницы должен находиться единый Footer.

Footer должен ощущаться как часть официального продукта/сайта, а не как
случайный текст внизу страницы.

Рекомендуемые группы:

## Компания

-   О компании;
-   О продукте;
-   Контакты;
-   Партнёры.

## Продукт

-   Возможности;
-   Документация;
-   Обновления;
-   Помощь.

## Ресурсы

-   Файлы;
-   Документы;
-   Материалы;
-   FAQ.

## Контакты

-   Email;
-   телефон;
-   адрес;
-   другие официальные каналы, если доступны.

## Legal

-   Политика конфиденциальности;
-   Пользовательское соглашение;
-   Обработка данных.

Не придумывать реальные юридические данные. Использовать только
предоставленные проектом данные.

------------------------------------------------------------------------

# 27. Floating Search

На всех основных страницах:

справа снизу находится единая Floating Search Button.

Она не является частью конкретной страницы.

Она является частью Application Shell.

При клике:

→ открывается перемещаемое Spotlight-подобное окно глобального поиска.

Поведение и внешний вид определяются документом:

**Design System: Интерфейс и интерактивные элементы**

Не переопределять стиль поиска на отдельных страницах.

------------------------------------------------------------------------

# 28. Responsive Shell

На desktop:

Sidebar постоянно виден.

На tablet:

Sidebar может быть свёрнут.

На узком экране:

-   Sidebar превращается в compact/drawer navigation;
-   Header остаётся доступным;
-   Search Button остаётся доступной;
-   notification feed корректирует позицию;
-   контент не выходит за viewport.

------------------------------------------------------------------------

# 29. Loading / Empty / Error

Каждая страница обязана иметь три стандартных состояния:

### Loading

Skeleton соответствующего layout.

Не показывать пустой экран.

### Empty

Показывать:

-   объяснение;
-   почему данных нет;
-   CTA, если действие возможно.

### Error

Показывать:

-   понятное описание;
-   Retry;
-   дополнительную информацию, если это полезно.

------------------------------------------------------------------------

# 30. Mock Data

Если backend сообщает mock/demo data:

показывать аккуратный badge:

**Демонстрационные данные**

Не выдавать demo data за реальные данные.

------------------------------------------------------------------------

# 31. Null Data

`null` означает:

**Нет данных**

Никогда автоматически не преобразовывать `null` в:

**0**

Это правило действует для: - KPI; - таблиц; - рейтингов; - графиков; -
статистики.

------------------------------------------------------------------------

# 32. Permissions

Шаблон страницы должен учитывать role-based UI.

Если у пользователя нет permission:

-   элемент не должен отображаться, если действие полностью недоступно;
-   либо отображаться disabled с понятным объяснением, если это важно
    для понимания продукта.

Не показывать пользователю внутренние данные другой роли.

------------------------------------------------------------------------

# 33. Consistency Rule

Новая страница должна строиться из существующих:

-   Application Shell;
-   Header;
-   Sidebar;
-   Page Header;
-   Breadcrumbs;
-   Tabs;
-   Buttons;
-   Cards;
-   Table;
-   Filters;
-   Modal;
-   Drawer;
-   Footer;
-   Floating Search.

Перед созданием нового компонента проверить, можно ли переиспользовать
существующий.

------------------------------------------------------------------------

# 34. Правило для AI-разработчика

**Не придумывай новый layout, если уже существует подходящий шаблон.**

Новая страница должна быть:

> новым содержимым внутри существующей системы,

а не:

> новым дизайном внутри того же проекта.

Цель:

**один SkillLink → один application shell → одна design system → единые
паттерны → разные данные и сценарии.**
