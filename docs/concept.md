Подходы команды к решению задачи

Единицей учёта в системе принимается связка «вуз - образовательная программа - ИТ-продукт». Один университет ведёт несколько потоков обучения одновременно, и находятся они на разных стадиях, поэтому статус закрепляется за связкой, а не за вузом. Иначе состояние работы с университетом невозможно описать корректно.

Этапы процесса собраны в управляемый конвейер из четырёх фаз: привлечение, оформление, внедрение, эксплуатация. Контроль исполнения вынесен отдельным слоем поверх всех фаз.

Трудозатраты сокращаются за счёт четырёх механик. Чек-листы этапа не дают перейти дальше, пока не закрыты обязательные пункты. Нормативные сроки с эскалацией при просрочке. Документы собираются из шаблонов с автоподстановкой реквизитов. Групповые операции по ИТ-продукту: одно действие ставит задачи во всех связках, где передана устаревшая версия.

Ранжирование образовательных программ ведётся по трём показателям из технического задания: заявки на обучение, количество обучающихся, количество параллельных потоков. Показатели нормируются и сводятся в общий рейтинг с настраиваемыми весами. В карточке программы видно вклад каждого показателя, поэтому сотрудник может проверить основание рекомендации.

Данные для рейтинга система получает изнутри процесса. Заявки приходят через интеграцию с сайтом либо вносятся вручную, численность обучающихся и число потоков фиксируются при запуске занятий. Внешних источников не требуется. Для вузов, с которыми сотрудничество ещё не начато, фактических данных нет, поэтому рейтинг рассчитывается по потенциалу: численности профильных направлений из справочника.

Аналитика востребованных навыков вынесена отдельным слоем и в формулу рейтинга не входит. Она сопоставляет спрос рынка труда с содержанием программ и показывает, каких навыков в программах не хватает. Вместе два инструмента отвечают на два разных вопроса: где набирать людей и чем дополнить обучение.

В системе работают три роли. Сотрудник ИТ-Школы ведёт свои связки, проходит этапы, работает с документами и получает рекомендации по программам. Руководитель направления видит всю картину: просрочки, нагрузку на сотрудников, настраивает веса показателей. Представитель вуза работает в ограниченном кабинете: видит статус сотрудничества по своему университету и список переданных материалов, подтверждает получение, указывает количество потоков и численность обучающихся, подаёт заявки на обучение. Участие вуза снимает часть переписки с сотрудника и даёт показатели рейтинга напрямую от источника. Доступ разграничивается политиками на уровне строк: вуз видит только свои записи.

Уникальность идеи

Альтернатива нашему решению - настроить универсальную CRM. Она закроет начальные этапы, где идёт поиск контакта и первые переговоры, и не закроет основную часть процесса, которая начинается после подписания документов.

Коробочная CRM устроена вокруг сделки с одним контрагентом и линейной воронки. Здесь другое: сотрудничество длится годами, а по одному вузу параллельно идёт несколько независимых связок с разными статусами и разным числом потоков. Актуализация учебной программы представляет собой вложенный процесс со своими вехами, а не стадию воронки. Сроки лицензии и сроки актуальности обучения преподавателей должны сами порождать задачи. В коробочной конфигурации это не настраивается.

Главное отличие в аналитике. CRM работает с заявками, которые уже пришли. Наша система решает обратную задачу: к кому идти и с какой программой. Это происходит до того, как появится хоть одна заявка.

Работает в системе сотрудник ИТ-Школы, то есть сторона вендора. Продукты для автоматизации самих вузов обслуживают другого пользователя и другие задачи, поэтому прямое сравнение с ними некорректно.

Описание планируемого результата

Рабочий прототип веб-системы на подготовленном наборе данных.

Ядро, которое демонстрируется: рейтинг программ по трём показателям с раскрытием вклада каждого, сопоставление программ с востребованными навыками рынка, работа со связкой по всем этапам процесса с чек-листами и контролем просрочек, сводный дашборд цикла взаимодействия.

Также реализовано: реестр вузов, программ и ИТ-продуктов, кабинет представителя вуза, генерация пакета документов из шаблонов с версионированием правок, групповые операции по ИТ-продукту, ролевое разграничение доступа, журнал действий пользователей.

Эффект измеряется тремя величинами, которые система считает сама и выводит на дашборд: количество ручных операций на одну связку, доля этапов, закрытых в норматив, время от первого контакта до начала занятий.

Ограничения прототипа. Аналитика работает на заранее подготовленном наборе данных о вакансиях, автоматический сбор не реализован. К информационным системам заказчика подключения нет, интеграция описана спецификацией. Электронной подписи нет, фиксируются факт и дата подписания. Данные об успеваемости обучающихся не используются, поскольку заказчиком не предоставляются.

Направления развития: интеграция с LMS и сайтом по REST API, подключение данных об успеваемости, электронная подпись документов, регулярное обновление рыночного набора данных.

Используемые технологии

Приложение реализуется одним проектом на Next.js и TypeScript. Интерфейс: React, компоненты shadcn/ui, стили Tailwind CSS. Серверная логика размещается в маршрутах API того же приложения, поэтому весь код ведётся на одном языке и в одном репозитории.

Хранение данных: PostgreSQL. Аналитические показатели рассчитываются представлениями и агрегирующими запросами на стороне СУБД. Разграничение доступа реализовано политиками на уровне строк, аутентификация и сессии через NextAuth.js на токенах JWT.

Визуализация: Recharts. Интеграционные интерфейсы описаны по спецификации OpenAPI. Контроль версий: Git. Контейнеризация: Docker.

Развёртывание предусмотрено в Yandex Cloud. Платформа размещает данные на территории Российской Федерации и аттестована по требованиям к защите персональных данных, что обеспечивает соответствие Федеральному закону № 152-ФЗ и применимость требований приказа ФСТЭК России № 117 при промышленной эксплуатации. Все компоненты стека распространяются по открытым лицензиям и устанавливаются в контуре заказчика, зарубежные облачные сервисы не используются.

Персональных данных обрабатывается минимум: фамилия, имя, отчество, должность и рабочие контакты. Факт и дата согласия субъекта фиксируются. Действия пользователей журналируются без возможности изменения записей, интеграционные интерфейсы защищены токенами доступа с ограничением частоты запросов и проверкой схемы.
