# Установка, запуск и проверка — подробно

Краткая версия — в [README](../README.md). Здесь всё, что нужно, чтобы поднять SkillLink
локально или в контейнере, прогнать проверки и подключить интеграции.

## Требования

- **Node.js `^20.19` или `^22.12` или `24+`** — проверено на 26.8.1
- PostgreSQL 16 — локально или в Docker
- npm 10 и новее

Диапазон непривычный, и это не придирка: Prisma 7 **не работает** на 20.0–20.18,
на всей ветке 21 и на 22.0–22.11. Это дыры между поддерживаемыми ветками,
а не «слишком старый Node».

Требование записано в `package.json`, и `engine-strict` в `.npmrc` останавливает
установку сразу с понятным сообщением. Без этого ошибка всплыла бы при первом
запросе к базе и выглядела бы как поломка проекта.

Проверить свою версию: `node -v`.

### Windows: три вещи, о которых надо знать заранее

Команды в этом файле написаны для macOS и Linux. На Windows три отличия,
и каждое проявляется непонятной ошибкой, если о нём не знать.

**1. `curl` в PowerShell — это не curl.** Там это псевдоним `Invoke-WebRequest`
с другим синтаксисом: примеры вида `curl -s -X POST …` выдадут ошибку про
несуществующий параметр. Пишите `curl.exe` — настоящий curl в Windows 10 и 11 есть:

```powershell
curl.exe -s http://localhost:3000/api/health
```

**2. Переменная перед командой не работает** — ни в `cmd`, ни в PowerShell:

```powershell
# PowerShell: задать отдельно, живёт до закрытия окна
$env:POSTGRES_PORT = "5433"
docker compose up -d postgres
```

```cmd
:: cmd
set POSTGRES_PORT=5433
docker compose up -d postgres
```

**3. `openssl` в Windows обычно нет.** Секрет для продакшена генерируется
средствами Node — они есть везде, где есть сам проект:

```bash
node -e "console.log(require('crypto').randomBytes(32).toString('base64'))"
```

Эта команда одинаково работает на всех системах, и ею лучше пользоваться везде.

Всё остальное — `npm install`, `npm run dev`, миграции, демо-данные — работает
одинаково. Концы строк нормализуются автоматически, права на файлы не нужны,
длинных путей в проекте нет.

## Установка

```bash
npm install
```

Установка сама генерирует клиент Prisma (`postinstall`), поэтому отдельного шага не нужно.

Если npm пожаловался на заблокированные установочные скрипты (сообщение `install-scripts`) —
разрешения хранятся в `package.json` и приходят вместе с репозиторием, но на всякий случай:

```bash
npm install-scripts approve @prisma/engines prisma @prisma/client
```

## База данных

### Вариант 1: Docker

```bash
docker compose up -d postgres
```

Поднимет `postgres:16-alpine` с базой, пользователем и паролем `skilllink`.

Если 5432 уже занят локальным PostgreSQL, задайте другой порт:
`POSTGRES_PORT=5433 docker compose up -d postgres`.

### Вариант 2: локальный PostgreSQL

```bash
createuser skilllink --createdb --pwprompt
createdb skilllink --owner skilllink
```

Право `CREATEDB` нужно `prisma migrate` для теневой базы. В промышленном контуре миграции
применяются командой `npm run db:deploy`, и это право не требуется.

### Переменные окружения

```bash
cp .env.example .env
```

Минимально достаточно `DATABASE_URL`:

```
DATABASE_URL="postgresql://skilllink:skilllink@localhost:5432/skilllink?schema=public"
```

Для продакшена дополнительно обязателен `AUTH_SECRET`. Генерировать лучше через Node —
работает на всех системах, в отличие от `openssl`, которого в Windows обычно нет:
`node -e "console.log(require('crypto').randomBytes(32).toString('base64'))"`
и `DEMO_AUTH_ENABLED="false"`.

### Миграции и демонстрационные данные

```bash
npm run db:deploy     # применить миграции
npm run db:seed       # загрузить демонстрационные данные
```

> **`db:deploy`, а не `db:migrate`.** Вторая команда создаёт временную базу
> для сравнения схем и потому требует у пользователя право создавать базы
> (`CREATEDB`). У роли, заведённой вручную, его обычно нет, и команда падает
> с `P3014` — ошибкой, по которой непонятно, что делать.
>
> `db:deploy` просто применяет готовые миграции: прав не требует и делает ровно
> то, что нужно всем, кроме того, кто меняет схему.


`db:seed` полностью очищает таблицы перед загрузкой. Все загружаемые записи помечены
`isMock: true` и **не являются подтверждённой статистикой**.

## Запуск

```bash
npm run dev
```

Приложение — `http://localhost:3000`, проверка живости — `http://localhost:3000/api/health`.

По адресу `/` — интерфейс: вход, дашборд, реестры вузов, программ и связок, карточка
связки с четырнадцатью этапами, рекомендации, аналитика, документы, личный кабинет
и кабинет представителя вуза. Войти можно демо-пользователями из `npm run db:seed`
(см. «Вход в систему» ниже).

### Пробник

```bash
npm run probe
```

Сквозной сценарий проверяет, что система делает то, что должна. Пробник — что она
**не делает** того, чего не должна: не пускает представителя вуза к чужим данным,
не оставляет противоречивых состояний, не падает на кривом вводе, переживает двойной клик.

### Сквозной сценарий

В одном окне:

```bash
npm run dev
```

В другом:

```bash
npm run smoke
```

**Против другого сервера** — контейнера, стенда, промышленной сборки на своём порту —
задайте `APP_BASE_URL`:

```bash
APP_BASE_URL=http://localhost:3100 npm run smoke
APP_BASE_URL=http://localhost:3100 npm run probe
```

Переменная одна на оба скрипта. Каждый печатает адрес, против которого работает,
первой строкой — сверяйтесь с ней: опечатка в имени переменной молча вернёт
проверку на `localhost:3000`, и вы получите зелёный результат не от того сервера.

Проверки по разделам 17 и 18 ТЗ: подключение к базе, дашборд, реестр вузов, создание вуза
и программы, привязка навыков, продукты, создание связки с 14 этапами, работа с чек-листом,
допустимые и недопустимые переходы статусов, прогресс и история, просроченные и заблокированные
этапы, востребованность навыков, дефициты, рейтинг программ, фильтры, рекомендации, документы,
встречи, кабинет представителя вуза, интеграции, журнал действий, лента событий,
групповые операции по продукту, сборку пакета документов из шаблонов, вход по паролю, спецификацию OpenAPI, выгрузку и загрузку реестров.

Сценарий переключает пользователя через cookie и отдельно проверяет, что представитель вуза
не видит чужие вузы, аналитику и внутренние комментарии к этапам.

### Скорость на объёме

Утверждения о скорости можно проверить, а не принимать на слово. Наполнение работает
только с базой, в имени которой есть `volume` — чтобы случайный запуск не стёр рабочие
данные.

```bash
createdb skilllink_volume
DATABASE_URL="postgresql://skilllink:skilllink@localhost:5432/skilllink_volume" npm run db:deploy
DATABASE_URL="postgresql://skilllink:skilllink@localhost:5432/skilllink_volume" npm run db:seed
DATABASE_URL="postgresql://skilllink:skilllink@localhost:5432/skilllink_volume" \
  VOLUME_UNIVERSITIES=1000 npm run volume
```

Затем поднять сервер на этой базе и в другом окне выполнить `npm run bench`.

На 1 000 вузов, 6 000 программ и 42 000 этапов самая медленная страница отвечает
за 35 мс. Медиана из семи прогонов, первый отбрасывается как прогревочный.

### Если что-то не работает

`/api/health` отвечает на четыре состояния, и у каждого своя подсказка:

| `status` | Что случилось | Что делать |
| --- | --- | --- |
| `ok` | всё работает | — |
| `misconfigured` | не задана `DATABASE_URL` | `cp .env.example .env` |
| `degraded`, `database: unreachable` | база не отвечает | запустить PostgreSQL |
| `degraded`, `schema: missing` | миграции не применены | `npm run db:deploy` |

Подсказка приходит в поле `hint` прямо в ответе — искать причину в логах не нужно.

### Если порт 3000 занят

Next возьмёт следующий свободный и напишет об этом при запуске — но проверки
об этом не узнают: `npm run smoke` и `npm run probe` по умолчанию стучатся
на 3000 и будут работать не с тем сервером.

Поэтому порт лучше задавать явно и говорить проверкам тот же:

```bash
PORT=3001 npm run dev
APP_BASE_URL=http://localhost:3001 npm run smoke
```

Каждый скрипт печатает адрес сервера первой строкой — сверяйтесь с ней.

## Демонстрационный сценарий

Раздел 18 ТЗ, целиком воспроизводится сквозным сценарием:

1. Открыть дашборд — `GET /api/analytics/overview`.
2. Перейти в реестр вузов — `GET /api/universities`.
3. Открыть карточку вуза — `GET /api/universities/:id`.
4. Перейти к программе — `GET /api/programs/:id`.
5. Посмотреть навыки, востребованность и дефициты — `GET /api/skills/demand`,
   `GET /api/skills/gaps?programId=:id`.
6. Открыть рейтинг программ — `GET /api/analytics/programs`.
7. Создать связку — `POST /api/cooperations`. Сразу появляются все 14 этапов.
8. Посмотреть текущий этап и чек-лист — `GET /api/cooperations/:id`.
9. Закрыть пункты чек-листа — `PATCH /api/workflow/tasks/:id`.
10. Завершить этап — `PATCH /api/workflow/stages/:id` со статусом `COMPLETED` и результатом.
11. Убедиться, что прогресс и история обновились — `GET /api/cooperations/:id`,
    `GET /api/workflow/stages/:id/history`.
12. Посмотреть проблемные связи — `GET /api/workflow/overdue`, `GET /api/workflow/blocked`.
13. Собрать рекомендации — `POST /api/recommendations/generate`, посмотреть их с основаниями —
    `GET /api/recommendations`.
14. Открыть кабинет представителя вуза — `GET /api/portal/overview` под его учётной записью.
15. Посмотреть ленту событий вуза — `GET /api/universities/:id/events`.
16. Выпустить новую версию продукта — `GET`, затем `POST /api/products/:id/release`:
    одно действие ставит задачи во всех связках и переоткрывает закрытые этапы.
17. Собрать пакет документов — `POST /api/cooperations/:id/documents/generate`:
    реквизиты подставляются автоматически, недостающие видны прочерком.

### Вход в систему

Аутентификация — NextAuth.js с сессиями на JWT, пароли хранятся хешами bcrypt.
Фронт входит через `signIn('credentials', { email, password })` из `next-auth/react`.

Демо-пользователи и общий пароль выводит `npm run db:seed`:

| Роль | Почта | Пароль |
| --- | --- | --- |
| ADMIN | `admin@skilllink.demo` | `skilllink` |
| MANAGER | `manager@skilllink.demo` | `skilllink` |
| ANALYST | `analyst@skilllink.demo` | `skilllink` |
| VIEWER | `viewer@skilllink.demo` | `skilllink` |
| UNIVERSITY_REP | `rep@spbgu.example.invalid` | `skilllink` |

Текущая роль и её права — `GET /api/me`. Справочник пользователей — `GET /api/users`.

### Быстрое переключение ролей в демо

Пока включён `DEMO_AUTH_ENABLED` (по умолчанию везде, кроме продакшена), пользователя
можно переключать без пароля — cookie `skilllink_user` с идентификатором:

```bash
curl -s http://localhost:3000/api/universities \
  -H "cookie: skilllink_user=ИДЕНТИФИКАТОР"
```

Настоящая сессия всегда важнее этой cookie. Под представителем вуза (`UNIVERSITY_REP`)
видно, что кабинет показывает только свой вуз, а аналитика и рекомендации закрыты.

**В промышленном контуре обязательно `DEMO_AUTH_ENABLED=false`** — иначе вход без пароля
остаётся открытым.

## Развёртывание в контейнере

Приложение собирается в образ и поднимается вместе с базой:

```bash
export DOCKER_AUTH_SECRET="$(node -e 'console.log(require("crypto").randomBytes(32).toString("base64"))')"

docker compose up -d postgres                       # база
docker compose --profile migrate run --rm migrate   # миграции
docker compose --profile app up -d app              # приложение
```

Приложение — на `http://localhost:3000` (порт меняется через `APP_PORT`).

Что важно знать:

- **Сборка не требует ни базы, ни секретов** — они нужны только на запуске.
  Поэтому образ собирается в CI без доступа к боевому контуру.
- **Миграции — отдельная задача.** Она собирается из сборочной ступени: в рантайм-образе
  лежит только standalone-сервер, CLI Prisma там намеренно нет.
- **`DEMO_AUTH_ENABLED` в контейнере выключен по умолчанию** — и это обеспечено
  не обещанием, а разными именами переменных. Compose подставляет значения
  из `.env` проекта, где после `cp .env.example .env` лежит `DEMO_AUTH_ENABLED=true`;
  если бы имя совпадало, вход без пароля утёк бы в контейнер молча.
  Поэтому контейнер читает `DOCKER_DEMO_AUTH_ENABLED` и `DOCKER_AUTH_SECRET` —
  включить демо-режим можно только осознанно.
- **Секрет подписи обязателен** — `DOCKER_AUTH_SECRET`, не `AUTH_SECRET`: по той же
  причине, что и с демо-режимом. Без него `/api/health` отвечает `misconfigured`,
  а не работает тихо с известным всем ключом.
- **За прокси с HTTPS нужен `DOCKER_AUTH_URL`** — публичный адрес сайта, например
  `https://skilllink.example`. Без него после входа пользователя отправит
  на `https://localhost:3000`: Next.js собирает адрес запроса из собственного имени,
  а не из заголовка `Host`, и NextAuth строит по нему переходы. Локально не нужен.
- **Проверка живости видит неприменённые миграции:** `/api/health` отдаёт 503 и `schema:
  "missing"`, пока база пуста. Оркестратор не поднимет трафик на неработоспособный контейнер.

Образ проверен: собирается, запускается, сквозной сценарий и пробник против контейнера
проходят полностью.

### На сервере — одной командой

```bash
SEED=1 scripts/deploy/deploy.sh skilllink@<адрес> <домен>
```

Поднимает базу, приложение и Caddy с автоматическим HTTPS на любой Ubuntu
с доступом по SSH. Что покупать, как проверить результат и что делать, если
что-то не так, — [docs/DEPLOY.md](DEPLOY.md). Развёртывание прогонялось
целиком на настоящей Ubuntu 24.04, включая поведение при сбоях.

Перед показом демо-данные перезаливаются без пересборки приложения —
`scripts/deploy/reseed.sh`: даты набора отсчитываются от заливки, и через двое
суток числа на экране расходятся со сценарием ([docs/DEPLOY.md](DEPLOY.md)).

## Спецификация OpenAPI

```bash
npm run openapi
```

Спецификация собирается из тех же Zod-схем, которыми API проверяет входные данные,
поэтому параметры и тела запросов не расходятся с кодом. Живой сервер отдаёт её по адресу
`GET /api/openapi.json` — на него можно направить генератор клиента или Swagger UI.

Полнота проверяется тестом: если в приложении появится маршрут, которого нет в
`src/shared/openapi/registry.ts`, тест упадёт. Поля ответов подробно описаны
в [docs/API_CONTRACT.md](API_CONTRACT.md).

| `MARKET_DATA_API_URL`, `MARKET_DATA_API_TOKEN` | для провайдера `external-api` |

| `SITE_ENABLED`, `SITE_API_URL`, `SITE_API_TOKEN` | заявки с сайта |
| `INTEGRATION_TIMEOUT_MS`, `INTEGRATION_RETRIES` | таймаут и число повторов |
| `AI_ASSIST_PROVIDER` | ИИ-помощник: `off` (по умолчанию), `yandexgpt`, `gigachat` — решение 90, подключение в [docs/DEPLOY.md](DEPLOY.md) |
| `YANDEX_GPT_API_KEY`, `YANDEX_FOLDER_ID`, `YANDEX_GPT_MODEL` | YandexGPT |
| `GIGACHAT_AUTH_KEY`, `GIGACHAT_SCOPE`, `GIGACHAT_MODEL`, `GIGACHAT_CA_CERT_PATH` | GigaChat, запасной |
| `AI_ASSIST_TIMEOUT_MS` | таймаут модели; не уложилась — шаблон |

Загрузка рыночных данных активным источником:

```bash
curl -s -X POST http://localhost:3000/api/data-sources/sync -H 'content-type: application/json' -d '{"period":"2026-Q1"}'
```

Навыки, которых нет в справочнике, не создаются автоматически — они возвращаются списком
в `unknownSkills`. Сбой внешнего источника отдаёт `INTEGRATION_ERROR` 502 и не затрагивает
остальную систему.

Наличие конкретных внутренних API заказчика не утверждается: провайдер `future-rtk` честно
сообщает, что спецификация не предоставлена.
