# Эксплуатационные испытания (решение 118)

Что сделано с работающим стендом намеренно — остановлено, убито, перегружено, — и что
из этого вышло, с цифрами. Всё прогнано **на своей машине**, не на сервере и не против
`skilllink.site`: на стенде идёт экспертиза, и эксперт в этот момент увидел бы
неработающую систему.

Скрипты: `scripts/ops/` (как включить на сервере — docs/DEPLOY.md, раздел 10).

## 2. Хаос-сценарии

`scripts/ops/chaos.sh --i-know all`, три прогона подряд на копии стенда. Время — от
действия до первого ответа 200; опрос 5 раз в секунду.

| Сценарий | Прогон 1 | Прогон 2 | Прогон 3 |
| --- | --- | --- | --- |
| **a.** `kill -9` процесса приложения → `/api/health` 200 | 0,78 с | 2,80 с | 3,06 с |
| то же → `/api/ready` через Caddy 200 | 0,92 с | 3,27 с | 3,90 с |
| **b.** `docker stop` базы → `/api/ready` 503 | 0,13 с | 0,32 с | 0,53 с |
| во время простоя базы: `/api/health` / `/login` через Caddy | 200 / 200 | 200 / 200 | 200 / 200 |
| `docker start` базы → `/api/ready` 200 | 0,37 с | 1,03 с | 0,92 с |
| приложение при этом не перезапускалось | да | да | да |
| **c.** `docker restart` Caddy → `/api/ready` через Caddy 200 | 0,23 с | 0,66 с | 0,89 с |
| **d.** `docker stop` приложения: вышло само, код | 0,12 с, 0 | 0,22 с, 0 | 0,24 с, 0 |
| `docker start` → `/api/ready` через Caddy 200 | 0,84 с | 2,40 с | 2,42 с |

Что из этого следует:

- **Падение процесса** Docker поднимает сам (`restart: unless-stopped`), за 1–4 с.
  Во втором и третьем прогоне дольше: Docker увеличивает паузу перед перезапуском,
  когда контейнер падает вскоре после старта, — при «падении по кругу» пауза растёт
  до минуты. Сторож сообщает о каждом перезапуске («контейнер перезапускался»).
- **Как убивали.** Не `docker kill` и не `docker exec <app> kill -9 1`. Оба проверены
  на отдельном контейнере: после `docker kill` контейнер остаётся остановленным
  (Docker считает это ручной остановкой, политика перезапуска не срабатывает); `kill -9 1`
  изнутри ядро игнорирует — процесс 1 своего пространства PID получает только сигналы
  с обработчиком, а SIGKILL обработать нельзя. Настоящее падение (нехватка памяти,
  ошибка рантайма) — смерть процесса снаружи: одноразовый контейнер с `--pid=host`
  шлёт SIGKILL процессу по его PID на машине. Перезапусков после этого — +1.
- **Падение базы не роняет приложение.** Живость остаётся 200 (healthcheck контейнера
  не срабатывает), готовность — 503 с `reason: database-unavailable`, страница входа
  открывается. После возвращения базы пул соединений восстанавливается сам,
  без перезапуска приложения, меньше чем за секунду. В журнале приложения —
  строки «Проверка готовности: база не ответила», необработанных ошибок нет.
- **Caddy** перезапускается быстрее секунды, сертификаты в томе переживают перезапуск.
- **Штатная остановка** — Next ловит SIGTERM, дожидается начатых запросов и выходит сам
  с кодом 0 за 0,1–0,25 с, до предела `stop_grace_period: 30s` далеко.

### Узкое место

**Один процесс Node упирается в процессор; база отдыхает.** Во время прогонов:

- `next start`: процесс Next — 100–140% CPU (одно ядро главного потока плюс служебные
  потоки), PostgreSQL — все 10 соединений пула большей частью `idle`;
- в Docker: приложение — 110–140% при пределе 150%, база — 0–13%, Caddy — 6–11%.

Рост одновременности с 10 до 50 почти не добавляет пропускной способности — только
времени ответа: запросы стоят в очереди к одному потоку JavaScript. Что этот поток делает:
отрисовка страниц на каждый запрос (с решения 112 у страницы свой nonce CSP, заранее
собранной её отдать нельзя — поэтому `/login` не дешевле главной), сборка запросов Prisma 7
в JavaScript (у Prisma 7 с драйверным адаптером нет отдельного движка), JSON-сериализация.

Чего хватает с запасом: демо-стенд с экспертами — единицы одновременных пользователей,
а один пользователь — несколько запросов в секунду. При C=10 копия стенда держит
220–440 запросов/с при p95 до ~100 мс.

Что делать, если понадобится больше: несколько процессов приложения за Caddy
(`reverse_proxy` с несколькими адресами; ограничитель перебора пароля и защита от
повторов оповещений тогда должны переехать из памяти процесса в общее хранилище —
SECURITY_LIMITATIONS, раздел 2), более быстрые ядра машины. База — не первое, во что
упрётся.

Память: у `next start` без Docker — до 600 МБ под нагрузкой; в Docker (standalone)
приложение держалось в 180–215 МБ из предела 1 ГБ.

### Ограничение частоты запросов

В этой ветке общего ограничения частоты запросов нет — его делает отдельная задача
(решение 117). Когда оно появится, для нагрузочного прогона его предел нужно поднять
через переменные окружения этой сборки — иначе в итоге будут 429, и тест измерит
ограничитель, а не приложение. Ограничение перебора пароля тесту не мешает: он входит
один раз.

Против стенда `skilllink.site` тест не запускается: скрипт отказывает на любой адрес,
кроме localhost.

## 6. 50 пользователей и 10 отчётов буквально по ТЗ (решение 146)

Раздел 5 показывает RPS на фиксированное число запросов (220–440 запросов/с) — это не тот
же сценарий, что в ТЗ буквально: «50 параллельных пользователей» и «10 параллельных
отчётов» одновременно, в течение нескольких минут, а не короткий всплеск однотипных
запросов. Здесь — отдельный прогон именно этого сценария.

**Команда:**

```bash
DEMO_AUTH_ENABLED=true npm run build
PORT=3174 DEMO_AUTH_ENABLED=true npm run start &
node scripts/ops/loadtest.mjs --base http://localhost:3174 --scenario tz \
  --vusers 50 --reportWorkers 10 --duration 240 --json /tmp/loadtest-tz.json
```

**Своя база, не стенд.** `createdb skilllink_tzwf`, `DATABASE_URL` в `.env` рабочей копии
на неё, `prisma migrate deploy && npm run db:seed`. Порт 3174, не 3174/3154 других веток —
не пересекается с параллельными агентами на той же машине. Против `skilllink.site`
не запускалось и не может: скрипт отказывает на любой адрес, кроме localhost.

**50 пользователей — сценарий.** Каждый логинится один раз (не входит в замер) под одной
из демо-учёток `admin@`, `manager@`, `manager2@`, `analyst@`, `viewer@`, `head@skilllink.demo`
(роли распределены по кругу; 50 сессий — 50 независимых входов, даже когда несколько
пользователей делят одну и ту же учётную запись, у каждого свой токен). Дальше — цикл
«главная (`/`) → реестр вузов (`/universities`) → карточка вуза (`/universities/:id`) →
карточка связки (`/cooperations/:id`) → рекомендации (`/recommendations`)» с паузами
1–3 с между шагами, до конца окна прогона. Это HTML-страницы (полный серверный рендер
на каждый запрос), а не JSON API — ближе к тому, что делает браузер реального человека.

**10 отчётов — что взято тяжёлым.** Готового PDF или отдельного «отчёта руководителю» в
системе нет (известное расхождение с ТЗ, п. 8 приоритета — не в этой задаче). Взята самая
тяжёлая из существующих выгрузок: `GET /api/export?dataset=cooperations&limit=5000` —
CSV по всем связкам (наименование вуза, направление, продукт, статус, ответственный —
раздел 7 приоритета сверялся отдельно). 10 воркеров формируют её подряд без паузы —
в любой момент внутри окна одновременно выполняется 10 таких запросов.

**Ограничение частоты (решение 117).** Прогон — с `DEMO_AUTH_ENABLED=true` (значение
`.env` по умолчанию для локальной сборки): ограничитель считает запросы и пишет заголовки
`RateLimit-*`, но не отклоняет их (`rate-limit-guard.ts`, `enforce = !isDemoAuthEnabled()`,
раздел 1 SECURITY_LIMITATIONS.md — «В демо-режиме общий счёт только считает»). Никакой
особый «тестовый ключ» не понадобился: этот режим уже есть и предназначен ровно для таких
прогонов. На стенде экспертов `DEMO_AUTH_ENABLED` всегда `false` (проверяет
`scripts/deploy/check.sh`) — пределы решения 117 там действуют без единого исключения,
этот прогон их никак не смягчает и не отменяет.

**Результат (26.09.2026):** production-сборка (`next build && next start`, порт 3174),
своя база `skilllink_tzwf`, демо-набор после `npm run db:seed` (19 вузов, 50 связок).
Машина: Apple M4, 10 ядер, 24 ГБ, Node 26 — та же, на которой параллельно работали ещё
несколько агентов фермы (решение не ждать отдельного окна тишины: числа ниже — с реальным

**Честно про число отчётов.** 358 отчётов/с — это скорость на демонстрационном наборе:
в нём 50 связок, и CSV на 50 строк собирается быстро независимо от того, что где-то в коде
`limit=5000`. Прогон подтверждает, что систе­ма держит **10 одновременных** таких запросов
без ошибок и без деградации остальной нагрузки (p95 у пользовательского сценария не растёт
пока отчёты формируются параллельно) — то, что спрашивает ТЗ буквально. Абсолютная
пропускная способность выгрузки на реальном объёме данных (тысячи связок) не измерялась
этим прогоном и может быть заметно ниже: это отдельный вопрос, не «выдерживает ли систе­ма
10 параллельных отчётов».
