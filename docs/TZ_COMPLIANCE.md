# Соответствие ТЗ РТК: где проверить каждый пункт

Построчная сверка с официальным текстом ТЗ заказчика (`Система контроля и обработки
статистических данных по обучению студентов ВУЗов и школ по ИТ направлениям`, 2026,
9 страниц) — по разделам и нумерации самого документа. Файл ТЗ не хранится в
репозитории (в `.git/info/exclude`), но прочитан целиком.

Для каждого пункта: что он требует (коротко, своими словами) → статус → где на стенде
https://skilllink.site → какой маршрут API → решение в [журнале](TECHNICAL_DECISIONS.md).
Учётные записи — в [README](../README.md), раздел «Попробовать».

Статусы: **готово** — есть и экран, и API (или пункт не про API — тогда просто сделано);
**API** — есть API, экрана нет, проверяется через [страницу API](https://skilllink.site/api-docs)
или запросом; **частично** — сделана часть, остальное — честно как пробел (см. раздел ниже);
**нет** — не сделано на момент проверки.

Разделы 1–3 ТЗ (список сокращений, актуальность задачи, описание задачи) и раздел 9
(критерии оценки) не содержат отдельных проверяемых требований к решению — они не
включены в таблицы, но прочитаны и учтены при формулировках ниже.

## Что сделано частично — и почему

- **Фильтрация отчётов по периоду и разрезам.** `GET /api/reports/tz` и `/api/reports/catalog`
  принимают только `format` — ни диапазона дат, ни фильтра по вузу, ИТ-направлению, продукту
  или ответственному нет (`reports.schema.ts`). Отчёт строится по всем связкам целиком.
  ТЗ явно требует этого в четырёх местах (п.4 «формировать отчёты… за период», функц. 1,
  «пользователь должен иметь возможность» п.3, «пользовательский путь» п.5) — это самый
  заметный пробел из найденных при полной сверке.
- **Экспорт диаграмм в png/pdf.** На главной есть живые SVG-визуализации (сеть, воронка,
  карта России, разбивка по вузам), но кнопки «сохранить как изображение» у них нет —
  только печать целой страницы у табличных отчётов.
- **Конструктор нового workflow с нуля.** Можно переименовать любой из 14 этапов и
  поменять его нормативный срок, в том числе для уже идущих связок. Признак
  контрольной точки у этапов 6, 7 и 11 не меняется из настроек: на нём держится
  порядок прохождения этапов (решения 5 и 28, [CONTROL_POINTS.md](CONTROL_POINTS.md)),
  и экран объясняет это словами. Новые процессы с нуля — в плане развития.
- **Keycloak.** Осознанное решение по срокам, подробно — в
  [ARCHITECTURE.md](ARCHITECTURE.md). Ролевая модель и API не зависят от способа входа.
- **Приём из LMS и с сайта.** Контракт с заказчиком ещё не согласован (так сказано в
  самом ТЗ), поэтому на другом конце нет настоящего источника. Приёмник работает и
  проверяется через страницу API. Актуализация вузов, программ и вендоров через
  CSV/xlsx есть с экраном («Инструменты → Импорт», решение 177), но без настраиваемого
  маппинга полей — только фиксированный формат файла. Загрузка заказов с сайта
  и файл «Загрузка пользователей» для LMS (`/api/import/site-orders`, `/lms-file`) —
  без экрана, только через страницу API.
- **152-ФЗ и приказ ФСТЭК № 117.** Меры приказа ФСТЭК № 21 (не № 117 — он для
  государственных информационных систем) реализованы частично и описаны честно в
  [PRIVACY.md](PRIVACY.md) и [SECURITY_LIMITATIONS.md](SECURITY_LIMITATIONS.md).
  Формальное соответствие не заявляется — это требует отдельного аудита.
- **Архитектура в Archi.** [ARCHITECTURE.md](ARCHITECTURE.md) описывает функциональную и
  компонентную структуру текстом (стек, модули, поток вызова, разграничение доступа), но
  не как диаграмму в инструменте Archi/ArchiMate, который прямо назван в ТЗ.
- **Справка внутри приложения.** `/help` открыта, но тексты — черновик по коду (решение
  154), скриншотов элементов интерфейса пока нет, а отдельного руководства системного
  администратора внутри справки нет — есть только общая карточка «Роли».
