**ТЕХНИЧЕСКОЕ ЗАДАНИЕ**

**На разработку информационной системы SkillLink**

Система контроля взаимодействия с учебными заведениями
для приобретения навыков работы с востребованными
на рынке цифровыми инструментами

Версия 1.0 | MVP для хакатона | Проект технического задания

# 1. Общие сведения

| Параметр | Описание |
| --- | --- |
| Наименование | SkillLink |
| Тип | Веб-система управления образовательными партнёрствами и аналитикой навыков |
| Предметная область | IT Школа РТК / РТК ИТ |
| Пользователи | Менеджеры партнёрств, аналитики, руководители, администраторы |
| Режим | Внутренняя рабочая система с возможностью будущих интеграций |
| Этап | MVP с демонстрационным контуром и расширяемой архитектурой |

# 2. Назначение системы

Система предназначена для цифровизации взаимодействия IT Школы РТК с образовательными организациями, программами обучения и IT-продуктами. Она объединяет операционное управление сотрудничеством, контроль этапов, аналитику востребованности навыков и рекомендации по дальнейшим действиям.

Основная логика продукта: рынок труда → востребованные навыки → образовательные программы → выявление дефицита навыков → подбор IT-продукта → сотрудничество с вузом → внедрение → обучение → контроль результата.

# 3. Цели и задачи

Создать единый реестр вузов, образовательных программ и IT-продуктов.

Хранить контакты, документы, встречи, задачи и историю взаимодействия.

Контролировать жизненный цикл сотрудничества по каждой связи.

Визуализировать этапы процесса и текущий прогресс.

Сопоставлять навыки образовательных программ с востребованными навыками рынка.

Выявлять skill gap — дефицит или недостаточную представленность навыков.

Формировать объяснимые рекомендации для сотрудников.

Снизить количество ручных операций и риск пропуска контрольных действий.

Предусмотреть интеграцию с LMS, сайтом и будущими системами заказчика.

# 4. Границы MVP

В MVP должен быть реализован полный демонстрационный контур: интерфейс → API → backend → база данных.

Не требуется промышленная интеграция с закрытыми системами РТК без предоставленного API.

Не допускается выдавать mock-данные за подтверждённую статистику.

Полное юридическое соответствие 152-ФЗ и требованиям ФСТЭК не заявляется без отдельного аудита.

Автоматические рекомендации не заменяют решение сотрудника.

Архитектура должна допускать дальнейшее расширение без переписывания всей системы.

Показатели сотрудничества.

Последние события.

## 7.4. Образовательные программы

Показатель соответствия требованиям рынка.

Фильтры по цели сотрудничества, региону и уровню подготовки.

Чек-листы и задачи.

Документы и их статусы.

Участники и ответственные.

История изменений.

Изменение статусов с фиксацией автора и времени.

# 8. Workflow сотрудничества

Система должна поддерживать следующие 14 этапов:

| № | Этап | Обязательные атрибуты |
| --- | --- | --- |
| 1 | Поиск контакта ответственного лица в вузе. | Статус, ответственный, срок, комментарий, результат |
| 2 | Связь и подтверждение актуальности IT-программ. | Статус, ответственный, срок, комментарий, результат |
| 3 | Организация встречи. | Статус, ответственный, срок, комментарий, результат |
| 4 | Обмен документами. | Статус, ответственный, срок, комментарий, результат |
| 5 | Доработка документов при необходимости. | Статус, ответственный, срок, комментарий, результат |
| 6 | Подписание документов. | Статус, ответственный, срок, комментарий, результат |
| 7 | Передача учебных материалов, лицензии и документации. | Статус, ответственный, срок, комментарий, результат |
| 8 | Поддержка внедрения IT-продукта. | Статус, ответственный, срок, комментарий, результат |
| 9 | Обучение преподавателей. | Статус, ответственный, срок, комментарий, результат |
| 10 | Обновление образовательной программы. | Статус, ответственный, срок, комментарий, результат |
| 11 | Проведение занятий. | Статус, ответственный, срок, комментарий, результат |
| 12 | Обновление документации и материалов. | Статус, ответственный, срок, комментарий, результат |
| 13 | Повышение квалификации преподавателей. | Статус, ответственный, срок, комментарий, результат |
| 14 | Контроль выполнения всех этапов. | Статус, ответственный, срок, комментарий, результат |

Допустимые статусы: NOT_STARTED, IN_PROGRESS, BLOCKED, COMPLETED, CANCELLED.

При завершении этапа сохраняются дата завершения, пользователь и комментарий. Для блокировки указывается причина.

Следующее действие.

# 10. Аналитика и рекомендации

Аналитика должна быть объяснимой. Пользователь должен видеть, на основании каких данных получен показатель.

Количество заявок на обучение.

Количество обучающихся.

Количество параллельных групп.

Востребованность навыка на рынке.

Наличие навыка в программе.

Важность навыка для направления.

Соответствие навыка IT-продукту.

Готовность университета к сотрудничеству.

Текущий статус и прогресс связи.

Формулы и коэффициенты фиксируются в ANALYTICS_METHODOLOGY.md. При отсутствии данных система показывает «Нет данных», а не случайное значение.

Рекомендация должна содержать заголовок, описание, приоритет, основание, связанные данные, уровень уверенности и статус.

# 12. API

API должен быть единым и документированным. Для каждого endpoint описываются метод, параметры, тело запроса, ответ, ошибки, авторизация и пример.

| Раздел | Минимальные операции |
| --- | --- |
| Universities | GET list/detail, POST create, PATCH update, archive |
| Programs | GET list/detail, POST create, PATCH update |
| Skills | GET skills, demand, gaps |
| Products | GET list/detail |
| Cooperations | GET list/detail, POST create, PATCH update |
| Workflow | GET stages, PATCH stage, overdue, blocked |
| Analytics | overview, programs, skills, recommendations |
| Documents | list, create metadata, update status |
| Meetings | list, create, update |

Использовать единый формат ошибок, серверную валидацию, корректные HTTP-коды, фильтрацию и пагинацию при необходимости.

# 13. Совместимость frontend и backend

Frontend не должен напрямую зависеть от структуры таблиц базы данных.

Использовать DTO и схемы валидации.

Согласовать названия полей и статусов.

Использовать единый формат дат.

Предусмотреть состояния загрузки, ошибки и пустые данные.

Проверить, что все кнопки имеют реальное действие или явно обозначенный статус MVP.

После изменения данных интерфейс должен обновляться.

Общие типы при возможности вынести в отдельный модуль.

Не допускать дублирования бизнес-логики в разных слоях.

# 19. Приёмочные критерии

Приложение запускается по инструкции.

Основные разделы доступны через навигацию.

Frontend получает данные через согласованный API.

Данные сохраняются и извлекаются из базы данных.

Вузы, программы, навыки, продукты и связи взаимосвязаны.

Workflow содержит все 14 этапов.

Статусы этапов можно просматривать и изменять с учётом прав.

Отображаются просроченные и заблокированные этапы.

Аналитика имеет источник или пометку о демонстрационном характере.

Рекомендации имеют объяснение причины.

Ошибки и отсутствие данных обрабатываются.

Основной демонстрационный сценарий проходит без критических ошибок.
