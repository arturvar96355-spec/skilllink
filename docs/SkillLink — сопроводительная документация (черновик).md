## 1. Обзор решения

**SkillLink** — система контроля и обработки статистических данных по обучению студентов вузов ИТ-направлениям для ИТ-Школы РТК (Ростелеком). Решение построено по официальному ТЗ конкурса «Лидеры цифровой трансформации 2026».

**Проблема.** Сотрудничество с вузами ведётся вручную — по таблицам и переписке, без единой картины: непонятно, какая связь с вузом застряла и на каком этапе, вузы и программы нельзя сравнить между собой, не видно, каким навыкам вузы обучают относительно того, что требует рынок.

**Решение.** Единица учёта — связка «вуз — образовательная программа — IT-продукт». По каждой связке система ведёт путь из 14 этапов (от поиска контакта до контроля исполнения) с обязательными чек-листами и тремя контрольными точками (подписание документов, передача лицензии, начало занятий), которые физически нельзя пройти, если не выполнено условие. Система сама находит, где работа встала, и объясняет рекомендацию данными, а не декларацией.

**Целевые пользователи** (по ролевой модели ТЗ): менеджер по работе с вузами (КАМ, ~20 человек), руководитель менеджеров (роль «Руководитель», с правом переназначать ответственного за вуз и связку), администратор платформы. Дополнительно к базовой трёхролевой модели ТЗ реализованы роль аналитика (доступ к аналитике без права записи) и отдельный портал для представителя вуза — итого 6 ролей.

## 3. Архитектура решения

**Тип архитектуры.** Модульный монолит: единое приложение на Next.js (React на фронтенде + Node.js API-маршруты на бэкенде в одном процессе), разделённое на независимые модули по предметной области. Поток вызова строго `маршрут → сервис → репозиторий`, бизнес-правила — чистые функции с модульными тестами.

**Почему не микросервисы.** Один процесс разработки, одна команда, одна база данных — микросервисная архитектура добавила бы сетевые отказы без выигрыша на этом объёме. Границы модулей проведены так, что при необходимости отдельный модуль можно вынести в самостоятельный сервис — это прямо соответствует требованию ТЗ «решение должно быть отдельным сервисом, который может стать независимой информационной системой».

**Слои (в терминах функциональной/компонентной архитектуры):**
- **Уровень представления** — Next.js App Router, React-компоненты, собственная дизайн-система (без сторонних UI-библиотек и Tailwind).
- **Уровень приложения** — API-маршруты (тонкие, только разбор запроса + вызов сервиса), сервисный слой с бизнес-правилами (контрольные точки, рекомендации, аналитика, рейтинг).
- **Уровень данных** — PostgreSQL, доступ через Prisma ORM, репозитории инкапсулируют все запросы к БД.
- **Инфраструктурный уровень** — Docker-контейнеры, Caddy (обратный прокси, HTTPS), Yandex Cloud (сервер в РФ, данные не покидают страну).

**Модули (по предметной области):** вузы, программы, IT-продукты, связки/workflow, документы, встречи, рекомендации, аналитика (рейтинг, дефициты навыков, рынок труда), пользователи и роли, журнал действий, ИИ-помощник, импорт/экспорт, кабинет вуза (портал).

**Примечание к п.7 ТЗ («архитектура в Archi»):** формальная модель в нотации ArchiMate — отдельная задача, не входит в этот текстовый документ. Описание выше — функциональная и компонентная архитектура словами и таблицей уровней, достаточная основа для построения диаграммы.

## 4. Модель данных

**СУБД:** PostgreSQL. **ORM:** Prisma. 50 моделей (таблиц) и 32 миграции (на 26.09.2026).

**Ключевые сущности:**
- **University (Вуз)** — статусы: новый / в работе / активный / приостановлен / архив.
- **Program (Программа)** — связана с вузом, статусы: черновик / действует / приостановлена / архив.
- **ITProduct (IT-продукт)** — версии, статусы (планируется / действует / выводится).
- **Cooperation (Связка)** — вуз + программа + продукт, 14 этапов (`WorkflowStage`), статус связки (черновик / в работе / на паузе / завершена / отменена).
- **WorkflowStage (Этап)** — номер, статус, срок, чек-лист, признак контрольной точки, история изменений.
- **Document, Meeting** — документы из шаблонов и встречи, привязаны к связке.
- **Recommendation** — рекомендации по правилам, с обоснованием и статусами (новая → в работе → выполнена/отклонена).
- **Skill, MarketDemand** — справочник навыков и рыночный спрос (источник демонстрационный, подключаемый).
- **User, Role** — пользователи и права.
- **AuditLog** — журнал действий с цепочкой хешей (запись только на дозапись, без возможности изменения задним числом).

**Целостность данных:** внешние ключи с индексами, CHECK-ограничения на уровне БД, отдельный скрипт проверки целостности (`db:verify`) — 48 правил на демо-наборе (на 26.09.2026), проверяет, например, что у каждой связки ровно 14 этапов, что программа связки принадлежит тому же вузу, что дата закрытия проставлена только у закрытых связок.

## 6. Безопасность и соответствие 152-ФЗ

### 6.1 Авторизация — почему не Keycloak, и как мигрировать

ТЗ прямо называет технологию: «реализация авторизации через Keycloak». В этой версии — NextAuth.js + bcrypt, не Keycloak. Это осознанное решение по срокам, зафиксированное здесь честно, а не тихо забытое требование.

**Почему не Keycloak в этой версии.** Сроки хакатона (сдача 29.09) не позволяют поднять и обкатать полноценную миграцию: Keycloak — отдельный Java-сервис (Quarkus), официально не меньше ~2 ГБ RAM только под сам процесс, плюс реалм, client, перенос пользователей, тесты входа по всем ролям. Сейчас всё — один процесс Next.js на одной машине рядом с PostgreSQL; добавление контейнера IdP на 2 ГБ туда, где память и так расписана, — риск уронить стенд посреди проверки экспертами, а не улучшение. При этом смысл требования ТЗ — стандартная проверяемая авторизация (роли, сессии, защита входа), а не конкретный продукт как таковой: всё, что Keycloak обычно закрывает «из коробки», в системе уже реализовано отдельно.

**Что уже закрыто без Keycloak:** хранение паролей — bcrypt, 10 раундов; сессии с отзывом — версия сессий в базе, отзывается при смене пароля/роли и блокировке; защита от перебора пароля — пять неудач с адреса и пятьдесят по учётной записи закрывают вход на время; капча — задача на вычисление после трёх неудач, без внешнего сервиса и передачи данных за рубеж; ограничение частоты запросов к API — скользящее окно в памяти процесса; журнал входов — успех/неудача/блокировка в журнале действий; роли и права — 6 ролей (включая «Руководитель») и матрица прав в коде. Чего Keycloak дал бы сверху: единый вход сразу в несколько систем (SSO), готовый экран смены пароля с политиками сложности, подключение LDAP/AD и соцпровайдеров без своего кода, готовая админ-консоль — весомо, если нужен один вход не только в SkillLink.

**Как мигрировать без изменения контракта API.** NextAuth поддерживает провайдер Keycloak через OpenID Connect «из коробки» — переход не требует переписывать ни один маршрут `/api/*`. Шаги: поднять Keycloak (реалм, client); добавить `KeycloakProvider` в конфиг NextAuth рядом с текущим `Credentials` (можно держать оба на переходный период); роли Keycloak (realm roles/groups) замаппить на текущую ролевую модель в `callbacks.jwt` — то же поле `role`, что и сейчас, матрица прав не меняется совсем, потому что она уже развязана от способа входа; сессия остаётся тем же JWT NextAuth, отзыв сессий не меняется. Оценка объёма: **3–5 рабочих дней** для разработчика, знакомого со стеком. Контракт API не меняется ни в одной строке — снаружи система выглядит так же.

**Остальное, что сделано:**
- Данные физически в России (Yandex Cloud), трансграничной передачи нет.
- Пароли — bcrypt с выравниванием времени ответа (защита от атак по времени).
- Защита от подбора пароля: после нескольких неудачных попыток — проверка «не робот» (своя реализация, без внешних сервисов — важно для 152-ФЗ, данные никуда не уходят), далее — временная блокировка учётной записи по паре «учётка + адрес».
- Журнал действий с цепочкой хешей — прошлую запись нельзя подменить незаметно, целостность проверяется отдельной командой.
- Права проверяются на уровне сервиса, а не только интерфейса — представитель вуза не видит чужие вузы (сервер отвечает «не найдено», а не «нет доступа», чтобы не раскрывать сам факт существования записи).
- По запросу человека — выгрузка всех данных о нём и обезличивание контакта (необратимо, доступно только администратору).
- Минимизация: почта и телефон контактов вуза видны только менеджеру и администратору, не аналитику и наблюдателю.
- Персональные данные в ИИ-помощник не передаются — обрабатываются только факты о связке.
- Приложение обращается к базе данных ролью без прав суперпользователя, ограничены права контейнеров.
- Резервное копирование — ежедневно, с проверенным восстановлением.
- Сетевой периметр — открыты только необходимые порты, защита от перебора по SSH.

**Честно, чего нет и почему:**
- **Не заявляем полное соответствие 152-ФЗ** — это оценка разработчиков, а не заключение аудитора.
- Персональных данных обучающихся система не собирает вовсе (ни СНИЛС, ни паспортные данные) — хранятся только рабочие контакты сотрудников вузов.
- Авторизация — не через Keycloak, как названо в ТЗ. Полное обоснование и оценка миграции — раздел 6.1.
- Резервные копии — пока только на том же сервере, копии вне сервера (объектное хранилище) — в дорожной карте.

## 7. Развёртывание и эксплуатация

- Контейнеризация — Docker, обратный прокси — Caddy с автоматическим HTTPS.
- Хостинг — Yandex Cloud (Россия).
- Автоматическая выкладка фронтенда — после прохождения всех проверок в CI (типы, тесты, сборка); изменения на уровне сервера — вручную, после отдельной проверки.
- Перед каждой выкладкой — резервная копия базы данных; после выкладки — автоматическая проверка (порядка 14 контрольных пунктов).
- Мониторинг: проверка доступности стенда каждые 30 минут, автоматическое уведомление при падении.
- Нагрузочное тестирование: на синтетическом объёме (порядка 1000 вузов, 6000 программ, 42000 этапов) самая медленная операция — единицы десятков миллисекунд; отдельный нагрузочный тест держит сотни запросов в секунду на конфигурации, сравнимой с боевым сервером (2 ядра, 4 ГБ); сценарий из ТЗ «50 параллельных пользователей + 10 параллельных отчётов» — 0 ошибок, p95 31,9 мс и 36 мс ([OPERATIONS_TESTS.md](OPERATIONS_TESTS.md), раздел 6).
- Учения по восстановлению: контролируемое отключение базы/сервера, замер времени восстановления — секунды, не часы.

## 8. Тестирование и качество

Четыре независимых слоя проверки, все — часть CI на каждое изменение:
1. **Модульные тесты** — около 3850 тестов на бизнес-правила (на 26.09.2026).
2. **Сквозной сценарий** — автоматический прогон по всему пути связки против живого сервера.
3. **Пробник** — проверка изоляции ролей, кривого ввода, противоречивых состояний.
4. **Сверка стенда со сценарием показа** — перед каждой демонстрацией автоматически проверяется, что цифры на живом стенде совпадают с тем, что заявлено.
