# DESIGN_INTEGRATION.md — связь экранов с API

**Состояние: черновик.** Макетов в `docs/design/` нет — там только заглушка. Документ составлен
по экранам из разделов 7.1–7.6 ТЗ и показывает, какой эндпоинт и какое поле DTO питает каждый
блок. После появления макетов документ нужно сверить с ними поле за полем.

Все перечисленные здесь эндпоинты существуют и проверены сквозным сценарием: на момент
написания — 205 проверок, все проходят.

**Что нужно от Вани и Серёжи:** экспорт макетов (скриншоты или Figma) в `docs/design/`.
Пока их нет, расхождения между макетом и контрактом не видны, а именно они дороже всего
исправлять в конце.

## Общие правила для всех экранов

### Импорт типов

Типы берутся **только** из `@/shared/contracts`:

```ts
import type { UniversityListItemDto, CooperationDto } from '@/shared/contracts'
```

Импортировать что-либо из `@/generated/prisma` запрещено: это внутренняя структура таблиц,
она меняется вместе со схемой.

### Четыре состояния каждого экрана

| Состояние | Как определить | Что показать |
| --- | --- | --- |
| Загрузка | запрос не завершён | скелетон или индикатор |
| Ошибка | HTTP ≥ 400, в теле `error.message` | текст `error.message` (он уже на русском) |
| Пусто | `data` — пустой массив | «Записей нет» + подсказка, что делать |
| Успех | `data` заполнена | содержимое |

Для ошибок валидации (`code: "VALIDATION_ERROR"`) в `error.details` лежит массив
`{ field, message }` — подсветить конкретные поля формы.

### Пометка демонстрационных данных

У каждой записи есть `isMock`, у аналитики — ещё и `containsMockData`. **Показывать пометку
обязательно** — это требование раздела 4 ТЗ, а не пожелание.

### «Нет данных»

Числовой показатель приходит объектом с `value` и `basis`. При `basis: "none"` значение равно
`null` — показать «Нет данных», не «0». Текст `explanation` годится для подсказки при наведении.

### Обновление после изменения

`PATCH /api/workflow/stages/:id` и `PATCH /api/workflow/tasks/:id` возвращают **этап целиком**,
`PATCH /api/cooperations/:id` — связку целиком. Второй запрос за свежими данными не нужен.

## 1. Dashboard (раздел 7.1 ТЗ)

Один запрос: `GET /api/analytics/overview`.

| Блок макета | Поле DTO |
| --- | --- |
| Количество активных связей | `metrics[key="activeCooperations"]` |
| Количество вузов в работе | `metrics[key="universitiesInWork"]` |
| Процент этапов, закрытых в срок | `metrics[key="stagesOnTimePercent"]` |
| Среднее время до контрольного события | `metrics[key="avgDaysToClasses"]` |
| Операций на связку (метрика эффекта из концепции) | `metrics[key="operationsPerCooperation"]`, `basis: "estimate"` |
| Топ рекомендуемых программ | `topPrograms[]`: `programName`, `universityName`, `score`, `factors[]` |
| Проблемные связи и просроченные этапы | `problemCooperations[]`: `reason`, `stageNumber`, `daysOverdue` |
| Соответствие навыков требованиям рынка | `skillMatch`: `coveragePercent`, `criticalGaps`, `period` |
| Блок приоритетных действий пользователя | `priorityActions[]` — открытые рекомендации, критичные сверху |

Переход из KPI к связанным объектам:

| KPI | Куда вести |
| --- | --- |
| Активные связи | `/cooperations?status=ACTIVE` |
| Вузы в работе | `/universities?status=IN_PROGRESS&status=ACTIVE` |
| Проблемные связи | `/cooperations/:cooperationId` |
| Соответствие навыков | `/skills/gaps` |

**Блок приоритетных действий пользователя** (последний пункт 7.1) — `priorityActions[]`:
открытые рекомендации, отсортированные по приоритету. У каждой есть `justification` —
показывать обязательно, иначе непонятно, почему система это предлагает.

Блок пуст, пока не запускалась генерация рекомендаций
(`POST /api/recommendations/generate`). Это нормальное пустое состояние, а не ошибка.

## 2. Реестр университетов (раздел 7.2 ТЗ)

`GET /api/universities`

| Колонка / элемент | Поле |
| --- | --- |
| Название | `name`, `shortName` |
| Город, регион | `city`, `region` |
| Статус | `status` |
| Количество программ | `programCount` |
| Количество связей | `cooperationCount`, `activeCooperationCount` |
| Дата последнего обновления | `updatedAt` |
| Пометка демо | `isMock` |

| Действие макета | Запрос |
| --- | --- |
| Поиск | `?q=` — ищет по названию, краткому названию, городу, региону **и названиям программ** |
| Фильтр по статусу | `?status=ACTIVE&status=NEW` |
| Фильтр по региону | `?region=Москва` |
| Сортировка | `?sort=name`, `?sort=-updatedAt` |
| Добавление | `POST /api/universities` |
| Редактирование | `PATCH /api/universities/:id` |
| Архивирование | `POST /api/universities/:id/archive` |
| Переход к карточке | `GET /api/universities/:id` |

**Расхождение с ТЗ.** Пункт 7.2 требует фильтрацию по рейтингу. Рейтинг считается у программ,
а не у вузов, и в базе не хранится (см. [DATABASE_SCHEMA.md](DATABASE_SCHEMA.md)). Фильтра по
рейтингу вуза сейчас нет. `TODO: PM DECISION` — нужен ли рейтинг вуза как отдельный показатель
или достаточно рейтинга его программ.

**Про архивирование.** Если у вуза есть незакрытые связки, придёт `CONFLICT` 409 с
`details.openCooperations`. Показать понятное сообщение, а не общую ошибку.

## 3. Карточка университета (раздел 7.3 ТЗ)

`GET /api/universities/:id`

| Блок | Поле |
| --- | --- |
| Название, краткое название, город, адрес, сайт | `name`, `shortName`, `city`, `address`, `website` |
| Статус взаимодействия | `status` |
| Контактное лицо, должность, телефон, почта | `primaryContact` (весь список — в `contacts[]`) |
| Количество направлений, студентов, программ | `directionCount`, `studentCount`, `programCount` |
| Показатели сотрудничества | `cooperationCount`, `activeCooperationCount` |

Вкладки:

| Вкладка | Запрос |
| --- | --- |
| Обзор | `GET /api/universities/:id` |
| Программы | `GET /api/programs?universityId=:id` |
| Связи | `GET /api/cooperations?universityId=:id` |
| Документы | `GET /api/documents?universityId=:id` |
| Встречи | `GET /api/meetings?universityId=:id` |
| История | **нет эндпоинта**, `audit_log` не отдаётся наружу |

**Чего нет в API.** «Рейтинг с указанием природы и методики расчёта» и «Последние события»
из 7.3. Рейтинг вуза не считается (см. выше), лента событий требует эндпоинта над `audit_log`.

## 4. Образовательные программы (раздел 7.4 ТЗ)

`GET /api/programs`, `GET /api/programs/:id`

| Блок | Поле |
| --- | --- |
| Связь с университетом | `universityId`, `universityName` |
| Уровень и длительность | `level`, `durationMonths` |
| Показатели набора | `metrics.applicationCount`, `metrics.studentCount`, `metrics.groupCount` |
| Список навыков программы | `skills[]`: `name`, `level`, `importance`, `source` |
| Связанные сотрудничества | `cooperationCount`, список — `GET /api/cooperations?programId=:id` |

| Блок | Отдельный запрос |
| --- | --- |
| Рыночная востребованность навыков | `GET /api/skills/demand` |
| Выявленные дефициты навыков | `GET /api/skills/gaps?programId=:id` |
| Показатель соответствия рынку | считается на фронте из ответа `gaps` либо берётся `skillMatch` с дашборда |

Связанные IT-продукты у программы напрямую не отдаются: связь идёт через сотрудничества.
Если макет показывает продукты прямо в карточке программы — нужен новый эндпоинт, сообщите.

**Про показатели набора.** Это объекты, а не числа. `metrics.studentCount.value` может быть
`null` — у демо-программ вроде «Сети связи и системы коммутации» данных нет намеренно, чтобы
проверить поведение интерфейса.

## 5. Раздел рекомендаций (раздел 7.5 ТЗ)

`GET /api/recommendations`, `POST /api/recommendations/generate`

| Блок макета | Поле |
| --- | --- |
| Разделение на рекомендации по программам, вузам и навыкам | `type`: `PROGRAM`, `UNIVERSITY`, `SKILL`, `ACTION` |
| Показ причины рекомендации | `justification` — **показывать всегда** |
| Показ соответствия рынка и ключевых навыков | `relatedData` — раскрывается в карточке |
| Приоритет | `priority`: `LOW`, `MEDIUM`, `HIGH`, `CRITICAL` |
| Уверенность | `confidence` |
| Переход к подробной карточке | `target.objectType` + `target.objectId` |
| Фильтр по региону | `?region=` — работает для рекомендаций, привязанных к связке |
| Передача объекта в раздел сотрудничества | `POST /api/cooperations` с данными из `relatedData` |

Работа сотрудника с рекомендацией — `PATCH /api/recommendations/:id`:

| Действие | Тело | Что учесть |
| --- | --- | --- |
| Взять в работу | `{ "status": "IN_PROGRESS" }` | |
| Принять | `{ "status": "ACCEPTED" }` | комментарий необязателен |
| Отклонить | `{ "status": "DISMISSED", "comment": "…" }` | **без комментария придёт 422** |

Кнопка «Обновить рекомендации» вызывает `POST /api/recommendations/generate`. Повторный запуск
не плодит дубликаты и не сбрасывает уже принятые решения.

Дополнительно доступны:

- рейтинг программ с раскрытием вклада — `GET /api/analytics/programs`;
- критичные дефициты навыков — `GET /api/skills/gaps?criticalOnly=true`.

**Чего нет.** Фильтров по цели сотрудничества и уровню подготовки, добавления объектов
в подборку. Если эти блоки есть в макетах — сообщите, нужен отдельный эндпоинт.

## 6. Раздел сотрудничества (раздел 7.6 ТЗ)

`GET /api/cooperations/:id` — один запрос, в нём есть всё, кроме документов.

| Блок | Поле |
| --- | --- |
| Университет, программа, IT-продукт | `universityName`, `programName`, `productName` |
| Текущий статус | `status` |
| Текущий этап | `currentStage`: `stageNumber`, `title`, `phase`, `status`, `isOverdue` |
| Процент выполнения | `progress.percent` (знаменатель — 13 этапов, без контрольного) |
| Срок до контрольного события | `daysToTarget` (отрицательное — срок прошёл) |
| Чек-листы и задачи | `stages[].tasks[]`: `title`, `isRequired`, `isDone` |
| Участники и ответственные | `responsible`, `stages[].responsible` |
| История изменений | `GET /api/workflow/stages/:id/history` |
| Документы и их статусы | `GET /api/documents?cooperationId=:id` |
| Кнопка «Собрать пакет документов» | `POST /api/cooperations/:id/documents/generate` |
| Встречи по связке | `GET /api/meetings?cooperationId=:id` |

### Конвейер этапов

`stages[]` — 14 этапов. Поле `phase` группирует их в четыре фазы конвейера из концепции:

| `phase` | Этапы | Подпись |
| --- | --- | --- |
| `ATTRACTION` | 1–3 | Привлечение |
| `FORMALIZATION` | 4–6 | Оформление |
| `IMPLEMENTATION` | 7–10 | Внедрение |
| `OPERATION` | 11–13 | Эксплуатация |
| `CONTROL` | 14 | Контроль |

Этап с `isAutoManaged: true` (только этап 14) показывается **только для чтения**: кнопок смены
статуса у него быть не должно. Попытка изменить вернёт `INVALID_TRANSITION` 409.

### Диалоги смены статуса

`PATCH /api/workflow/stages/:id`. Какие поля обязательно спрашивать у пользователя:

| Действие | Что спросить | Иначе придёт |
| --- | --- | --- |
| Завершить | `result` — описание результата | 422 `VALIDATION_ERROR` |
| Завершить | сначала закрыть обязательные пункты чек-листа | 409 `INVALID_TRANSITION` |
| Заблокировать | `blockingReason` | 422 |
| Отменить | `comment` с основанием | 422 |
| Переоткрыть завершённый или отменённый | `comment` с причиной | 422 |

Доступные кнопки считаются из текущего статуса:

| Статус | Что можно |
| --- | --- |
| `NOT_STARTED` | Начать, Отменить |
| `IN_PROGRESS` | Завершить, Заблокировать, Отменить |
| `BLOCKED` | Возобновить, Отменить |
| `COMPLETED` | Переоткрыть |
| `CANCELLED` | Переоткрыть (только роль ADMIN) |

Индикация: `isOverdue: true` — срок прошёл, `daysToDeadline` отрицательное. Количество
обязательных пунктов — `requiredTasksDone` / `requiredTasksTotal`.

## 7. Кабинет представителя вуза

Экранов в макетах нет — их нужно нарисовать. Данные уже отдаются.

| Экран | Запрос | Что показать |
| --- | --- | --- |
| Сводка кабинета | `GET /api/portal/overview` | свой вуз, его программы с показателями, связки со статусом и процентом, счётчик неподтверждённых материалов |
| Переданные материалы | `GET /api/portal/materials` | список с признаком `isConfirmed` и кнопкой подтверждения |
| Подтверждение получения | `POST /api/portal/materials/:taskId/confirm` | тело необязательно; в ответе — обновлённый список |
| Ввод показателей | `PATCH /api/portal/programs/:id/metrics` | только `studentCount` и `groupCount` |
| Подача заявки | `POST /api/portal/applications` | `programId` и `quantity`; **полей ФИО быть не должно** |
| Список заявок | `GET /api/portal/applications` | |

Чего представитель вуза **не видит** — эти разделы в его интерфейсе показывать нельзя:

- аналитику, рейтинги и рекомендации (`403 FORBIDDEN`);
- другие вузы: запрос чужой записи возвращает **404**, а не 403;
- внутренние комментарии к этапам, причины блокировок и заметки по связке — они приходят
  как `null`. Статус, результат этапа и автора изменения он видит.

Роль и права приходят из `GET /api/auth/me` в поле `permissions` — по ним фронт решает,
какие разделы рисовать, вместо того чтобы дублировать матрицу доступа у себя.

## 8. Что нужно проверить, когда появятся макеты

1. Все ли поля макета есть в DTO — и наоборот, нет ли в DTO лишнего.
2. Совпадают ли подписи статусов с перечислениями (`NEW`, `IN_PROGRESS`, …).
3. Есть ли в макетах состояния «загрузка», «ошибка», «нет данных».
4. Показана ли пометка демонстрационных данных.
5. У каждой ли кнопки есть реальное действие или явная пометка «заглушка MVP» (раздел 13 ТЗ).
6. Сходится ли формат дат: API отдаёт ISO 8601 в UTC, формат отображения — забота фронта.
