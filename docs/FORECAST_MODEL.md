# FORECAST_MODEL.md — прогноз «дойдёт ли связка до вехи»

Решение 132 (docs/TECHNICAL_DECISIONS.md). Код — `src/modules/analytics/forecast-*.ts`,
`forecast.repo.ts`, `forecast.service.ts`; настройки — `src/shared/config/forecast.config.ts`
(все числа там — рабочие гипотезы, помечены `TEMP`).

## Задача одной фразой

Вуз и IT-компания идут по конвейеру из 14 этапов (`docs/DATABASE_SCHEMA.md`). Ключевые вехи —
этап 6 «Подписание документов» и этап 11 (начало занятий). Для связки, которая ещё не дошла
до ближайшей вехи, система оценивает: какова вероятность дойти до неё за горизонт (60 или
90 дней), и объясняет — почему.

## Как объяснить жюри за минуту

1. Берём историю: на каждую дату, когда связка была на каком-то этапе, — набор признаков
   («снимок») и метка: дошла ли связка до вехи в следующие 60/90 дней. Признаки считаются
   только по тому, что уже случилось к этой дате, — будущего модель не видит.
2. Обучаем логистическую регрессию (метод Ньютона, штраф L2) — 13 признаков,
   один понятный коэффициент на каждый.
3. Проверяем честно: обучаемся на ранней части истории, проверяем на поздней (без
   перемешивания дат — так же, как модель будет работать в реальности: только вперёд по
   времени). Считаем AUC, Brier, калибровку по 5 корзинам.
4. **Публикуем модель, только если она доказала, что лучше простого правила** (частота вехи
   по текущему этапу) на статистически вменяемой выборке. Если нет — честно показываем
   правило и говорим, что данных мало. На нынешнем размере выборки это ожидаемо: см.
   «Честные ограничения».
5. Для конкретной связки — не просто число: разложение по признакам («3 встречи за месяц —
   больше, чем у 80% связок») плюс топ-3 причины «за» и «против».

## 1. Признаки на момент t (без утечки будущего)

`forecast-features.ts`, функция `featuresAt`. История связки обрезается по дате `t`
(`truncateTimeline`) до вызова `featuresAt` — функция физически не получает событий позже `t`.
Метка (дошла ли связка до вехи за горизонт `H`) считается отдельно, по полной истории,
в полуинтервале `(t; t + H]` — это то, что мы предсказываем, а не признак.

| Признак | Смысл |
| --- | --- |
| `stageNumber` | номер текущего этапа (1–13) |
| `stageDurationRatio` | дней на текущем этапе ÷ медиана этапа (геттер из аналитики этапов — медиана по Каплану–Мейеру, решение 120; нет данных по этапу — запасной расчёт по истории связок или норматив) |
| `meetings30`, `meetings90` | встреч за 30 / 90 дней |
| `daysSinceActivity` | дней с последнего события (встреча, смена статуса этапа/документа, отметка пункта, отклонение рекомендации) |
| `stageTasksDoneShare` | доля закрытых пунктов чек-листа текущего этапа |
| `documentsInReview` | есть ли документ связки в статусе «На согласовании» |
| `regionCapital` | вуз в Москве или Санкт-Петербурге |
| `levelSpo`, `levelMaster` | уровень программы (one-hot, СПО / магистратура и аспирантура) |
| `universityActiveCooperations` | сколько ещё действующих связок у вуза на момент `t` |
| `hadBlock` | этапы связки уже блокировались |
| `dismissedRecommendations` | сколько рекомендаций по связке отклонено |

Снимки истории — скользящее окно с шагом 7 дней (`snapshotStepDays`) назад от
`now − горизонт`: более поздние даты не берутся — их исход ещё не наступил (правое
цензурирование, `snapshotDates`).

## 2. Модель

Логистическая регрессия с L2-регуляризацией, обучение методом Ньютона (IRLS,
`fitLogisticNewton`, шаг делится пополам, если он ухудшил потери — не расходится на почти
разделимых данных). Признаки стандартизуются (среднее 0, отклонение 1) — коэффициенты
сравнимы между собой и не зависят от единиц измерения.

**Базовая линия** (`fitBaseline`) — частота достижения вехи среди снимков на том же
текущем этапе, со сглаживанием к общей частоте (меньше данных по этапу — оценка ближе
к общей). Это то, с чем модель обязана конкурировать: простое, понятное правило
«у нас обычно с этапа N доходят в стольки-то процентах случаев».

## 3. Честная оценка и ворота публикации

**Временное разбиение** (`splitDate`, доля проверки — 30% самых поздних снимков по дате):
обучаются модель и правило только на снимках, чей исход уже известен к границе разбиения
(`t + H ≤ граница`); проверяются — на снимках позже границы. Даты не перемешиваются: модель
проверяется именно на будущем относительно обучения, как в реальной работе.

- **AUC** — площадь под ROC-кривой через ранги (статистика Манна — Уитни), тем самым
  correctно обрабатывает и ничьи (одинаковые вероятности получают половину очка).
- **Brier score** — средний квадрат ошибки вероятности (0 — идеально, 0,25 — «всегда 50%»).
- **Калибровка** — 5 корзин по предсказанной вероятности: средняя предсказанная вероятность
  против доли фактически дошедших.
- **PSI** (Population Stability Index) — сдвиг распределения признака: `Σ (a − e)·ln(a/e)`
  по 10 корзинам (децили обучающей выборки), `a` — доля в текущих данных, `e` — в обучении.
  Меньше 0,1 — сдвига нет, 0,1–0,25 — умеренный, больше 0,25 — сильный.

**Ворота публикации** (`evaluateGate`) — модель заменяет правило, только если ВСЕ условия
выполнены:

1. на обучении было не меньше 30 снимков и не меньше 5 каждого исхода (иначе модель даже
   не обучается);
2. на проверке — не меньше 60 снимков, из них не меньше 15 положительных и 15 отрицательных;
3. AUC модели выше AUC правила хотя бы на 0,02;
4. нижняя граница 95% доверительного интервала AUC (формула Хэнли — Макнила) выше 0,5 —
   модель доказанно лучше угадывания, а не просто по точечной оценке.

Если хотя бы одно из первых двух условий не выполнено — статус `insufficient_data`
(«Недостаточно данных»); если данных достаточно, но модель не выиграла у правила —
`baseline_better`; всё пройдено — `published`. В любом непубликуемом случае API отдаёт
вероятность **правила**, явно помечая источник (`source: "baseline"`).

**Статус прогноза** дополнительно проверяет, не устарела ли опубликованная модель:
- обучена больше 14 дней назад (`staleAfterDays`), или
- у какого-то признака PSI текущих открытых связок против обучающей выборки выше 0,25
  (сдвиг считается только при не менее чем 20 текущих связках — на горстке значений
  PSI — шум, а не сигнал).

## 4. Объяснение прогноза

Вклад признака = коэффициент × стандартизованное значение (`contributions` в
`forecast-model.ts`). Сумма вкладов всех признаков плюс свободный член — это логит,
из которого сигмоидой получается вероятность: объяснение складывается ровно в то же
число, а не рассказывает о нём что-то приблизительное (проверено тестом,
`forecast-explain.test.ts`). Топ-3 «за» и топ-3 «против» по силе вклада переводятся в
обычные фразы («3 встречи за месяц — больше, чем у 80% связок», по квантилям обучающей
выборки) — `describeFeature`, `explainContributions`.

Если модель не прошла ворота, вместо разложения по признакам — предложение вида
«Из 7 случаев, когда связка была на этапе 4, до подписанного договора за 60 дней дошли 2»
(частота правила по этому этапу, `direction: "info"`, вкладов у правила нет).

## 5. Хранение

Таблица `forecast_models` — одна запись на веху (`milestoneStage`, уникальность), новое
обучение заменяет предыдущую. Прогнозы для конкретных связок не хранятся — считаются на
лету. Это агрегированные коэффициенты и метрики качества модели, не персональные данные
(`src/modules/dsar/dsar.registry.ts`, `DSAR_NOT_PERSONAL`).

## 6. API и права

- `GET /api/analytics/forecast/model` — метрики, статус, коэффициенты, калибровка обеих вех.
- `GET /api/cooperations/:id/forecast` — прогноз одной связки.
- `POST /api/analytics/forecast/train` — переобучение (право `ADMIN`, группа rate-limit
  `heavy`); тот же результат печатает `npm run forecast:train`.

Право на чтение прогноза — `ANALYTICS`, как и на остальную аналитику: представителю вуза
недоступно ни по чужим связкам, ни по своим — это внутренняя оценка ИТ-Школы, а не то,
чем делятся с вузом (`docs/API_CONTRACT.md`, раздел 9а).

## 7. Тесты и синтетика

`forecast.synthetic.ts` — детерминированный генератор (mulberry32, зерно фиксировано)
**только для тестов**, в приложении и сиде не используется:

- `patternTimelines` — у каждого вуза постоянная вовлечённость: у трети она низкая
  (мало встреч, долгая тишина) — вуз медленнее проходит все этапы, и это заметно
  по признаку «дней без активности», а не только по номеру этапа. На этом наборе модель
  обязана обойти правило: AUC > 0,75, коэффициент при `daysSinceActivity` — отрицательный
  (дольше тишина — меньше шанс дойти до вехи);
- `noiseTimelines` — подписание наступает с постоянной интенсивностью независимо ни от
  чего; на этом наборе ворота обязаны НЕ пропустить модель.

`npm run forecast:report` печатает метрики и калибровку обеих вех в консоль — для слайда
презентации, без похода в интерфейс.

## Честные ограничения

- **Выборка маленькая и демонстрационная.** На демонстрационном наборе (50 связок,
  решение 131) веха «подписание договора» набирает достаточно снимков для расчёта
  AUC, но нижняя граница доверительного интервала не выше угадывания — ворота честно
  отдают `baseline_better`; у вехи «начало занятий» снимков вообще меньше порога —
  `insufficient_data`. Это не баг, а то, зачем ворота вообще нужны — не выдавать
  неподтверждённую модель за надёжную. Метрики на реальных данных появятся только
  когда накопится настоящая история этапов.
- **Данные демонстрационные**, включая часть сюжетов. `isMock` в ответе API это отмечает.
- **AUC на снимках одной связки не независим** (несколько снимков одной связки коррелируют
  между собой), доверительный интервал по Хэнли — Макнилу это не учитывает и немного
  оптимистичен — честно сказано в самой формуле (`aucLowerBound`, `forecast-math.ts`).
- **История пауз не хранится**: связка на паузе помечается оговоркой в ответе, а не
  отдельным признаком.
- **Линейная модель одним коэффициентом на признак** — читаема и объяснима (важно для
  жюри), но не ловит нелинейные и пороговые эффекты так же хорошо, как более сложные
  модели; отчасти поэтому у неё не всегда получается обойти простое частотное правило —
  ворота именно поэтому и нужны, а не только «для галочки».
- **PSI по возрасту вехи «начало занятий»** может годами не набирать 20 текущих связок —
  тогда сдвиг признаков не проверяется вовсе, статус зависит только от возраста модели.
