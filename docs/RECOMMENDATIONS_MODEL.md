# RECOMMENDATIONS_MODEL.md — рекомендации, которые учатся и объясняют себя

Решение 119. Код: `src/modules/recommendations/recommendations.learning.ts` (формулы),
`recommendations.stats.repo.ts` (запись в базу), `recommendations.explain.ts` и
`recommendations.reasons.ts` (объяснимость), `recommendations.simulation.ts` (модель решений).
Параметры — `RECOMMENDATION_LEARNING`, `RECOMMENDATION_VALUE_ANCHORS`,
`RECOMMENDATION_DISABLED_RULES` в `src/shared/config/analytics.config.ts`, все видны
в «Настройки → Параметры расчётов».

## Жюри за одну минуту

1. **Правила решают, что предложить** — пять прозрачных правил (просрочка, застой, связка
   без продукта, нет данных по программе, дефицит навыка). Модель ничего не выдумывает.
2. **Решения менеджеров решают, в каком порядке.** Каждое правило копит простую статистику:
   сколько раз его рекомендацию показали и сколько раз она оказалась полезной (выполнена,
   проблема ушла, связка сдвинулась на следующий этап).
3. **Вес правила = доля полезных**, сглаженная: `(1 + полезных) / (2 + показов)`. Без данных — 0,5.
   Правило, которое систематически отклоняют, за 90 дней опускается с 0,50 до 0,13
   (`npm run recs:simulate`), и его рекомендации идут ниже в ленте — но не исчезают.
4. **Память с забыванием**: событие месячной давности весит вдвое меньше свежего. Поменялись
   люди или процесс — система переучивается за пару месяцев, старые решения её не держат.
5. **Каждая рекомендация объясняет себя**: причины из фактов («связка без движения 27 дн.
   при пороге 14», «вес правила 0,12 ниже 0,35: рекомендации „Связка без движения“ полезны лишь
   примерно в 12 % случаев — балл снижен») и разбор балла.
   А на вопрос «почему здесь нет рекомендации» отвечают **те же проверки**, что у правила.

## Формулы

**Событие.** Показ — рекомендация создана или открыта снова (`trials + 1`). Успех —
выполнена человеком, закрыта системой при действующем объекте (проблема ушла), или связка
перешла на следующий этап в течение `progressCreditDays` = 30 дн. после показа
(`successes + 1`, не больше одного раза на показ). Отклонение — показ без успеха.

**Затухание.** `coef = 0,5^(Δt / H)`, `H = halfLifeDays = 30`. На каждом событии:

    successes_eff := successes_eff · coef + Δs
    trials_eff    := max(trials_eff · coef + Δt, successes_eff)
    eff_updated_at := max(eff_updated_at, момент события)

`max` нужен потому, что успех приходит позже показа: к этому времени показ уже остыл,
а успех весит 1. Так `successes_eff ≤ trials_eff` держится точно (проверяют тест и
`db:verify`). Дробные счётчики не округляются. При чтении счётчики «доостуживаются»
до текущего момента тем же множителем.

**Вес правила.** Среднее апостериорного Beta(1 + s, 1 + t − s) по эффективным счётчикам:

    p = (1 + s) / (2 + t)

**Частичный пулинг.** Уровни: общий → вуз → менеджер. Уровень берёт априорное
распределение у уровня выше с «весом» `k = poolingStrength = 5` показов:

    p_уровня = (s_уровня + k · p_выше) / (t_уровня + k)

Почему `k ≈ 5`: у вуза или менеджера в демо-объёме 1–10 показов в месяц. При `k = 5` пять
собственных решений весят столько же, сколько вся общая статистика, — один случайный
отказ не роняет вес вуза вдвое, а устойчивая разница проявляется за 2–3 недели. Формула
одна при любом объёме данных, поэтому балл не прыгает на границе «мало данных / достаточно».
`pSource` в ответе — только подпись: `global` — своих данных нет, `pooled` — меньше
`localDataTrials` = 5 эффективных показов (общая оценка ещё перевешивает), `local` — больше.

**Балл рекомендации** в [0..1]:

    score = 0,50 · p + 0,35 · v / (v + якорь) + 0,15 · приоритет

| Правило | Ценность `v` | Якорь (ценность 0,5) |
| --- | --- | --- |
| Просроченный этап | дней просрочки | 14 |
| Связка без движения | дней без движения | 30 |
| Критичный дефицит | спрос на навык, из 100 | 50 |
| Нет данных по программе | пустых показателей из 3 | 1,5 |
| Связка без продукта | этапов оформления без продукта | 3 |

Приоритет: критичный 1, высокий 0,67, средний 0,33, низкий 0. Каждая часть в [0..1], веса
в сумме 1 — балл не выходит за [0..1] и не убывает ни по одной части (тесты).

**Детерминированно.** По умолчанию `p` — среднее распределения: лента одинакова при каждом
обновлении, что нужно для показа. Режим `sampling: 'thompson'` берёт `p` случайной выборкой
из того же Beta: правило с малым числом данных иногда поднимается наверх и получает шанс
набрать статистику. Включается одной строкой конфига; разбор балла тогда говорит
`sampling: "thompson"`.

**Интервал.** `ci90` в весах правил — квантили 5 % и 95 % того же Beta (неполная бета-функция
численно, без приближения нормалью — при малых счётчиках нормаль вылезала бы за [0, 1]).

**Пауза после отклонения** — `dismissPauseDays` = 30: то же правило по тому же объекту не
создаётся и не открывается снова; «почему нет» называет дату конца паузы.

**Защита от перегрузки.** У менеджера за 30 дней ≥ 15 показов и выполнено < 10 % —
его рекомендации с баллом < 0,6 получают `isDeferred: true` и уходят в конец ленты
по баллу. Не удаляются, фильтр `deferred=false` их прячет.

## Гонки

Статистика пишется одним `INSERT … ON CONFLICT (rule_type, scope_type, scope_id) DO UPDATE`
на пачку событий; затухание считается в SQL от значения в строке на момент записи.
Два параллельных решения блокируют строку по очереди, второе видит результат первого —
события не теряются. Отметка «успех засчитан» (`success_at`) и запись статистики —
в одной транзакции, условие `success_at IS NULL OR success_at < shown_at` не даёт засчитать
один показ дважды. Пробник: три параллельные пересборки дают ровно столько показов, сколько
записей создано; шесть параллельных «Выполнено» — ровно шесть успехов.

## Объяснимость

- `reasons: [{ code, pass, label, detail, facts }]` — проверки правила (все пройдены, раз
  рекомендация есть) и пометки обучения (`rule_weight_low`, `manager_overloaded`). Коды —
  `<предмет>_<состояние>`, тексты — один словарь `recommendations.reasons.ts`, только из фактов.
- `scoreBreakdown` — `p`, `pSource`, `pLevel`, эффективные счётчики, ценность и её
  насыщение, приоритет, веса, балл: «почему эта рекомендация выше».
- `GET /api/recommendations/why-not?entity=program|cooperation|skill&id=…` — те же функции
  проверок (`evaluateCooperation`, `evaluateProgram`, `evaluateSkillGaps`), что у пересборки;
  черновик рекомендации создаётся ровно тогда, когда все проверки пройдены (тест на сотнях
  случайных связок).
- `GET /api/recommendations/rules/stats` — вес каждого правила, интервал, счётчики.

## Цифры для слайда

`npm run recs:simulate` — 90 дней, объекты демо-набора (52 пары «правило × объект»),
зерно 119. Модель менеджера: просрочку выполняют в 75 % случаев, дефицит — 55 %, продукт — 65 %,
данные программы — 60 %, застой — 10 %.

| Правило | Показано | Выполнено | Отклонено | Вес на 90-й день | 90 % интервал |
| --- | --- | --- | --- | --- | --- |
| Просроченный этап | 40 | 25 | 11 | 0,57 | 0,38–0,74 |
| Критичный дефицит | 77 | 46 | 29 | 0,58 | 0,44–0,72 |
| Связка без продукта | 36 | 24 | 10 | 0,65 | 0,45–0,83 |
| Нет данных по программе | 45 | 27 | 16 | 0,52 | 0,34–0,70 |
| **Связка без движения** | 27 | 3 | 24 | **0,13** | 0,02–0,31 |

Вес «связки без движения» по неделям: 0,50 → 0,21 (7-й день) → 0,27 (28-й) → 0,19 (56-й) →
0,13 (90-й). Балл одинаковой рекомендации «без движения 21 дн.» падает с 0,44 до 0,26 —
ниже «просрочки 5 дн.» того же приоритета (0,42). `--json файл` — ряды для графика.

В демо-данных та же модель пишет 90-дневную историю в базу тем же SQL (сид сверяет результат
с формулой построчно): на стенде «связка без движения» весит около 0,12, остальные — 0,5–0,65.

## Ограничения — честно

- **Это не машинное обучение в смысле CLAUDE.md** («ML-модели в бизнес-логике» запрещены):
  нет обучаемых весов и чёрного ящика — счётчики, одна формула и параметры в конфиге;
  каждое число раскладывается в разборе балла.
- **Неотвеченная = отклонённая.** Показ учитывается сразу, поэтому ещё не решённые
  рекомендации временно тянут вес правила вниз так же, как отклонённые. На свежем правиле
  с потоком новых рекомендаций вес занижен на долю ещё не решённых.
- **Успех — не причинность.** «Проблема ушла» и «связка сдвинулась в течение 30 дней» могли
  случиться и без рекомендации. Настоящий эффект можно мерить только сравнением с группой,
  которой рекомендацию не показывали, — на объёмах пилота это неосуществимо.
- **Уровни пересекаются.** Общий уровень включает события вуза и менеджера — при пулинге они
  учитываются дважды; на малых объёмах это слегка тянет свою оценку к общей.
- **Ответственный сменился** — успех засчитывается новому менеджеру, показ был у прежнего;
  `max` сохраняет инвариант, но статистика менеджеров на таких связках неточна.
- **Балл закрытых не пересчитывается** — остаётся на момент последнего пересчёта открытых.
- **Истории весов сервер не хранит** — только текущие счётчики. График «как падал вес» —
  из симуляции; для реальной истории нужна таблица снимков (после защиты).
- **Модель менеджера в симуляции придумана**: доли выполненных — допущения, а не данные.
  Цифры показывают механизм, а не обещают результат.
- Все параметры — рабочие значения (TEMP), подбираются на реальных решениях после пилота.
