## 3. Prisma 7 с драйверным адаптером вместо Prisma 6

**Дата:** 21.09.2026

В Prisma 7 свойство `url` в блоке `datasource` больше не поддерживается: строка подключения
задаётся в `prisma.config.ts`, а клиент работает через драйверный адаптер.

**Решение.** Взята Prisma 7.10 с `@prisma/adapter-pg`. Строка подключения — в `prisma.config.ts`
из `DATABASE_URL`, клиент создаётся в единственном месте (`src/shared/db/prisma.ts`).

**Альтернатива.** Остаться на Prisma 6 с привычным синтаксисом. Отклонено: начинать новый
проект на предыдущем мажоре означает запланировать миграцию на ближайшие месяцы.

**Новые зависимости и зачем.** `@prisma/adapter-pg` и `pg` — требование Prisma 7, без них
клиент не подключится. `@types/pg` — типы для строки подключения.

## 7. Отмена этапа требует комментария на любом этапе

**Дата:** 21.09.2026

Решение 4 в `CLAUDE.md` говорит про этап 5: «можно отменить с комментарием "не требуется"».
Про остальные этапы условие не задано.

**Решение.** Комментарий требуется при отмене **любого** этапа.

**Почему.** Отмена — необратимое для менеджера действие (переоткрыть может только ADMIN),
и оно попадает в историю. История без основания бесполезна.

**Что это ограничивает.** Фронт обязан запрашивать комментарий в диалоге отмены, иначе
получит `VALIDATION_ERROR` 422.

## 10. Рейтинг считается в приложении, а не в СУБД

**Дата:** 21.09.2026

Концепция обещает «аналитические показатели рассчитываются представлениями и агрегирующими
запросами на стороне СУБД».

**Решение.** На MVP рейтинг и skill gap считаются в `src/modules/analytics/rating.ts` и
`src/modules/skills/skills.rules.ts` — чистыми функциями, покрытыми тестами.

**Почему.** Формулы ещё не утверждены (все веса помечены TEMP). Менять коэффициент в конфиге
дешевле, чем переписывать представление и миграцию. Чистые функции проверяются тестами
без поднятия базы.

**Когда пересмотреть.** При росте объёма данных расчёт переносится в представления PostgreSQL
без изменения контракта API. Обсудить с Тиграном.

## 11. Нормирование внутри выборки

**Дата:** 21.09.2026

**Решение.** Рейтинг нормируется внутри выборки ответа; спрос на навыки — по всей выборке
периода, а не по отфильтрованной странице.

**Почему.** Для спроса иначе масштаб зависел бы от фильтров и значения нельзя было бы
сравнивать между запросами.

**Что это ограничивает.** Баллы рейтинга сравнимы только внутри одного ответа. Это написано
в поле `explanation` каждой записи, фронт обязан это показывать.

## 12. Мягкое удаление вместо физического

**Дата:** 21.09.2026

**Решение.** Вузы и программы архивируются (`archived_at`), связи на них — `RESTRICT`.
Архивировать вуз с незакрытыми связками нельзя — `CONFLICT` 409.

**Почему.** Сотрудничество длится годами, история — основная ценность системы.

## 15. Пустое тело PATCH отклоняется

**Дата:** 21.09.2026

При реализации обнаружено: `.partial()` в Zod **не снимает** `.default()`. Схема изменения,
построенная из схемы создания, на пустом теле возвращала `{ status: "NEW" }` и молча меняла
статус записи.

**Решение.** Для вузов, программ и связок заведены отдельные наборы полей без значений
по умолчанию. Схема создания добавляет `.default()` поверх, схема изменения строится из чистой
базы. Поведение закреплено тестами в `universities.test.ts`, `programs.test.ts`,
`cooperation.test.ts`.

## 16. Сортировка с `nulls: 'last'` только для nullable-полей

**Дата:** 21.09.2026

При прогоне сквозного сценария выяснилось: Prisma отклоняет `orderBy: { field: { sort, nulls } }`
для полей, которые не могут быть NULL. Список связок падал с 500.

**Решение.** В `shared/http/pagination.ts` добавлен `buildOrderBy(sort, nullableFields)`.
Каждый репозиторий перечисляет свои nullable-поля: показатели набора у программ, контрольные
даты у связок. В сквозной сценарий добавлены проверки сортировки по обоим видам полей.

## 20. Застой связки считается по любому незакрытому этапу

**Дата:** 21.09.2026

Первая версия правила `cooperation.stalled` срабатывала только на этапе в статусе
`NOT_STARTED`. На демонстрационных данных оно не сработало ни разу: связка, которая месяц
висит на начатом этапе, под правило не попадала.

**Решение.** Правило смотрит на любой незакрытый текущий этап и подбирает формулировку под
его статус. Застой на заблокированном этапе получает повышенный приоритет: блокировка,
которую месяц никто не снимает, — не рабочее состояние.

## 21. Просрочка и застой по одной связке не дублируются

**Дата:** 21.09.2026

**Решение.** Если по связке уже сформирована рекомендация о просроченном этапе, рекомендация
о застое не создаётся.

**Почему.** Это две карточки об одной проблеме. Список приоритетных действий должен отвечать
на вопрос «чем заняться», а не показывать одну связку дважды.

## 22. Демонстрационные заявки согласованы с показателем

**Дата:** 21.09.2026

При проверке кабинета вуза выяснилось: `applicationCount` в демо-данных проставлялся вручную
и не совпадал с суммой записей в `applications`. Первая же поданная заявка запускала пересчёт,
и показатель на глазах менялся с 420 на 120.

**Решение.** Seed создаёт заявки ровно на то количество, которое стоит в показателе, и в конце
сверяет сумму. Расхождение роняет загрузку данных с явной ошибкой.

**Почему.** Решение 9 объявляет заявки источником истины для `applicationCount`. Набор данных,
который этому противоречит, ломает демонстрацию в самый неудобный момент.

## 23. `next typegen` перед проверкой типов

**Дата:** 21.09.2026

Next.js генерирует типы маршрутов в `.next/types`, и `tsc` их проверяет. Пока сгенерированные
типы не обновлены, новые маршруты дают ложные ошибки, а ошибки в старых — не видны.

**Решение.** `npm run typecheck` выполняет `next typegen && tsc --noEmit`.

## 25. Добавлен модуль `audit`

**Дата:** 21.09.2026

`CLAUDE.md` перечисляет `AuditLog` среди сущностей, но модуля для него не задаёт.

**Решение.** Заведён `src/modules/audit` с двумя разными ответами на два разных вопроса:
`GET /api/audit` — технический журнал для администратора, `GET /api/universities/:id/events` —

**Что это ограничивает.** Лента показывает только то, что оставляет след в доменных
таблицах. Действия без такого следа (например, правка описания вуза) в неё не попадут.

## 26. NextAuth.js версии 5 (beta) вместо стабильной четвёртой

**Дата:** 21.09.2026

Концепция обещает «аутентификация и сессии через NextAuth.js на токенах JWT». Стабильная
линия next-auth 4 рассчитана на Pages Router; с App Router работает версия 5, которая пока
в статусе beta.

**Решение.** Взята `next-auth@5.0.0-beta.32`, версия зафиксирована точно — без диапазона.

**Почему это приемлемо.** Весь доступ к пользователю идёт через единственную функцию
`getCurrentUser()`. Если бета подведёт, её реализация меняется в одном файле, а модули
не трогаются — ровно то, ради чего решение 9 и вводило эту функцию.

**Новые зависимости и зачем.** `next-auth` — обещано концепцией. `bcryptjs` — хеширование
паролей; выбран вместо `bcrypt`, потому что не требует нативной сборки и одинаково ставится
на машинах команды.

## 27. Демо-режим входа остаётся, но выключается переменной

**Дата:** 21.09.2026

Решение 9 предполагает, что на P1 mock-авторизация просто исчезает. На защите проекта
переключение ролей в один клик — половина демонстрации: кабинет вуза, права аналитика,
скрытые комментарии показываются именно так.

**Решение.** Настоящий вход по паролю работает всегда. Дополнительно, пока включён
`DEMO_AUTH_ENABLED`, действует переключение пользователя cookie `skilllink_user`.
По умолчанию режим выключен только в продакшене.

**Что это ограничивает.** Включённый демо-режим — это обход авторизации. Настоящая сессия
имеет приоритет над cookie, но сам режим в промышленном контуре держать нельзя. Записано
отдельной строкой в [SECURITY_LIMITATIONS.md](SECURITY_LIMITATIONS.md).

## 28. Текущий пользователь переехал с `/api/auth/me` на `/api/me`

**Дата:** 21.09.2026

NextAuth занимает всё пространство `/api/auth/*` перехватывающим маршрутом.

**Решение.** Собственный эндпоинт текущего пользователя перенесён на `/api/me`.

**Почему сразу.** Статический сегмент в Next перекрывает перехватывающий, так что технически
соседство работало бы. Но держать свой маршрут внутри чужого пространства имён — это мина
на будущее. Фронт к эндпоинту ещё не подключался, поэтому переезд ничего не ломает.

**Затрагивает фронт:** `GET /api/auth/me` → `GET /api/me`.

## 29. Клиент Prisma создаётся лениво

**Дата:** 21.09.2026

Клиент создавался прямо при импорте модуля и падал без `DATABASE_URL`. Из-за этого
юнит-тест чистой функции падал, если в её файле был хоть один транзитивный импорт,
ведущий к базе.

**Решение.** `prisma` — прокси, который создаёт клиент при первом обращении к свойству.
Методы привязываются к экземпляру, поведение для вызывающего кода не меняется.

**Почему это важнее удобства.** Модуль, который падает на импорте, делает нетестируемым
всё, что его касается. Проблема всплыла на первом же тесте настроек авторизации.

## 30. Текст документа хранится, а файл — нет

**Дата:** 21.09.2026

Концепция обещает «генерацию пакета документов из шаблонов с автоподстановкой реквизитов».
Решение 14 при этом ограничивает документы метаданными и ссылкой.

**Решение.** В таблицу `documents` добавлены `content` (собранный текст) и `template_key`.
Файлы по-прежнему не хранятся и не загружаются — это остаётся P2.

**Почему.** Без хранения текста генерация не оставляет после себя ничего: пользователь
увидел бы документ один раз в ответе и потерял его. Текст — это не файл, и ограничение
решения 14 он не нарушает.

**Изменение схемы:** миграция `20260921082617_document_template_content`.

## 33. Спецификация OpenAPI собирается из Zod-схем

**Дата:** 21.09.2026

Концепция обещает: «интеграционные интерфейсы описаны по спецификации OpenAPI».

**Решение.** Реестр эндпоинтов в `src/shared/openapi/registry.ts` ссылается на те же

## 36. За прокси с HTTPS задаётся `AUTH_URL`

**Дата:** 22.09.2026

**Что нашлось.** Вход через имитацию HTTPS-прокси (заголовки `Host`, `X-Forwarded-Proto`,
`X-Forwarded-Host` как у Caddy) проходил, cookie получали приставку `__Secure-`,
но после входа NextAuth отправлял пользователя на **`https://localhost:3100`**.

Причина в Next.js: при `next start` он собирает адрес запроса из собственного имени
(`localhost:порт`), а заголовок `Host` не использует. NextAuth строит все переходы
от этого адреса. Протокол при этом берётся из `X-Forwarded-Proto` — поэтому снаружи
всё выглядело почти правильно.

**Решение.** Публичный адрес задаётся переменной `AUTH_URL` — её читает сам next-auth.
В контейнере — через `DOCKER_AUTH_URL`, по той же причине, что и `DOCKER_AUTH_SECRET`.
Пустое значение безопасно: next-auth считает его незаданным (проверено запуском).

**Проверено:** без `AUTH_URL` — переход на `localhost`; с ним — на адрес сайта.
Сессия видна и снаружи через прокси, и изнутри сервера (`apiFetch` ходит
на `127.0.0.1` без заголовков прокси) — в обоих случаях.

**Попутно исправлено.** README и HANDOFF велели `export AUTH_SECRET=...` перед
`docker compose`, а контейнер с прошлого исправления читает `DOCKER_AUTH_SECRET`:
по инструкции секрет в контейнер не попадал. Теперь это ловит тест
`src/shared/config/compose-docs.test.ts`.

## 37. Уведомления собираются из данных, прочитанность хранит фронт

**Дата:** 22.09.2026

Дизайн-система ставит колокольчик с лентой в шапку каждой страницы. Уведомления
были P2 с невыбранным каналом — дизайн выбрал его сам: лента в интерфейсе.
**Одобрено Артуром 22.09.2026** (`DECISIONS.md`, решение 14).

**Решение.** `GET /api/notifications` собирает ленту на лету: сроки своих этапов,
изменения других людей в своих связках и документах, открытые рекомендации высокого
приоритета. Представителю вуза — только движение по его вузу.

**Почему без таблицы уведомлений.** Лента из данных не расходится с ними: закрытый
этап перестаёт быть «просроченным» и в ленте. Таблица требовала бы изменения схемы,
согласования с Тиграном и фоновой рассылки — за неделю до защиты.

**Прочитанность — на фронте**: время последнего просмотра в `localStorage`,
передаётся в `since`. Ограничение честное: на другом устройстве лента снова
непрочитанная. Нужна общая — это одна колонка `users.notifications_seen_at`.

**Время события — когда оно случилось**, а не когда посчитано: иначе просрочка
выглядела бы новой при каждом запросе, и «отметить прочитанным» не работало бы.

**Проверено:** просроченных в ленте столько же, сколько в личной статистике;
каждая ссылка открывается тем, кому пришло уведомление (контрольный опыт: подмена
id — пробник поймал 5 из 20); в ленте представителя вуза нет внутреннего.

Новая пометка TEMP: `NOTIFICATION_WINDOW_DAYS = 14` — за сколько дней показываются
изменения других людей.

## 40. Исчерпанные попытки входа называют себя

**Дата:** 22.09.2026

Было: после пяти неудач подряд учётная запись закрывалась на 15 минут, а отказ выглядел
ровно как «неверный пароль». Человек вводил правильный пароль, получал отказ и решал,
что забыл его. На защите это 15 минут растерянности при переключении на представителя вуза.

Одинаковый ответ был выбран сознательно — чтобы по нему нельзя было узнать, какие
адреса заблокированы. Пересмотрено: блокируется и несуществующий адрес, поэтому код
не выдаёт, есть ли учётная запись; а тот, кто исчерпал попытки, и так знает об этом.

**Решение.** Код `too_many_attempts` в ответе входа (`CredentialsSignin` с собственным
`code`). «Нет пользователя» и «неверный пароль» по-прежнему неразличимы.

**Проверено** на живом сервере: пять неудач по несуществующему адресу — `credentials`,
шестая — `too_many_attempts`; обычная ошибка пароля — `credentials`; верный пароль входит
и обнуляет счётчик. Проверка осталась в пробнике.

**Затрагивает фронт:** экран входа должен различать два кода — `API_CONTRACT.md`, «Вход».

## 41. Интерфейс собран в том же приложении

**Дата:** 22.09.2026

Фронт по плану делали Ваня и Серёжа, и правило «их вёрстку не переделывать» стояло
в CLAUDE.md с самого начала. К 22 сентября от них не было ни одного коммита: у одного
не получалось подключить рабочий инструмент. Артур попросил собрать интерфейс здесь,
передав дизайн-систему из шести документов. Дедлайн — вечер 29-го, и ждать дальше
значило прийти на защиту с одним API.

**Решение.** Интерфейс живёт в этом же приложении Next.js, а не отдельным проектом:

- `src/ui/` — дизайн-система: примитивы, таблица, состояния, всплывающие окна, каркас,
  поиск, уведомления, хуки и обращения к API. Страницы берут всё оттуда и своих кнопок,
  карточек и таблиц не заводят.
- `src/app/(app)/` — внутренние страницы внутри общего каркаса;
  `src/app/(auth)/login` — вход.
- Оформление — переменные в `src/app/globals.css` плюс CSS Modules. Никакого Tailwind
  и никаких UI-библиотек: значения дизайн-системы заданы точно (цвета, радиусы, размеры
  шрифта), и слой утилит между ними и разметкой ничего не добавляет, зато добавляет
  зависимость и конфигурацию, которую потом некому поддерживать.
- Иконки — свой набор линейных значков в `src/ui/primitives/Icon.tsx`. Библиотека икон
  ради двадцати начертаний — лишняя зависимость (CLAUDE.md).
- Данные — только через API теми же маршрутами, что описаны в контракте. Прямых обращений
  к сервисам и Prisma из страниц нет: фронт остаётся отделяемым.

**Почему не отдельный проект.** Отдельный фронт — это второй репозиторий, вторая сборка,
CORS, свои переменные окружения и своя выкладка. За неделю до защиты это цена без выгоды:
страница и эндпоинт, который её кормит, проверяются одной командой и выкатываются одним
образом.

**Что это меняет в правилах.** Пункт «не переделывать вёрстку фронта» остаётся в силе
для чужого кода: если Ваня и Серёжа принесут свои экраны, они встают рядом и
переписываться не будут. Дизайн-система при этом общая — она из их документов.

**Проверка.** `npm run typecheck`, `npm test` (тесты меню и форматирования — новые),
`npm run build` и живой проход по экранам в браузере.

## 42. Страницы проверяют сессию куки, а права — сервер

**Дата:** 22.09.2026

`middleware.ts` отправляет на `/login` того, у кого нет куки сессии. Подпись токена
при этом не проверяется: middleware выполняется в edge-среде, где нет ни bcrypt,
ни Prisma, и полноценная проверка потребовала бы отдельной сборки конфигурации входа.

Это не ослабляет защиту: страницы не содержат данных — всё приходит запросами к API,
где каждый маршрут проверяет сессию и права по-настоящему. С подделанной кукой
откроется пустой каркас, который тут же получит 401 и вернёт на вход.

Маршруты `/api/**` из middleware исключены намеренно: они обязаны отвечать кодом 401,
а не перенаправлением на HTML-страницу, иначе любой запрос из интерфейса ломается.

## 43. Страницы не кэшируются браузером без проверки

**Дата:** 23.09.2026

Сергей открыл стенд после выкладки интерфейса и увидел старую заглушку
«SkillLink API». Браузер был ни при чём: Next отдаёт готовые страницы
с `Cache-Control: s-maxage=31536000`. Этот заголовок адресован промежуточным
кэшам, но браузер, не найдя `max-age`, выбирает срок хранения сам — Safari
выбрал «долго» и показывал страницу, которой в приложении уже нет.

На защите это стоило бы показа: у всех, кто открывал стенд раньше, осталась бы
старая версия, и никакая выкладка этого бы не изменила.

**Решение.** Страницы и ответы API отдаются с `Cache-Control: no-cache`:
браузер обязан спросить сервер перед показом, а при совпадении ETag получает
пустой ответ 304. Файлы сборки под `/_next/static` кэшируются навсегда — у них
хеш в имени. Правило задано дважды: в `next.config.ts` (чтобы локальный запуск
вёл себя так же) и в Caddyfile стенда (последнее слово за прокси).

**Проверка.** `scripts/deploy/check.sh` смотрит этот заголовок и падает, если
страницы снова начнут кэшироваться без проверки. Проверка написана до
исправления и на тогдашнем стенде падала — это и был тот самый заголовок.

**Что это не чинит.** Копию, уже сохранённую браузером, заголовок не отменяет:
её нужно один раз обновить с очисткой кэша. Предупреждение добавлено
в `DEMO.md`, пункт подготовки.

## 44. Плотность реестров и первый экран главной — по решению Артура

**Дата:** 23.09.2026

Артур решил два продуктовых вопроса: реестр должен выглядеть рабочим инструментом
(20–25 строк на экран), а главная — отвечать «где горит» (проблемы — главный блок,
показатели — одной строкой).

**Плотность.** Строка таблицы — 32 пикселя, содержимое в одну строку: длинное
обрезается многоточием, полное — в подсказке (`CellText`). Раскладка столбцов
фиксированная: иначе запрет переноса растягивал столбец с длинным названием
и выталкивал остальные за край. Подписи над фильтрами скрыты визуально
и оставлены для программ чтения с экрана — их смысл и так читается из подсказки
внутри поля. Итог на 1440×900: 20 строк реестра на экране, на Full HD — 25.

Для этого в ответы API добавлены краткие названия вузов (`universityShortName`
у связок, программ и проблемных связок): полное название в плотной строке
обрезалось на первом слове.

**Главная.** Пять плиток заменены полосой показателей (`KpiStrip`), под ней —
«Требует внимания» на три пятых ширины и приоритетные действия рядом. Строка
проблемы ведёт сразу на этап (`stageId`).

**Найдено по дороге — две неправды на первом экране.**

1. Подпись «5 связок встали» выдавала лимит вывода за число проблем: в демо-наборе
   проблемных этапов двенадцать. Теперь сводка отдаёт `problemStageTotal`,
   главная пишет «12 этапов стоят… показаны 10 самых давних», а пробник сверяет
   это число со списками просроченных и заблокированных этапов (обратный
   эксперимент: сдвиг счётчика на единицу ловится).
2. В реестре связок у текущего этапа значок «просрочен на N дн.» подставлял дни
   до контрольной даты всей связки. У СПбГУТ «Программная инженерия» выходило
   «74 дня» вместо настоящих 58. У текущего этапа теперь свой `daysToDeadline`.

## 47. Дни — по московскому календарю; в день срока — «сегодня»

**Дата:** 23.09.2026

## 48. Устаревшая сессия ведёт на вход, а не в пустой экран

**Дата:** 23.09.2026

**Что было.** Middleware проверяет только наличие cookie сессии и вошедшего
со страницы входа отправляет на главную. Когда cookie остался, а пользователя
за ним нет, главная получала 401 и уводила на `/login`, middleware возвращал
на главную — экран оставался пустым. Войти было нельзя, пока не почистишь
cookie. Так случилось бы утром перед защитой: перезаливка демо-данных создаёт
пользователей заново, и у каждого, кто входил накануне, стенд открылся бы
пустым. Тот же тупик ждал отключённого администратором пользователя.

Локально не воспроизводилось: в режиме разработки включён демо-вход,
и сервер молча подставлял менеджера вместо пропавшего пользователя. Найдено
на боевой сборке с `DEMO_AUTH_ENABLED=false`, как на стенде.

**Что сделано.**

- На 401 `useResource` и `useMutation` вызывают `leaveToLogin()`: снимают сессию
  (`signOut`) и полным переходом открывают `/login?reauth=1&from=<где был>`.
  Действие без сессии тоже уводит на вход: отказ «Требуется вход» в карточке
  этапа читался бы как отказ системы.
- Middleware пропускает `/login?reauth=1` и с cookie — на случай, если снять
  сессию не удалось. Имя параметра — `src/shared/auth/reauth.ts`, общее
  для middleware и клиента.
- Страница входа пишет «Сессия устарела — войдите снова», после входа
  возвращает туда, где человек был.

**Проверено.** Боевая сборка на демо-базе, демо-вход выключен: вкладка вошла,
демо-данные перезалиты, открытие реестра привело на вход с подсказкой, вход
вернул в реестр; нажатие «Начать этап» на открытой до перезаливки карточке
привело на вход, а не к ошибке в карточке. Пробник проверяет, что вход
с `reauth` открывается при старом cookie (обратный эксперимент: без исключения
в middleware — 307), `check.sh` — то же на стенде.

**Попутно.** Сквозной сценарий проверял сработавшие правила рекомендаций
по первой странице в 50 строк. На рабочей базе, где записи копятся от прогонов,
нужная уехала на 53-е место, и проверка падала без ошибки в приложении. Теперь
сценарий читает все страницы, а «повторная генерация не плодит дубликаты»
сравнивает общее число, а не длину страницы, которая при сотне записей
одинакова всегда.

## 52. Пределы базы — на входе API, а не в тексте внутренней ошибки

**Дата:** 23.09.2026

Проверка входа знала смысл полей, но не типы колонок. Всё, что проходило Zod
и не помещалось в PostgreSQL, доходило до запроса и отвечало 500 «Внутренняя
ошибка сервера». Нашлось обстрелом API на локальном сервере: мусор в каждый
параметр, путь и тело каждого маршрута.

- **Символ с кодом 0** (`%00`, `\u0000`) PostgreSQL не принимает ни в записи,
  ни в поиске. Давал 500 на двадцати адресах API: поиск `q` в девяти списках, карточки по `id`,
  создание и правку, загрузку CSV, cookie демо-входа; вход по паролю отвечал
  «ошибка конфигурации». Теперь он останавливается там же, где проверяется
  остальное: `parseBody`, `parseOptionalBody`, `parseQuery` — `VALIDATION_ERROR`
  с именем поля; параметры пути — в общей обёртке `handle`, ответ «не найдено»
  (такого идентификатора быть не может); в CSV — «Файл не похож на текстовый CSV»:
  нулевые байты бывают только в двоичных файлах, и .xlsx раньше получал
  «не найдены колонки» при колонках на месте.
- **Количества.** `z.number().int()` пропускает целые до 2^53, колонка `Int` —
  до 2 147 483 647: «Студентов: 99 999 999 999» падало на записи. Количества
  идут через `countSchema()` из `shared/zod`, импорт проверяет тот же предел —
  раньше предпросмотр обещал «Будет создан», а запись падала. `minDaysOverdue`
  без границы давал несуществующую дату — теперь не больше 36 500.
- **Текст ошибки базы уходил наружу.** Импорт писал в `detail` строки сообщение
  Prisma целиком — с вызовом и данными. Теперь наружу — только то, что отдаёт
  общая `toAppError` (её же использует `handle`), остальное — «внутренняя ошибка».
- **Персональные данные в журнале.** Обработчик писал в журнал `error.message`,
  а у Prisma это весь вызов с аргументами: при сбое записи контакта в журнал
  попали бы ФИО, телефон и почта. `describeForLog` оставляет имя ошибки, код
  и последнюю строку — причину. Так же пишет журнал аудита.

Сторож в `storable.test.ts`: целое без `.max()` в схемах модулей роняет тесты.
Контрольный опыт — без исправления падают 8 тестов из 48.

## 53. Вход и границы запроса: возврат, перебор, размер тела

**Дата:** 23.09.2026

Нашлось сквозной проверкой кода по четырём направлениям; каждое место
воспроизведено до исправления.

- **Возврат после входа уводил на чужой сайт.** `from` проверялся условием
  «начинается с `/`», а `//evil.example` и `/\evil.example` браузер читает как
  адрес другого сайта. Ссылка `/login?reauth=1&from=//evil.example` открывала
  вход даже вошедшему — с надписью «Сессия устарела» — и после ввода настоящего
  пароля переводила на чужую страницу. Теперь `safeReturnPath` разбирает адрес
  тем же парсером URL, что и браузер, и пропускает только свой сайт.
- **Ограничение перебора обходилось параллельными запросами.** Неудача
  записывалась после запроса к базе и bcrypt (~50 мс), и все одновременные
  попытки проходили проверку блокировки раньше, чем первая успевала записаться.
  `throttledAttempt` засчитывает попытку сразу после проверки, без `await`
  между ними; удачный вход обнуляет счётчик. Тест: сто одновременных догадок —
  проверяется пять (без исправления — сто).
- **Тело запроса читалось целиком.** `request.json()`, `.text()`, `.arrayBuffer()`
  не знают предела, а проверка длины по заголовку при передаче chunked не
  срабатывает: наблюдатель мог прислать на импорт гигабайты, и процесс держал
  их в памяти до проверки прав. `readBodyBytes` читает поток кусками и обрывает
  на пределе; через него идут `parseBody`, `parseOptionalBody` и импорт; права
  на импорт — до чтения файла.
- **Причина отклонения документа уходила представителю вуза.** В истории этапов
  и в ленте событий комментарии для этой роли скрыты (решение 9), а карточка
  документа их отдавала. Сборщик карточки теперь требует пользователя — ни один
  путь к ней не может забыть о правиле. Раздел пробника.
- **Кнопка входа зависала при обрыве сети**: `signIn` в этом случае бросает
  исключение, и ожидание не снималось. Теперь — сообщение «Сервер не ответил».

## 55. Этапы связки: проверяется итог записи, изменения — по очереди

**Дата:** 23.09.2026

- **Завершённый этап терял результат, заблокированный — причину** (решение 4).
  Правила перехода проверяли запрос, а записывался этап, собранный из запроса
  и сохранённых полей. `{"status":"COMPLETED","result":"   "}` проходило
  проверку по сохранённому результату и записывало пустой; `{"result":null}`
  у завершённого не проверялось вовсе — правка полей без смены статуса правил
  не касалась; `{"blockingReason":""}` у заблокированного оставляло его без
  причины. Теперь итог собирается один раз (`resolveStageFields`), проверяется
  (`assertStageFieldsComplete`) и он же записывается. Завершение с пустым
  результатом в теле берёт сохранённый — как обещает контракт.
- **Изменения этапов одной связки шли без очереди.** Проверки — вне транзакции,
  транзакция ничего не блокировала. Тринадцать одновременных закрытий этапов 1–13
  оставляли этап 14 «в работе» — три раза из трёх; снятие обязательного пункта
  одновременно с завершением давало завершённый этап с открытым пунктом.
  `lockCooperation` берёт строку связки `FOR UPDATE` в начале каждой транзакции,
  меняющей этапы (смена статуса, отметка пункта, выпуск версии продукта); то, что
  могли изменить соседи, — контрольная точка и чек-лист — проверяется ещё раз
  под блокировкой. Раздел пробника с контрольным опытом.
- **Повторная отметка пункта переписывала, кто его отметил**: подтверждение
  представителя вуза переходило к менеджеру на устаревшей странице. Повтор
  ничего не меняет.
- **Правило этапа 14 было в трёх местах**: в сервисе, в выпуске версии продукта
  и в демонстрационном наборе. Копия в наборе считала по номеру последнего
  закрытого этапа, и у связки УрФУ «Компьютерная безопасность» с начатым этапом 1
  этап 14 значился «Не начат». Теперь одно правило (`computeControlStatus`)
  и один пересчёт (`recomputeControlStage` в `workflow.repo`). Числа показа
  не меняются: сверка со сценарием на новом наборе — 25 из 25.

## 56. Рекомендации: вернувшаяся проблема снова открыта, застой — по движению этапов

**Дата:** 23.09.2026

- **«Связка без движения» смотрела на запись связки.** Смена статуса этапа

## 60. Рейтинг и дефициты: действующая программа, спрос по навыку, период по календарю

**Дата:** 23.09.2026

- **Навык с несколькими замерами спроса считался несколько раз.** Замеров на навык

  строке: навык дважды в списке, покрытие на главной с двойным счётом, две
  рекомендации с одним ключом затирали друг друга. Теперь одна строка на навык

  главная и кабинет — нет. Одно определение — `ACTIVE_COOPERATION_STATUSES`.

## 63. Визуальное направление 07: графит, сигналы вместо материала

**Дата:** 23.09.2026

Серёжа прислал `docs/design/07_Human_Crafted_Override.md` — документ с высшим
приоритетом над 01–06 — и бриф к нему. Главная претензия: интерфейс выглядит
сгенерированным — одинаковые тёмные карточки с фиолетовой рамкой, градиент на
каждой кнопке, свечение, иконки в квадратиках. Переделка идёт в порядке,
который задаёт сам документ (раздел 39): убрать шум → выстроить иерархию →
главная → фирменные элементы → движение.

**Шаг 1 (этот).** Токены `globals.css`: холст и три уровня графита (L0–L3),
акценты фиолетовый/розовый/оранжевый/бирюзовый — только как сигналы, текст
тёплого белого, линии белого с малой прозрачностью. Свечения погашены
(имена токенов оставлены, чтобы страницы не ломались), градиент — один
фирменный `--gradient-brand` для редких мест. Радиусы по разделу 14.
Кнопки: основная — светлая сплошная, акцентная (`variant="accent"`) —
фиолетовая, для одного продуктового действия на экран; вторичная — прозрачная
с тонкой линией; «призрачная» — без контейнера до наведения. Карточки —
без рамки и тени, отделяются тоном. Боковое меню — тонкая вертикальная метка
у текущего пункта, наведение — сдвиг на 3px. Таблица — редакционный список:
наведение — лёгкий фон и сдвиг содержимого на 4px, сетка не двигается.
Фиолетовые значения в модулях стилей переведены в графит правилом
по свойству (рамка → линия, подложка → графит, свечение → убрано).

**Что взято не буквально — потому что данных нет, а выдумывать их нельзя
(CLAUDE.md, «Данные»):** «время до найма» остаётся «временем до начала
занятий» — данных о найме в системе нет; «компания» в схеме связей —
ИТ-Школа РТК, других компаний в модели нет; «рекомендуемые программы
с баллом совпадения и причинами» — это рейтинг программ с его настоящим
баллом и вкладами показателей.

**Шаг 2 — главная (раздел 10 документа 07).** Пять плиток показателей заменены
на Live Rail: числа — типографикой в одну строку, под ними маршрут из четырнадцати
этапов с засечками и фазами, на нём — связки в работе точками на своём текущем
этапе, подписанные вузом; застрявшие (просрочка или блокировка) — красные и
получают один импульс при появлении. Внизу блока — «N этапов требуют внимания»
и время обновления. «Требует внимания» — лента событий на линии времени с записью
этапа «06 / 14», а не таблица в рамке; «Приоритетные действия» — строки; «Связки
в работе» — строки-маршруты «вуз ── программа ── продукт · 06 / 14», звенья
включаются фирменным градиентом при наведении; «Ключевые программы» — ранжированные
строки: номер, вуз, программа, из чего сложился балл, балл. Появление — одна
композиция: числа → линия дорисовывается → точки → импульс → группы ниже; после
этого всё неподвижно. Показатели, текст сводки и блоки шпаргалки — прежние;
в ответ сводки добавлено краткое имя вуза у ключевых программ.

**Шаг 3 — фирменные элементы карточки связки (разделы 7, 8, 30).** Схема связки —
Collaboration Link Map: «Компания ── Вуз ── Программа ── IT-продукт» типографикой,
без иконок в квадратах; компания — ИТ-Школа РТК (другой в модели нет). Звенья
дорисовываются по очереди, по цепочке проходит один импульс фирменного градиента;
наведение на узел подсвечивает соседей и звенья к ним, остальное приглушает.
От цепочки — ветка к текущему этапу «06 / 14 · название», красная, если этап
просрочен или заблокирован. Лента этапов — 14-stage Depth Rail: перспектива
с точкой схода у текущего этапа, каждый этап сдвинут по оси Z на расстояние от
него — пройденные уходят назад и тише, будущие дальше, проблемные не гаснут;
у текущего — светлый номер и короткая фирменная линия, над лентой — «Текущий
этап 06 / 14». Замки контрольных точек, цвета статусов и щелчок по номеру —
прежние: на них опирается шаг 3 показа.

**Шаг 4 — движение и остатки шума (разделы 5, 9, 17, 18, 23, 24, 29).**
- *Строка реестра → карточка* (`ui/lib/morph.ts`): по щелчку название объекта
  отделяется от строки копией, остальные строки приглушаются; когда карточка
  отрисовала заголовок, копия переезжает на его место и масштабируется, заголовок
  проявляется. Копия, а не общий элемент двух страниц: страницы Next монтируются
  заново, а карточке бывает нужно время на загрузку — название ждёт на месте.
  Не дождалось за полторы секунды — исчезает. Работает во всех реестрах через
  общую таблицу и шапку страницы; при «уменьшить движение» выключено.
- *Поиск*: окно вырастает из кнопки — стартует с её места и формы и
  разворачивается, содержимое проявляется следом.
- *Уведомления*: открытие вниз от колокольчика — сдвиг, прозрачность, масштаб
  0,985 → 1; строки по очереди с шагом 30 мс.
- *Вход*: слева — схема «Вуз ── Программа ── IT-продукт» и маршрут из 14 засечек
  вместо трёх пунктов с иконками; появление — холст, знак, схема дорисовывается,
  панель выходит справа, поля по очереди. После входа форма гаснет, панель
  раскрывается в холст, схема уходит вправо — и через 420 мс открывается главная;
  меню и шапка при первом открытии после входа дописывают сцену (`arrival.ts`).
- *Шум*: знак SkillLink без квадрата-подложки и градиентной обводки; аббревиатуры
  вузов и программ без неоновой рамки; у пустых состояний нет декоративной плитки
  со значком — они говорят текстом.

## 72. Вход — «варп в систему»: из созвездия в сайт

**Дата:** 24.09.2026

После «Войти» сцена входа (решение 71) переходит в сайт одним движением, ~1,5 с:
1. скопления «вузы» и «IT-компании» летят навстречу и сливаются в центре — связь;
2. камера ныряет сквозь ядро, звёзды растут и летят навстречу, фиолетовая вспышка;
3. из вспышки проступает сайт: рабочая область выплывает из глубины и выпрямляется

   и шапка — как раньше (решение 63).

Экран входа уходит через 420 мс (время перехода не менялось), поэтому на время
прыжка холст переносится в `body` поверх сайта и доигрывает над ним, затем гаснет
и сам освобождает ресурсы. Во скрытой вкладке прыжок всё равно доигрывает — иначе
холст остался бы висеть. При «уменьшить движение» прыжка нет, вход прежний.

меткой `ARRIVAL_KEY`; настоящий вход с паролем при проверке не выполнялся.

браузер (загрузка кода и сборка главной) — звёзды замирали. Теперь: главная
предзагружается сразу после проверки пароля (`router.prefetch`); с прыжком страница
меняется под пиком вспышки (`WARP_NAVIGATE_MS`, форма узнаёт о прыжке по
`body[data-warp=ready]`), без прыжка — через 420 мс, как раньше; в прыжке
плотность пикселей холста — 1, звёзды растут втрое, а не вшестеро; холст
и вспышка — отдельными слоями (`will-change: opacity`). Боевая сборка, чистый
кэш, настоящий клиентский переход: 6 прогонов, ни одного кадра длиннее 34 мс.

это ведёт видеокарта, и движение идёт плавно, даже пока главный поток собирает
страницу. Лист лежит под шапкой и меню. Во скрытой вкладке анимации стоят, поэтому
лист снимается ещё и по таймеру.

друг друга: тёмный «билет на курс» (`programs/ProgramTag.tsx`) — цветная полоса

Программ больше, чем вузов, но в карусели одновременно не больше 13 бирок, остальные

Промежуточная полноэкранная карточка вуза (по мотивам Melius) была сделана и убрана

## 75. Вход: звёзды во весь экран и сборка сайта по частям в 3D

**Дата:** 24.09.2026

Уточняет решение 72. Жалобы: звёзды собирались «в отдельном квадрате», переход на

от левого края (rotateY), шапка откидывается сверху (rotateX), блоки страницы по
очереди подлетают из глубины с наклоном. На главной части помечены `data-assemble`:
«Требует внимания» и «Связки в работе» прилетают слева, «Приоритетные действия»
и «Ключевые программы» — справа, воронка — по центру. Только transform и opacity.
Метку `.arrival` каркас снимает через 4 с — дальше страницы приходят обычным

ту же сцену на странице, как раньше. Новых зависимостей нет.

## 76. Звёзды собирают главную по частям

**Дата:** 24.09.2026

Уточняет решение 75. Просьба: конец входа подтормаживал; звёзды, собравшиеся в ядро,
должны сами собрать главную по частям, в движении.

**Сборка.** Звёзды закручиваются в ядро (0,9 с) и не замирают — кружат в нём, пока
открывается сайт. Экран входа (`login/Constellation.tsx`) после перехода ждёт
страницу: каркас, шапку, блоки (заготовки — не дольше 0,7 с). Пока ждёт, части
скрыты (`body[data-star-assembly=pending]`). Затем меряет блоки по порядку — меню,
шапка, дальше сверху вниз — и передаёт сцене их прямоугольники: каждая звезда
вылетает из ядра к точке на контуре (три четверти) или внутри своего блока, по дуге
навстречу камере, со своей задержкой; блок проявляется из глубины (transform
и opacity, Web Animations), когда звёзды к нему почти долетели, а звёзды гаснут на
нём. Блоки главной со своей стороной (`data-assemble`) прилетают слева и справа.
То, что пришло позже (данные главной), собирается обычной сборкой каркаса
(`.arrival`, решение 75). Страница не пришла за 2,6 с — звёзды разлетаются мимо
камеры, как раньше.

**Подтормаживание.** Две причины: под шапкой с размытием 18 px летели блоки, и
размытие пересчитывалось каждый кадр; в разлёте звёзды раздувались в крупные
светящиеся точки во весь экран — лишняя заливка для видеокарты. На время сборки
размытие шапки выключено (сплошной фон), точки больше не раздуваются. Угасание
холста CSS-анимацией не нужно — звёзды гаснут сами; холст снимается по окончании.

**Переделка того же дня.** Пользователь увидел не сборку, а разлёт: на локальном
сервере главная после входа компилируется и грузит пользователя дольше 2,4 с,
и ядро отпускало звёзды. И «лагающий» конец воронки: в момент, когда звёзды
собрались, скорость вращения скачком менялась с нуля на большую, а все звёзды
сжимались в одну белую точку. Теперь:
- ядро — наклонный звёздный диск: у каждой звезды свой радиус и скорость
  (внутренние быстрее), вращение разгоняется плавно с начала прыжка — скорость
  нигде не прыгает, и видно, что диск движется;
- ядро ждёт главную до 10 с (`PAGE_WAIT_MS`), данные главной — до 1,5 с; пока
  ждёт, скрыта и загрузочная заготовка каркаса (`data-shell-loading`);
- звёзды собирают экран по одному блоку (шаг 150 мс): 90 % звёзд ложатся на контур
  блока, светятся на нём и мерцают, блок проявляется внутри контура, затем звёзды
  гаснут; меню во всю высоту не забирает себе больше звёзд, чем крупный блок;
- вспышки больше нет — страница под звёздами скрыта до сборки; сайт открывается
  раньше, на середине воронки (`WARP_NAVIGATE_MS` = 600 мс).

**След звёзд (дополнение).** Звёзды держались на контуре и гасли 0,9 с — дольше,
чем проявлялся блок, и их след висел поверх загруженной страницы; холст убирался
только по сообщению фонового потока. Теперь свечение на контуре 120 мс, угасание
160 мс, разброс вылета звёзд одного блока 60 мс; блок начинает проявляться за 100 мс
до прилёта звёзд и становится непрозрачным, когда они уже гаснут. Холст снимается
сразу, как доиграл последний блок.

**Холст под сайтом (дополнение).** Даже короткое угасание поверх готовых блоков
читалось как след. Холст прыжка теперь лежит не поверх сайта (z-index 1200), а под
его содержимым и над живым фоном (z-index −1, позже фона в документе): звёзды
прилетают на пустое место, где блок ещё скрыт, и проявившийся блок закрывает их
своей непрозрачной поверхностью — поверх содержимого звёзды не видны вовсе.

**След — настоящая причина (дополнение).** Прыжок впервые снят покадрово: Chrome без
окна, экран входа, вместо главной — подложенные меню, шапка и блоки (60 кадров/с,
без пауз). На кадрах след оказался тёмными точками: при обычном сложении погасшая
звезда (цвет — ноль) оставалась в холсте непрозрачной и закрывала фон под собой;
тот же эффект давал тёмный кружок в центре ядра. Теперь у каждой звезды неба
своя прозрачность (цвет — rgba): гаснущая звезда теряет и свет, и непрозрачность,
погасшая невидима. Сначала вместо этого материалы перестали писать непрозрачность
вовсе (только свет) — в Chrome без окна это работало, а обычный Chrome на Mac такие
пиксели холста не показывает, и 3D на экране входа пропал; откатено. Звёзды больше не ложатся на контур блока
(пунктир висел на прозрачных частях — заголовках колонок), а летят в блок струёй
через его центр, расходятся по нему и гаснут ровно к касанию; блок становится
непрозрачным к их прилёту. Диск ядра заполнен до центра.

**Запасной путь (дополнение).** Если фоновый поток не справлялся (нет WebGL

## 80. Два режима интерфейса: «Рабочий» и «Презентационный»

**Дата:** 25.09.2026

Наставник хакатона: SkillLink — рабочий инструмент аналитиков, лишний визуал ему
не нужен, на каждом экране сразу должно быть видно, где горит. Визуал дизайнера
(решения 70, 73, 79) при этом готов и нужен для показа. Удалять его не стали —
режим выбирает сам человек.

**Рабочий** (по умолчанию для всех ролей):
- реестры вузов и программ по умолчанию «Список», а не «Бирки»; выбор вида
  по-прежнему запоминается, и запомненный выбор главнее режима;
- на главной нет бегущей строки, колец «Здоровье портфеля» и карты вузов —
  «Требует внимания» и «Приоритетные действия» идут сразу за приветствием
  и полосой «Активно сейчас» (и появляются раньше); ленту событий и список вузов
  для карты главная в этом режиме не запрашивает;
- нет заставки, «рассыпки» букв приветствия, линейки прокрутки, импульсов
  и прорисовки проводов графа связей, «магнитных» кнопок, перекатывания букв
  в меню; живой фон неподвижен (дымка не дышит, свечение не ходит за курсором);
- счётчики, полосы, воронка, радар и бирки не анимируются — как при
  «уменьшить движение».

**Презентационный** — всё как было до этого решения.

**Механика.** Выбор — в `localStorage` (`skilllink.uiMode`, чтение и запись
в try/catch: приватное окно не ломает страницу), копия — атрибут
`data-mode="work|showcase"` на `<html>`. Атрибут ставит встроенный скрипт до
первой отрисовки (`UI_MODE_BOOT_SCRIPT`, по образцу скрипта заставки) — рабочий
режим не мигает визуалом; скрипт заставки идёт следом и в рабочем режиме её
пропускает. Чистые функции — `ui/lib/ui-mode.ts` (с тестом), хуки — `ui/hooks/ui-mode.ts`:
`useUiMode()` (через `useSyncExternalStore`, смена режима сразу видна во всех
компонентах и других вкладках) и `useCalmMotion()` = «уменьшить движение» ИЛИ
рабочий режим. Декоративные компоненты, которые раньше спрашивали только
`usePrefersReducedMotion`, теперь спрашивают `useCalmMotion`. Где проще CSS
(меню, дымка фона) — правило `:global(html[data-mode='work'])`.

**Переключатель** — пара кнопок «Рабочий / Презентационный», как «Бирки / Список»
в реестрах (`ui/layout/UiModeSwitch.tsx`): в шапке рядом с именем пользователя
(на экране от 1081 px), в настройках — раздел «Режим интерфейса», в личном кабинете —
строка в «Настройках» (там его найдёт и представитель вуза, и человек с телефона).

**Не менялось.** Экран входа и 3D-сцена входа (решения 71–76), сборка сайта после
входа, переходы между страницами (View Transitions и перелёт названия, решение 64),
появление блоков — это не украшение, а связь экранов, они уважают только
«уменьшить движение», как раньше. Заставка показывается и на странице входа, поэтому
в рабочем режиме её нет и там. API, контракт и база не менялись.

**Что это ограничивает.** Режим живёт в браузере, а не в профиле: на другом
устройстве человек выберет его заново. Хранить в профиле — поле в базе и эндпоинт
(Тигран), не нужно до защиты.

## 83. Рекомендации и уведомления не говорят неправды о просрочке

**Дата:** 25.09.2026

«Закрыть» убирала рекомендацию «Просрочен этап N» с главной, хотя этап оставался
просроченным, и «Пересобрать» её не возвращала. После завершения или отмены этапа
рекомендация о его просрочке висела «Новой», пересборка отвечала «закрыто 0».
Таблица переходов статусов жила только в интерфейсе: API принимал `DONE → NEW`.
В колокольчике одна просрочка приходила дважды — от срока этапа и от рекомендации.

**Решение.**

- Таблица переходов — `RECOMMENDATION_TRANSITIONS` в `shared/contracts`, одна на сервер
  и интерфейс; остальное — `INVALID_TRANSITION`.
- `DONE` по правилам с проверяемым условием (просрочка, застой, продукт не выбран,
  нет показателей программы) — только когда условие ушло, иначе `CONFLICT` с тем,
  что сделать вместо этого. Не согласен — отклонить с основанием. Проверка —
  та же функция `draftsForCooperation`, что у пересборки: закрытие и пересборка
  не расходятся в том, что считать просрочкой.
- Пересборка закрывает системой открытые, включая принятые, чья проблема ушла,
  и открывает закрытые, чья проблема вернулась, кто бы их ни закрыл. Исключение —
  дефицит навыка, закрытый человеком: действие сделано, дефицит остаётся.
  Отклонённые с основанием не трогаются никогда. Это уточняет решение 56: там
  «решение человека не переписывается», но закрытие человеком при живой проблеме
  теперь невозможно, а закрытое раньше было неправдой о состоянии дел.
- Смена статуса или срока этапа и отметка в чек-листе сразу сверяют открытые
  рекомендации связки: неправда закрывается, правда получает свежий текст. Сверка —
  после транзакции этапа и без исключений наружу: сбой не отменяет смену статуса,
  недосверенное доделает пересборка. Пересчёт одной связки — несколько запросов,
  без очереди и фоновых задач.
- Лента склеивает просрочку по виду события и объекту (связка и номер этапа),
  оставляя пункт срока этапа: он ведёт к самому этапу, и его время не сдвигает
  пересборка. Переоткрытая рекомендация о том же случае проблемы (тот же этап и срок,
  то же последнее движение) сохраняет время создания и не всплывает непрочитанной.
- Не начатый этап за незавершённой контрольной точкой (`isLockedByControlPoint`
  поверх `findBlockingStages`) не даёт ни рекомендации «просрочен», ни уведомлений
  о сроке: начать его нельзя, действие — закрыть точку.

**Расхождение с решением 37.** Оно обещало «просроченных в ленте столько же, сколько
в личной статистике». Теперь в ленте их меньше ровно на запертые контрольной точкой:
счётчики просрочек (главная, реестр связок, личная статистика) не менялись — что в них

## 84. Просрочен только начатый этап; не начатый с вышедшим сроком — «план сдвинут»

**Контекст.** Срок каждого этапа ставится при создании связки и дальше не двигается.
Когда задерживается этап перед ним или держит контрольная точка, у этапов 7–10 срок
выходит раньше, чем их вообще можно начать. Они получали «Просрочен на N дн.» при
статусе «Не начат»: из десяти строк «Требует внимания» шесть были такими, одна связка
(СПбГУТ — Программная инженерия) занимала четыре строки. Задача Артура (ТЗ беку, п. 1);
закрывает `TODO: PM DECISION` из решения 83 — считать ли такие этапы в счётчиках.

**Решение.**
- Просрочен только этап **в работе или заблокированный** с вышедшим сроком —
  `OVERDUE_STAGE_STATUSES` в `workflow.rules.ts`. Одно множество на правило `isOverdue`
  и на запросы: список просрочек, фильтр связок «только просроченные», проблемные
  этапы и счётчик главной, личная статистика, выгрузка (там была своя копия правила —
  теперь вызов `isOverdue`). Рекомендации и лента берут то же правило.
- Не начатый этап с вышедшим сроком — `isPlanShifted`, новое поле в DTO этапа
  и текущего этапа. Интерфейс показывает серую пометку «план сдвинут» с подсказкой;
  на ленте этапов такой этап больше не красный. В счётчики и списки проблем не идёт.
- Связку, где текущий этап так и не начали, ловит правило «Связка без движения»:
  оно смотрит на текущий этап в любом статусе.

**Числа сценария:** проблемных этапов 12 → 5 (по одному на связку, список на главной
больше не обрезается), у СПбГУТ — Программная инженерия просрочено 5 → 1.
Через двое суток после заливки — 6 (срок первого этапа УрФУ), дальше число само не растёт.

**Изменения схемы:** нет. **Затрагивает фронт:** новое поле `isPlanShifted`
у `WorkflowStageDto` и `CurrentStageDto`; `isOverdue` больше не бывает `true`
у не начатого этапа.

## 85. Демо-данные: даты по сюжету, сроки после занятий — от начала занятий

**Контекст.** ТЗ Артура беку, п. 2. В демо-наборе у всех вузов, программ, продуктов,
документов и встреч «Заведён/Обновлён» — момент заливки, при первом контакте в мае.
Срок этапа 11 «Проведение занятий» (октябрь) раньше начала занятий (декабрь).
Все завершённые этапы закрывались в первые две недели связки: у СПбГУТ ИБ «Проведение
занятий» завершено за полгода до начала занятий, за последний месяц не закрывалось
ничего — тренд главной (решение 81) на демо был бы пуст. У наблюдателя ФИО «Наблюдатель
Демонстрационный». 420 заявок СПбГУТ — «оценка» в карточке программы
и «подтверждена вузом» в кабинете вуза.

**Решение (только `prisma/seed.ts`, логика системы не менялась).**
- Сроки этапов 11–14 не раньше начала занятий + 30/60/90/120 дней
  (`DAYS_AFTER_CLASSES_START`, TEMP). В самой системе сроки по-прежнему по нормативам.
- Хронология этапов: этап начинается, когда закрыт предыдущий, закрывается незадолго
  до своего срока, опоздавший — через несколько дней после. Кто в срок, а кто
  с опозданием — как было, доля «в срок» та же (89,1 %). История этапов, журнал
  и отметки чек-листа — теми же датами.
- У СПбГУТ ИБ занятия идут два месяца (раньше — начнутся через 30 дней): этапы 11–12
  у неё закрыты. Лицензия и встреча «Передача учебных материалов» — до закрытия этапа 7.
- Вузы, контакты, программы, продукты, документы, встречи — даты записи по сюжету:
  вуз заведён до первой связки, документ — в день выпуска и обновлён последней
  сменой статуса (день подписания совпадает с переходом «Подписан» в истории).
- Показатели программ СПбГУТ — источник «вручную» (данные вуза): у вуза есть кабинет,
  и заявки там подтверждены. Пометка «оценка» у них уходит; у вузов без кабинета — остаётся.
- Наблюдатель — Лебедева Анна Сергеевна.

**Числа сценария:** среднее время до начала занятий 204 → 186 дней; проблемных этапов
5 → 4 (у СПбГУТ ИБ этап 13 в срок); через двое суток после заливки — 5. Тренд главной
на демо больше не пустой: сервер отдаёт «+1 за 30 дней» у связей и «+0,5» у доли в срок.
Подпись тренда на экране рисует фронт (ТЗ фронту, задача 1) — пока её нет.

**Изменения схемы:** нет. **Затрагивает фронт:** нет.
