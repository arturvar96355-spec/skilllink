## 3. Prisma 7 с драйверным адаптером вместо Prisma 6

**Дата:** 21.09.2026

В Prisma 7 свойство `url` в блоке `datasource` больше не поддерживается: строка подключения
задаётся в `prisma.config.ts`, а клиент работает через драйверный адаптер.

**Решение.** Взята Prisma 7.10 с `@prisma/adapter-pg`. Строка подключения — в `prisma.config.ts`
из `DATABASE_URL`, клиент создаётся в единственном месте (`src/shared/db/prisma.ts`).

**Альтернатива.** Остаться на Prisma 6 с привычным синтаксисом. Отклонено: начинать новый
проект на предыдущем мажоре означает запланировать миграцию на ближайшие месяцы.

**Новые зависимости и зачем.** `@prisma/adapter-pg` и `pg` — требование Prisma 7, без них
клиент не подключится. Типы `@types/pg` отдельно не ставятся: их приносит
`@prisma/adapter-pg`, а сам проект `pg` напрямую не импортирует.

## 7. Отмена этапа требует комментария на любом этапе

**Дата:** 21.09.2026

Решение 4 в `CLAUDE.md` говорит про этап 5: «можно отменить с комментарием "не требуется"».
Про остальные этапы условие не задано.

**Решение.** Комментарий требуется при отмене **любого** этапа.

**Почему.** Отмена — необратимое для менеджера действие (переоткрыть может только ADMIN),
и оно попадает в историю. История без основания бесполезна.

**Что это ограничивает.** Фронт обязан запрашивать комментарий в диалоге отмены, иначе
получит `VALIDATION_ERROR` 422.

## 10. Рейтинг считается в приложении, а не в СУБД

**Дата:** 21.09.2026

Концепция обещает «аналитические показатели рассчитываются представлениями и агрегирующими
запросами на стороне СУБД».

**Решение.** На MVP рейтинг и skill gap считаются в `src/modules/analytics/rating.ts` и
`src/modules/skills/skills.rules.ts` — чистыми функциями, покрытыми тестами.

**Почему.** Формулы ещё не утверждены (все веса помечены TEMP). Менять коэффициент в конфиге
дешевле, чем переписывать представление и миграцию. Чистые функции проверяются тестами
без поднятия базы.

**Когда пересмотреть.** При росте объёма данных расчёт переносится в представления PostgreSQL
без изменения контракта API. Обсудить с Тиграном.

## 11. Нормирование внутри выборки

**Дата:** 21.09.2026

**Решение.** Рейтинг нормируется внутри выборки ответа; спрос на навыки — по всей выборке
периода, а не по отфильтрованной странице.

**Почему.** Для спроса иначе масштаб зависел бы от фильтров и значения нельзя было бы
сравнивать между запросами.

**Что это ограничивает.** Баллы рейтинга сравнимы только внутри одного ответа. Это написано
в поле `explanation` каждой записи, фронт обязан это показывать.

## 12. Мягкое удаление вместо физического

**Дата:** 21.09.2026

**Решение.** Вузы и программы архивируются (`archived_at`), связи на них — `RESTRICT`.
Архивировать вуз с незакрытыми связками нельзя — `CONFLICT` 409.

**Почему.** Сотрудничество длится годами, история — основная ценность системы.

## 15. Пустое тело PATCH отклоняется

**Дата:** 21.09.2026

При реализации обнаружено: `.partial()` в Zod **не снимает** `.default()`. Схема изменения,
построенная из схемы создания, на пустом теле возвращала `{ status: "NEW" }` и молча меняла
статус записи.

**Решение.** Для вузов, программ и связок заведены отдельные наборы полей без значений
по умолчанию. Схема создания добавляет `.default()` поверх, схема изменения строится из чистой
базы. Поведение закреплено тестами в `universities.test.ts`, `programs.test.ts`,
`cooperation.test.ts`.

## 16. Сортировка с `nulls: 'last'` только для nullable-полей

**Дата:** 21.09.2026

При прогоне сквозного сценария выяснилось: Prisma отклоняет `orderBy: { field: { sort, nulls } }`
для полей, которые не могут быть NULL. Список связок падал с 500.

**Решение.** В `shared/http/pagination.ts` добавлен `buildOrderBy(sort, nullableFields)`.
Каждый репозиторий перечисляет свои nullable-поля: показатели набора у программ, контрольные
даты у связок. В сквозной сценарий добавлены проверки сортировки по обоим видам полей.

## 20. Застой связки считается по любому незакрытому этапу

**Дата:** 21.09.2026

Первая версия правила `cooperation.stalled` срабатывала только на этапе в статусе
`NOT_STARTED`. На демонстрационных данных оно не сработало ни разу: связка, которая месяц
висит на начатом этапе, под правило не попадала.

**Решение.** Правило смотрит на любой незакрытый текущий этап и подбирает формулировку под
его статус. Застой на заблокированном этапе получает повышенный приоритет: блокировка,
которую месяц никто не снимает, — не рабочее состояние.

## 21. Просрочка и застой по одной связке не дублируются

**Дата:** 21.09.2026

**Решение.** Если по связке уже сформирована рекомендация о просроченном этапе, рекомендация
о застое не создаётся.

**Почему.** Это две карточки об одной проблеме. Список приоритетных действий должен отвечать
на вопрос «чем заняться», а не показывать одну связку дважды.

## 22. Демонстрационные заявки согласованы с показателем

**Дата:** 21.09.2026

При проверке кабинета вуза выяснилось: `applicationCount` в демо-данных проставлялся вручную
и не совпадал с суммой записей в `applications`. Первая же поданная заявка запускала пересчёт,
и показатель на глазах менялся с 420 на 120.

**Решение.** Seed создаёт заявки ровно на то количество, которое стоит в показателе, и в конце
сверяет сумму. Расхождение роняет загрузку данных с явной ошибкой.

**Почему.** Решение 9 объявляет заявки источником истины для `applicationCount`. Набор данных,
который этому противоречит, ломает демонстрацию в самый неудобный момент.

## 23. `next typegen` перед проверкой типов

**Дата:** 21.09.2026

Next.js генерирует типы маршрутов в `.next/types`, и `tsc` их проверяет. Пока сгенерированные
типы не обновлены, новые маршруты дают ложные ошибки, а ошибки в старых — не видны.

**Решение.** `npm run typecheck` выполняет `next typegen && tsc --noEmit`.

## 25. Добавлен модуль `audit`

**Дата:** 21.09.2026

`CLAUDE.md` перечисляет `AuditLog` среди сущностей, но модуля для него не задаёт.

**Решение.** Заведён `src/modules/audit` с двумя разными ответами на два разных вопроса:
`GET /api/audit` — технический журнал для администратора, `GET /api/universities/:id/events` —

**Почему лента строится не из журнала.** Пункт 7.3 ТЗ требует «Последние события» —

собирается из доменных данных: истории этапов, истории документов, встреч и заявок.

**Что это ограничивает.** Лента показывает только то, что оставляет след в доменных
таблицах. Действия без такого следа (например, правка описания вуза) в неё не попадут.

## 26. NextAuth.js версии 5 (beta) вместо стабильной четвёртой

**Дата:** 21.09.2026

Концепция обещает «аутентификация и сессии через NextAuth.js на токенах JWT». Стабильная
линия next-auth 4 рассчитана на Pages Router; с App Router работает версия 5, которая пока
в статусе beta.

**Решение.** Взята `next-auth@5.0.0-beta.32`, версия зафиксирована точно — без диапазона.

**Почему это приемлемо.** Весь доступ к пользователю идёт через единственную функцию
`getCurrentUser()`. Если бета подведёт, её реализация меняется в одном файле, а модули
не трогаются — ровно то, ради чего решение 9 и вводило эту функцию.

**Новые зависимости и зачем.** `next-auth` — обещано концепцией. `bcryptjs` — хеширование
паролей; выбран вместо `bcrypt`, потому что не требует нативной сборки и одинаково ставится
на машинах команды.

## 27. Демо-режим входа остаётся, но выключается переменной

**Дата:** 21.09.2026

Решение 9 предполагает, что на P1 mock-авторизация просто исчезает. На защите проекта
переключение ролей в один клик — половина демонстрации: кабинет вуза, права аналитика,
скрытые комментарии показываются именно так.

**Решение.** Настоящий вход по паролю работает всегда. Дополнительно, пока включён
`DEMO_AUTH_ENABLED`, действует переключение пользователя cookie `skilllink_user`.
По умолчанию режим выключен только в продакшене.

**Что это ограничивает.** Включённый демо-режим — это обход авторизации. Настоящая сессия
имеет приоритет над cookie, но сам режим в промышленном контуре держать нельзя. Записано
отдельной строкой в [SECURITY_LIMITATIONS.md](SECURITY_LIMITATIONS.md).

## 28. Текущий пользователь переехал с `/api/auth/me` на `/api/me`

**Дата:** 21.09.2026

NextAuth занимает всё пространство `/api/auth/*` перехватывающим маршрутом.

**Решение.** Собственный эндпоинт текущего пользователя перенесён на `/api/me`.

**Почему сразу.** Статический сегмент в Next перекрывает перехватывающий, так что технически
соседство работало бы. Но держать свой маршрут внутри чужого пространства имён — это мина
на будущее. Фронт к эндпоинту ещё не подключался, поэтому переезд ничего не ломает.

**Затрагивает фронт:** `GET /api/auth/me` → `GET /api/me`.

## 29. Клиент Prisma создаётся лениво

**Дата:** 21.09.2026

Клиент создавался прямо при импорте модуля и падал без `DATABASE_URL`. Из-за этого
юнит-тест чистой функции падал, если в её файле был хоть один транзитивный импорт,
ведущий к базе.

**Решение.** `prisma` — прокси, который создаёт клиент при первом обращении к свойству.
Методы привязываются к экземпляру, поведение для вызывающего кода не меняется.

**Почему это важнее удобства.** Модуль, который падает на импорте, делает нетестируемым
всё, что его касается. Проблема всплыла на первом же тесте настроек авторизации.

## 30. Текст документа хранится, а файл — нет

**Дата:** 21.09.2026

Концепция обещает «генерацию пакета документов из шаблонов с автоподстановкой реквизитов».
Решение 14 при этом ограничивает документы метаданными и ссылкой.

**Решение.** В таблицу `documents` добавлены `content` (собранный текст) и `template_key`.
Файлы по-прежнему не хранятся и не загружаются — это остаётся P2.

**Почему.** Без хранения текста генерация не оставляет после себя ничего: пользователь

## 33. Спецификация OpenAPI собирается из Zod-схем

**Дата:** 21.09.2026

## 36. За прокси с HTTPS задаётся `AUTH_URL`

**Дата:** 22.09.2026

**Что нашлось.** Вход через имитацию HTTPS-прокси (заголовки `Host`, `X-Forwarded-Proto`,
`X-Forwarded-Host` как у Caddy) проходил, cookie получали приставку `__Secure-`,
но после входа NextAuth отправлял пользователя на **`https://localhost:3100`**.

Причина в Next.js: при `next start` он собирает адрес запроса из собственного имени
(`localhost:порт`), а заголовок `Host` не использует. NextAuth строит все переходы
от этого адреса. Протокол при этом берётся из `X-Forwarded-Proto` — поэтому снаружи
всё выглядело почти правильно.

**Решение.** Публичный адрес задаётся переменной `AUTH_URL` — её читает сам next-auth.
В контейнере — через `DOCKER_AUTH_URL`, по той же причине, что и `DOCKER_AUTH_SECRET`.
Пустое значение безопасно: next-auth считает его незаданным (проверено запуском).

**Проверено:** без `AUTH_URL` — переход на `localhost`; с ним — на адрес сайта.
Сессия видна и снаружи через прокси, и изнутри сервера (`apiFetch` ходит
на `127.0.0.1` без заголовков прокси) — в обоих случаях.

**Попутно исправлено.** README и HANDOFF велели `export AUTH_SECRET=...` перед
`docker compose`, а контейнер с прошлого исправления читает `DOCKER_AUTH_SECRET`:
по инструкции секрет в контейнер не попадал. Теперь это ловит тест
`src/shared/config/compose-docs.test.ts`.

## 37. Уведомления собираются из данных, прочитанность хранит фронт

**Дата:** 22.09.2026

Дизайн-система ставит колокольчик с лентой в шапку каждой страницы. Уведомления
были P2 с невыбранным каналом — дизайн выбрал его сам: лента в интерфейсе.
**Одобрено Артуром 22.09.2026** (`DECISIONS.md`, решение 14).

**Решение.** `GET /api/notifications` собирает ленту на лету: сроки своих этапов,
изменения других людей в своих связках и документах, открытые рекомендации высокого
приоритета. Представителю вуза — только движение по его вузу.

**Почему без таблицы уведомлений.** Лента из данных не расходится с ними: закрытый
этап перестаёт быть «просроченным» и в ленте. Таблица требовала бы изменения схемы,
согласования с Тиграном и фоновой рассылки — за неделю до защиты.

**Прочитанность — на фронте**: время последнего просмотра в `localStorage`,
передаётся в `since`. Ограничение честное: на другом устройстве лента снова
непрочитанная. Нужна общая — это одна колонка `users.notifications_seen_at`.

**Время события — когда оно случилось**, а не когда посчитано: иначе просрочка
выглядела бы новой при каждом запросе, и «отметить прочитанным» не работало бы.

**Проверено:** просроченных в ленте столько же, сколько в личной статистике;
каждая ссылка открывается тем, кому пришло уведомление (контрольный опыт: подмена
id — пробник поймал 5 из 20); в ленте представителя вуза нет внутреннего.

Новая пометка TEMP: `NOTIFICATION_WINDOW_DAYS = 14` — за сколько дней показываются
изменения других людей.

## 40. Исчерпанные попытки входа называют себя

**Дата:** 22.09.2026

Было: после пяти неудач подряд учётная запись закрывалась на 15 минут, а отказ выглядел
ровно как «неверный пароль». Человек вводил правильный пароль, получал отказ и решал,
что забыл его. На защите это 15 минут растерянности при переключении на представителя вуза.

Одинаковый ответ был выбран сознательно — чтобы по нему нельзя было узнать, какие
адреса заблокированы. Пересмотрено: блокируется и несуществующий адрес, поэтому код
не выдаёт, есть ли учётная запись; а тот, кто исчерпал попытки, и так знает об этом.

**Решение.** Код `too_many_attempts` в ответе входа (`CredentialsSignin` с собственным
`code`). «Нет пользователя» и «неверный пароль» по-прежнему неразличимы.

**Проверено** на живом сервере: пять неудач по несуществующему адресу — `credentials`,
шестая — `too_many_attempts`; обычная ошибка пароля — `credentials`; верный пароль входит
и обнуляет счётчик. Проверка осталась в пробнике.

**Затрагивает фронт:** экран входа должен различать два кода — `API_CONTRACT.md`, «Вход».

## 41. Интерфейс собран в том же приложении

**Дата:** 22.09.2026

По первоначальному плану фронт собирался отдельно, по дизайн-системе команды
(шесть документов в `docs/design/`). Чтобы к дедлайну система была цельной, интерфейс
решили собрать в этом же приложении по той же дизайн-системе.

**Решение.** Интерфейс живёт в этом же приложении Next.js, а не отдельным проектом:

- `src/ui/` — дизайн-система: примитивы, таблица, состояния, всплывающие окна, каркас,
  поиск, уведомления, хуки и обращения к API. Страницы берут всё оттуда и своих кнопок,
  карточек и таблиц не заводят.
- `src/app/(app)/` — внутренние страницы внутри общего каркаса;
  `src/app/(auth)/login` — вход.
- Оформление — переменные в `src/app/globals.css` плюс CSS Modules. Никакого Tailwind
  и никаких UI-библиотек: значения дизайн-системы заданы точно (цвета, радиусы, размеры
  шрифта), и слой утилит между ними и разметкой ничего не добавляет, зато добавляет
  зависимость и конфигурацию, которую потом некому поддерживать.
- Иконки — свой набор линейных значков в `src/ui/primitives/Icon.tsx`. Библиотека икон
  ради двадцати начертаний — лишняя зависимость (CLAUDE.md).
- Данные — только через API теми же маршрутами, что описаны в контракте. Прямых обращений
  к сервисам и Prisma из страниц нет: фронт остаётся отделяемым.

**Почему не отдельный проект.** Отдельный фронт — это второй репозиторий, вторая сборка,
CORS, свои переменные окружения и своя выкладка. За неделю до защиты это цена без выгоды:
страница и эндпоинт, который её кормит, проверяются одной командой и выкатываются одним
образом.

**Что это меняет в правилах.** Пункт «не переделывать вёрстку фронта» остаётся в силе
для экранов дизайнеров команды: они встают рядом и не переписываются. Дизайн-система
общая — `docs/design/`.

**Проверка.** `npm run typecheck`, `npm test` (тесты меню и форматирования — новые),
`npm run build` и живой проход по экранам в браузере.

## 42. Страницы проверяют сессию куки, а права — сервер

**Дата:** 22.09.2026

`middleware.ts` отправляет на `/login` того, у кого нет куки сессии. Подпись токена
при этом не проверяется: middleware выполняется в edge-среде, где нет ни bcrypt,
ни Prisma, и полноценная проверка потребовала бы отдельной сборки конфигурации входа.

Это не ослабляет защиту: страницы не содержат данных — всё приходит запросами к API,
где каждый маршрут проверяет сессию и права по-настоящему. С подделанной кукой
откроется пустой каркас, который тут же получит 401 и вернёт на вход.

Маршруты `/api/**` из middleware исключены намеренно: они обязаны отвечать кодом 401,
а не перенаправлением на HTML-страницу, иначе любой запрос из интерфейса ломается.

## 43. Страницы не кэшируются браузером без проверки

**Дата:** 23.09.2026

Сергей открыл стенд после выкладки интерфейса и увидел старую заглушку
«SkillLink API». Браузер был ни при чём: Next отдаёт готовые страницы
с `Cache-Control: s-maxage=31536000`. Этот заголовок адресован промежуточным
кэшам, но браузер, не найдя `max-age`, выбирает срок хранения сам — Safari
выбрал «долго» и показывал страницу, которой в приложении уже нет.

На защите это стоило бы показа: у всех, кто открывал стенд раньше, осталась бы
старая версия, и никакая выкладка этого бы не изменила.

**Решение.** Страницы и ответы API отдаются с `Cache-Control: no-cache`:
браузер обязан спросить сервер перед показом, а при совпадении ETag получает
пустой ответ 304. Файлы сборки под `/_next/static` кэшируются навсегда — у них
хеш в имени. Правило задано дважды: в `next.config.ts` (чтобы локальный запуск
вёл себя так же) и в Caddyfile стенда (последнее слово за прокси).

**Проверка.** `scripts/deploy/check.sh` смотрит этот заголовок и падает, если
страницы снова начнут кэшироваться без проверки. Проверка написана до
исправления и на тогдашнем стенде падала — это и был тот самый заголовок.

**Что это не чинит.** Копию, уже сохранённую браузером, заголовок не отменяет:
её нужно один раз обновить с очисткой кэша. Предупреждение добавлено
в сценарии показа, пункт подготовки.

## 44. Плотность реестров и первый экран главной — по решению Артура

**Дата:** 23.09.2026

Артур решил два продуктовых вопроса: реестр должен выглядеть рабочим инструментом
(20–25 строк на экран), а главная — отвечать «где горит» (проблемы — главный блок,
показатели — одной строкой).

**Плотность.** Строка таблицы — 32 пикселя, содержимое в одну строку: длинное
обрезается многоточием, полное — в подсказке (`CellText`). Раскладка столбцов
фиксированная: иначе запрет переноса растягивал столбец с длинным названием
и выталкивал остальные за край. Подписи над фильтрами скрыты визуально
и оставлены для программ чтения с экрана — их смысл и так читается из подсказки
внутри поля. Итог на 1440×900: 20 строк реестра на экране, на Full HD — 25.

Для этого в ответы API добавлены краткие названия вузов (`universityShortName`
у связок, программ и проблемных связок): полное название в плотной строке
обрезалось на первом слове.

**Главная.** Пять плиток заменены полосой показателей (`KpiStrip`), под ней —
«Требует внимания» на три пятых ширины и приоритетные действия рядом. Строка
проблемы ведёт сразу на этап (`stageId`).

**Найдено по дороге — две неправды на первом экране.**

1. Подпись «5 связок встали» выдавала лимит вывода за число проблем: в демо-наборе
   проблемных этапов двенадцать. Теперь сводка отдаёт `problemStageTotal`,
   главная пишет «12 этапов стоят… показаны 10 самых давних», а пробник сверяет
   это число со списками просроченных и заблокированных этапов (обратный
   эксперимент: сдвиг счётчика на единицу ловится).
2. В реестре связок у текущего этапа значок «просрочен на N дн.» подставлял дни
   до контрольной даты всей связки. У СПбГУТ «Программная инженерия» выходило
   «74 дня» вместо настоящих 58. У текущего этапа теперь свой `daysToDeadline`.

Все изменения API — только новые поля, прежние не менялись.

## 45. Устойчивый порядок списков и подготовка стенда к показу

Сверка стенда со сценарием показа (`scripts/demo-check.ts`) нашла две ошибки,

## 47. Дни — по московскому календарю; в день срока — «сегодня»

**Дата:** 23.09.2026

**Сутки по UTC расходились с датой на экране.** Интерфейс показывает даты по Москве,
а сервер считал дни до срока по суткам UTC. Срок «01.10, 01:00» по Москве — это
30.09, 22:00 по UTC, и 30 сентября днём рядом с датой «01.10» стояло «срок через
0 дн.». `daysBetween` (`src/shared/utils/date.ts`) теперь считает московские сутки:
постоянное смещение +3 часа, перехода на летнее время в Москве нет с 2014 года.
Разница целых суток от этого не меняется, поэтому числа демо-набора те же
(сверка со сценарием — 25 из 25). Модульные тесты на границы суток; с прежним
расчётом по UTC два из них падают.

**«Просрочен на 0 дн.»** Срок этапа — точный момент (начало плюс норматив),
и к вечеру дня срока этап уже просрочен, а календарных дней не прошло. Значок
писал «Просрочен на 0 дн.», главная — «−0 дн.», причина — «Этап просрочен на 0 дн.».
Теперь — «Срок вышел сегодня», в узком столбце «сегодня» (`deadlineBadgeText`,
тест). Момент просрочки не менялся: этап, у которого срок прошёл по часам,
по-прежнему в числе проблемных — иначе главная и списки разошлись бы.

**Попутно — ошибка в контракте.** Пример `daysOverdue` в API_CONTRACT.md был
отрицательным, сервер всегда отдавал положительное число. Интерфейс брал модуль
и ошибки не показывал; исправлен пример и описан знак.

## 48. Устаревшая сессия ведёт на вход, а не в пустой экран

**Дата:** 23.09.2026

**Что было.** Middleware проверяет только наличие cookie сессии и вошедшего
со страницы входа отправляет на главную. Когда cookie остался, а пользователя
за ним нет, главная получала 401 и уводила на `/login`, middleware возвращал
на главную — экран оставался пустым. Войти было нельзя, пока не почистишь
cookie. Так случилось бы утром перед защитой: перезаливка демо-данных создаёт
пользователей заново, и у каждого, кто входил накануне, стенд открылся бы
пустым. Тот же тупик ждал отключённого администратором пользователя.

Локально не воспроизводилось: в режиме разработки включён демо-вход,
и сервер молча подставлял менеджера вместо пропавшего пользователя. Найдено
на боевой сборке с `DEMO_AUTH_ENABLED=false`, как на стенде.

**Что сделано.**

- На 401 `useResource` и `useMutation` вызывают `leaveToLogin()`: снимают сессию
  (`signOut`) и полным переходом открывают `/login?reauth=1&from=<где был>`.
  Действие без сессии тоже уводит на вход: отказ «Требуется вход» в карточке
  этапа читался бы как отказ системы.
- Middleware пропускает `/login?reauth=1` и с cookie — на случай, если снять
  сессию не удалось. Имя параметра — `src/shared/auth/reauth.ts`, общее
  для middleware и клиента.
- Страница входа пишет «Сессия устарела — войдите снова», после входа
  возвращает туда, где человек был.

**Проверено.** Боевая сборка на демо-базе, демо-вход выключен: вкладка вошла,
демо-данные перезалиты, открытие реестра привело на вход с подсказкой, вход
вернул в реестр; нажатие «Начать этап» на открытой до перезаливки карточке
привело на вход, а не к ошибке в карточке. Пробник проверяет, что вход
с `reauth` открывается при старом cookie (обратный эксперимент: без исключения
в middleware — 307), `check.sh` — то же на стенде.

**Попутно.** Сквозной сценарий проверял сработавшие правила рекомендаций
по первой странице в 50 строк. На рабочей базе, где записи копятся от прогонов,
нужная уехала на 53-е место, и проверка падала без ошибки в приложении. Теперь
сценарий читает все страницы, а «повторная генерация не плодит дубликаты»
сравнивает общее число, а не длину страницы, которая при сотне записей
одинакова всегда.

## 50. Просрочка не вытесняется из ленты уведомлений

**Дата:** 23.09.2026

Решение 37 обещало: «просроченных в ленте столько же, сколько в личной статистике».
Держалось это, пока событий мало. Время просрочки — истёкший срок, то есть прошлое,

наверх и не становится непрочитанной заново. Модульный тест: тридцать свежих
изменений и две старые просрочки при `limit` 20 — обе просрочки в ленте (без
исправления тест падает).

**Попутно — пробник на растущей базе.** Проверка обхода реестра вузов по рейтингу
сравнивала все страницы с одной выдачей, а одна выдача ограничена сотней: на рабочей
базе вузов стало 105, и проверка падала без ошибки в приложении. Теперь обход
сверяется с первыми строками выдачи.

## 52. Пределы базы — на входе API, а не в тексте внутренней ошибки

**Дата:** 23.09.2026

Проверка входа знала смысл полей, но не типы колонок. Всё, что проходило Zod
и не помещалось в PostgreSQL, доходило до запроса и отвечало 500 «Внутренняя
ошибка сервера». Нашлось обстрелом API на локальном сервере: мусор в каждый
параметр, путь и тело каждого маршрута.

- **Символ с кодом 0** (`%00`, `\u0000`) PostgreSQL не принимает ни в записи,
  ни в поиске. Давал 500 на двадцати адресах API: поиск `q` в девяти списках, карточки по `id`,
  создание и правку, загрузку CSV, cookie демо-входа; вход по паролю отвечал
  «ошибка конфигурации». Теперь он останавливается там же, где проверяется
  остальное: `parseBody`, `parseOptionalBody`, `parseQuery` — `VALIDATION_ERROR`
  с именем поля; параметры пути — в общей обёртке `handle`, ответ «не найдено»
  (такого идентификатора быть не может); в CSV — «Файл не похож на текстовый CSV»:
  нулевые байты бывают только в двоичных файлах, и .xlsx раньше получал
  «не найдены колонки» при колонках на месте.
- **Количества.** `z.number().int()` пропускает целые до 2^53, колонка `Int` —
  до 2 147 483 647: «Студентов: 99 999 999 999» падало на записи. Количества
  идут через `countSchema()` из `shared/zod`, импорт проверяет тот же предел —
  раньше предпросмотр обещал «Будет создан», а запись падала. `minDaysOverdue`
  без границы давал несуществующую дату — теперь не больше 36 500.
- **Текст ошибки базы уходил наружу.** Импорт писал в `detail` строки сообщение
  Prisma целиком — с вызовом и данными. Теперь наружу — только то, что отдаёт
  общая `toAppError` (её же использует `handle`), остальное — «внутренняя ошибка».
- **Персональные данные в журнале.** Обработчик писал в журнал `error.message`,
  а у Prisma это весь вызов с аргументами: при сбое записи контакта в журнал
  попали бы ФИО, телефон и почта. `describeForLog` оставляет имя ошибки, код
  и последнюю строку — причину. Так же пишет журнал аудита.

Сторож в `storable.test.ts`: целое без `.max()` в схемах модулей роняет тесты.
Контрольный опыт — без исправления падают 8 тестов из 48.

## 53. Вход и границы запроса: возврат, перебор, размер тела

**Дата:** 23.09.2026

Нашлось сквозной проверкой кода по четырём направлениям; каждое место
воспроизведено до исправления.

- **Возврат после входа уводил на чужой сайт.** `from` проверялся условием
  «начинается с `/`», а `//evil.example` и `/\evil.example` браузер читает как
  адрес другого сайта. Ссылка `/login?reauth=1&from=//evil.example` открывала
  вход даже вошедшему — с надписью «Сессия устарела» — и после ввода настоящего
  пароля переводила на чужую страницу. Теперь `safeReturnPath` разбирает адрес
  тем же парсером URL, что и браузер, и пропускает только свой сайт.
- **Ограничение перебора обходилось параллельными запросами.** Неудача
  записывалась после запроса к базе и bcrypt (~50 мс), и все одновременные
  попытки проходили проверку блокировки раньше, чем первая успевала записаться.
  `throttledAttempt` засчитывает попытку сразу после проверки, без `await`
  между ними; удачный вход обнуляет счётчик. Тест: сто одновременных догадок —
  проверяется пять (без исправления — сто).
- **Тело запроса читалось целиком.** `request.json()`, `.text()`, `.arrayBuffer()`
  не знают предела, а проверка длины по заголовку при передаче chunked не
  срабатывает: наблюдатель мог прислать на импорт гигабайты, и процесс держал
  их в памяти до проверки прав. `readBodyBytes` читает поток кусками и обрывает
  на пределе; через него идут `parseBody`, `parseOptionalBody` и импорт; права
  на импорт — до чтения файла.

## 54. Интерфейс: данные — только своего адреса, этап 14 — со связкой

**Дата:** 23.09.2026

## 55. Этапы связки: проверяется итог записи, изменения — по очереди

**Дата:** 23.09.2026

- **Завершённый этап терял результат, заблокированный — причину** (решение 4).
  Правила перехода проверяли запрос, а записывался этап, собранный из запроса
  и сохранённых полей. `{"status":"COMPLETED","result":"   "}` проходило
  проверку по сохранённому результату и записывало пустой; `{"result":null}`
  у завершённого не проверялось вовсе — правка полей без смены статуса правил
  не касалась; `{"blockingReason":""}` у заблокированного оставляло его без
  причины. Теперь итог собирается один раз (`resolveStageFields`), проверяется
  (`assertStageFieldsComplete`) и он же записывается. Завершение с пустым
  результатом в теле берёт сохранённый — как обещает контракт.
- **Изменения этапов одной связки шли без очереди.** Проверки — вне транзакции,
  транзакция ничего не блокировала. Тринадцать одновременных закрытий этапов 1–13
  оставляли этап 14 «в работе» — три раза из трёх; снятие обязательного пункта
  одновременно с завершением давало завершённый этап с открытым пунктом.
  `lockCooperation` берёт строку связки `FOR UPDATE` в начале каждой транзакции,
  меняющей этапы (смена статуса, отметка пункта, выпуск версии продукта); то, что
  могли изменить соседи, — контрольная точка и чек-лист — проверяется ещё раз
  под блокировкой. Раздел пробника с контрольным опытом.
- **Повторная отметка пункта переписывала, кто его отметил**: подтверждение
  представителя вуза переходило к менеджеру на устаревшей странице. Повтор
  ничего не меняет.
- **Правило этапа 14 было в трёх местах**: в сервисе, в выпуске версии продукта
  и в демонстрационном наборе. Копия в наборе считала по номеру последнего
  закрытого этапа, и у связки УрФУ «Компьютерная безопасность» с начатым этапом 1
  этап 14 значился «Не начат». Теперь одно правило (`computeControlStatus`)
  и один пересчёт (`recomputeControlStage` в `workflow.repo`). Числа показа
  не меняются: сверка со сценарием на новом наборе — 25 из 25.

## 56. Рекомендации: вернувшаяся проблема снова открыта, застой — по движению этапов

**Дата:** 23.09.2026

- **«Связка без движения» смотрела на запись связки.** Смена статуса этапа

## 60. Рейтинг и дефициты: действующая программа, спрос по навыку, период по календарю

**Дата:** 23.09.2026

- **Программы архивного вуза оставались в аналитике.** «Действующая программа»

- **Навык с несколькими замерами спроса считался несколько раз.** Замеров на навык
  за период бывает несколько — по регионам и источникам. Дефицит считался по каждой
  строке: навык дважды в списке, покрытие на главной с двойным счётом, две
  рекомендации с одним ключом затирали друг друга. Теперь одна строка на навык

  строкой «2026-Q1» больше «2026-09». Теперь по календарю (`latestOfPeriods`), и одна
  функция вместо двух копий — в дефицитах и в рекомендациях.
- **Покрытие на главной считалось по первым двумстам строкам**, отсортированным

- **Рейтинг брал пустые показатели первыми.** PostgreSQL ставит NULL первыми при

- **«Активные связи» значили разное**: карточка вуза считала и приостановленные,
  главная и кабинет — нет. Одно определение — `ACTIVE_COOPERATION_STATUSES`.

Числа показа не меняются: сверка со сценарием — 25 из 25, покрытие те же 88,9%.

## 63. Визуальное направление 07: графит, сигналы вместо материала

**Дата:** 23.09.2026

Серёжа прислал `docs/design/07_Human_Crafted_Override.md` — документ с высшим
приоритетом над 01–06 — и бриф к нему. Главная претензия: интерфейс выглядит
сгенерированным — одинаковые тёмные карточки с фиолетовой рамкой, градиент на
каждой кнопке, свечение, иконки в квадратиках. Переделка идёт в порядке,
который задаёт сам документ (раздел 39): убрать шум → выстроить иерархию →
главная → фирменные элементы → движение.

**Шаг 1 (этот).** Токены `globals.css`: холст и три уровня графита (L0–L3),
акценты фиолетовый/розовый/оранжевый/бирюзовый — только как сигналы, текст
тёплого белого, линии белого с малой прозрачностью. Свечения погашены
(имена токенов оставлены, чтобы страницы не ломались), градиент — один
фирменный `--gradient-brand` для редких мест. Радиусы по разделу 14.
Кнопки: основная — светлая сплошная, акцентная (`variant="accent"`) —
фиолетовая, для одного продуктового действия на экран; вторичная — прозрачная
с тонкой линией; «призрачная» — без контейнера до наведения. Карточки —
без рамки и тени, отделяются тоном. Боковое меню — тонкая вертикальная метка
у текущего пункта, наведение — сдвиг на 3px. Таблица — редакционный список:
наведение — лёгкий фон и сдвиг содержимого на 4px, сетка не двигается.
Фиолетовые значения в модулях стилей переведены в графит правилом
по свойству (рамка → линия, подложка → графит, свечение → убрано).

**Что взято не буквально — потому что данных нет, а выдумывать их нельзя
(CLAUDE.md, «Данные»):** «время до найма» остаётся «временем до начала
занятий» — данных о найме в системе нет; «компания» в схеме связей —
ИТ-Школа РТК, других компаний в модели нет; «рекомендуемые программы
с баллом совпадения и причинами» — это рейтинг программ с его настоящим
баллом и вкладами показателей.

**Шаг 2 — главная (раздел 10 документа 07).** Пять плиток показателей заменены
на Live Rail: числа — типографикой в одну строку, под ними маршрут из четырнадцати
этапов с засечками и фазами, на нём — связки в работе точками на своём текущем
этапе, подписанные вузом; застрявшие (просрочка или блокировка) — красные и
получают один импульс при появлении. Внизу блока — «N этапов требуют внимания»
и время обновления. «Требует внимания» — лента событий на линии времени с записью
этапа «06 / 14», а не таблица в рамке; «Приоритетные действия» — строки; «Связки
в работе» — строки-маршруты «вуз ── программа ── продукт · 06 / 14», звенья
включаются фирменным градиентом при наведении; «Ключевые программы» — ранжированные
строки: номер, вуз, программа, из чего сложился балл, балл. Появление — одна
композиция: числа → линия дорисовывается → точки → импульс → группы ниже; после
этого всё неподвижно. Показатели, текст сводки и блоки шпаргалки — прежние;
в ответ сводки добавлено краткое имя вуза у ключевых программ.

**Шаг 3 — фирменные элементы карточки связки (разделы 7, 8, 30).** Схема связки —
Collaboration Link Map: «Компания ── Вуз ── Программа ── IT-продукт» типографикой,
без иконок в квадратах; компания — ИТ-Школа РТК (другой в модели нет). Звенья
дорисовываются по очереди, по цепочке проходит один импульс фирменного градиента;
наведение на узел подсвечивает соседей и звенья к ним, остальное приглушает.
От цепочки — ветка к текущему этапу «06 / 14 · название», красная, если этап
просрочен или заблокирован. Лента этапов — 14-stage Depth Rail: перспектива
с точкой схода у текущего этапа, каждый этап сдвинут по оси Z на расстояние от
него — пройденные уходят назад и тише, будущие дальше, проблемные не гаснут;
у текущего — светлый номер и короткая фирменная линия, над лентой — «Текущий
этап 06 / 14». Замки контрольных точек, цвета статусов и щелчок по номеру —
прежние: на них опирается шаг 3 показа.

**Шаг 4 — движение и остатки шума (разделы 5, 9, 17, 18, 23, 24, 29).**
- *Строка реестра → карточка* (`ui/lib/morph.ts`): по щелчку название объекта
  отделяется от строки копией, остальные строки приглушаются; когда карточка
  отрисовала заголовок, копия переезжает на его место и масштабируется, заголовок
  проявляется. Копия, а не общий элемент двух страниц: страницы Next монтируются
  заново, а карточке бывает нужно время на загрузку — название ждёт на месте.
  Не дождалось за полторы секунды — исчезает. Работает во всех реестрах через
  общую таблицу и шапку страницы; при «уменьшить движение» выключено.
- *Поиск*: окно вырастает из кнопки — стартует с её места и формы и
  разворачивается, содержимое проявляется следом.
- *Уведомления*: открытие вниз от колокольчика — сдвиг, прозрачность, масштаб
  0,985 → 1; строки по очереди с шагом 30 мс.
- *Вход*: слева — схема «Вуз ── Программа ── IT-продукт» и маршрут из 14 засечек
  вместо трёх пунктов с иконками; появление — холст, знак, схема дорисовывается,
  панель выходит справа, поля по очереди. После входа форма гаснет, панель
  раскрывается в холст, схема уходит вправо — и через 420 мс открывается главная;
  меню и шапка при первом открытии после входа дописывают сцену (`arrival.ts`).
- *Шум*: знак SkillLink без квадрата-подложки и градиентной обводки; аббревиатуры
  вузов и программ без неоновой рамки; у пустых состояний нет декоративной плитки
  со значком — они говорят текстом.

## 72. Вход — «варп в систему»: из созвездия в сайт

**Дата:** 24.09.2026

После «Войти» сцена входа (решение 71) переходит в сайт одним движением, ~1,5 с:
1. скопления «вузы» и «IT-компании» летят навстречу и сливаются в центре — связь;
2. камера ныряет сквозь ядро, звёзды растут и летят навстречу, фиолетовая вспышка;
3. из вспышки проступает сайт: рабочая область выплывает из глубины и выпрямляется

   и шапка — как раньше (решение 63).

Экран входа уходит через 420 мс (время перехода не менялось), поэтому на время
прыжка холст переносится в `body` поверх сайта и доигрывает над ним, затем гаснет
и сам освобождает ресурсы. Во скрытой вкладке прыжок всё равно доигрывает — иначе
холст остался бы висеть. При «уменьшить движение» прыжка нет, вход прежний.

меткой `ARRIVAL_KEY`; настоящий вход с паролем при проверке не выполнялся.

**Без рывка на переходе.** Смена страницы посреди прыжка на мгновение занимает
браузер (загрузка кода и сборка главной) — звёзды замирали. Теперь: главная
предзагружается сразу после проверки пароля (`router.prefetch`); с прыжком страница
меняется под пиком вспышки (`WARP_NAVIGATE_MS`, форма узнаёт о прыжке по
`body[data-warp=ready]`), без прыжка — через 420 мс, как раньше; в прыжке
плотность пикселей холста — 1, звёзды растут втрое, а не вшестеро; холст
и вспышка — отдельными слоями (`will-change: opacity`). Боевая сборка, чистый
кэш, настоящий клиентский переход: 6 прогонов, ни одного кадра длиннее 34 мс.

лист снимается ещё и по таймеру.

Программ больше, чем вузов, но в карусели одновременно не больше 13 бирок, остальные

Промежуточная полноэкранная карточка вуза (по мотивам Melius) была сделана и убрана

## 75. Вход: звёзды во весь экран и сборка сайта по частям в 3D

**Дата:** 24.09.2026

Уточняет решение 72. Жалобы: звёзды собирались «в отдельном квадрате», переход на

**Квадрат.** Звёздная пыль лежала коробкой 22×12 единиц; при нырке камеры её края
читались как отдельный прямоугольник. Теперь звёздное небо — в сцене (не в
покачивающемся мире) и рассчитано под окно с запасом 15 % по видимой области

**Прыжок** (2 с вместо 1,5): звёзды всего экрана закручиваются воронкой к центру,
скопления «вузы» и «IT-компании» сливаются в яркое ядро, затем звёзды разлетаются

от левого края (rotateY), шапка откидывается сверху (rotateX), блоки страницы по
очереди подлетают из глубины с наклоном. На главной части помечены `data-assemble`:
«Требует внимания» и «Связки в работе» прилетают слева, «Приоритетные действия»
и «Ключевые программы» — справа, воронка — по центру. Только transform и opacity.
Метку `.arrival` каркас снимает через 4 с — дальше страницы приходят обычным
появлением. Узкий экран и «уменьшить движение» — без сборки, как раньше.

ту же сцену на странице, как раньше. Новых зависимостей нет.

## 76. Звёзды собирают главную по частям

**Дата:** 24.09.2026

Уточняет решение 75. Просьба: конец входа подтормаживал; звёзды, собравшиеся в ядро,
должны сами собрать главную по частям, в движении.

**Сборка.** Звёзды закручиваются в ядро (0,9 с) и не замирают — кружат в нём, пока
открывается сайт. Экран входа (`login/Constellation.tsx`) после перехода ждёт
страницу: каркас, шапку, блоки (заготовки — не дольше 0,7 с). Пока ждёт, части
скрыты (`body[data-star-assembly=pending]`). Затем меряет блоки по порядку — меню,
шапка, дальше сверху вниз — и передаёт сцене их прямоугольники: каждая звезда
вылетает из ядра к точке на контуре (три четверти) или внутри своего блока, по дуге
навстречу камере, со своей задержкой; блок проявляется из глубины (transform
и opacity, Web Animations), когда звёзды к нему почти долетели, а звёзды гаснут на
нём. Блоки главной со своей стороной (`data-assemble`) прилетают слева и справа.
То, что пришло позже (данные главной), собирается обычной сборкой каркаса
(`.arrival`, решение 75). Страница не пришла за 2,6 с — звёзды разлетаются мимо
камеры, как раньше.

**Подтормаживание.** Две причины: под шапкой с размытием 18 px летели блоки, и
размытие пересчитывалось каждый кадр; в разлёте звёзды раздувались в крупные
светящиеся точки во весь экран — лишняя заливка для видеокарты. На время сборки
размытие шапки выключено (сплошной фон), точки больше не раздуваются. Угасание
холста CSS-анимацией не нужно — звёзды гаснут сами; холст снимается по окончании.

**Переделка того же дня.** Пользователь увидел не сборку, а разлёт: на локальном
сервере главная после входа компилируется и грузит пользователя дольше 2,4 с,
и ядро отпускало звёзды. И «лагающий» конец воронки: в момент, когда звёзды
собрались, скорость вращения скачком менялась с нуля на большую, а все звёзды
сжимались в одну белую точку. Теперь:
- ядро — наклонный звёздный диск: у каждой звезды свой радиус и скорость
  (внутренние быстрее), вращение разгоняется плавно с начала прыжка — скорость
  нигде не прыгает, и видно, что диск движется;
- ядро ждёт главную до 10 с (`PAGE_WAIT_MS`), данные главной — до 1,5 с; пока
  ждёт, скрыта и загрузочная заготовка каркаса (`data-shell-loading`);
- звёзды собирают экран по одному блоку (шаг 150 мс): 90 % звёзд ложатся на контур
  блока, светятся на нём и мерцают, блок проявляется внутри контура, затем звёзды
  гаснут; меню во всю высоту не забирает себе больше звёзд, чем крупный блок;
- вспышки больше нет — страница под звёздами скрыта до сборки; сайт открывается
  раньше, на середине воронки (`WARP_NAVIGATE_MS` = 600 мс).

**След звёзд (дополнение).** Звёзды держались на контуре и гасли 0,9 с — дольше,
чем проявлялся блок, и их след висел поверх загруженной страницы; холст убирался
только по сообщению фонового потока. Теперь свечение на контуре 120 мс, угасание
160 мс, разброс вылета звёзд одного блока 60 мс; блок начинает проявляться за 100 мс
до прилёта звёзд и становится непрозрачным, когда они уже гаснут. Холст снимается
сразу, как доиграл последний блок.

**Холст под сайтом (дополнение).** Даже короткое угасание поверх готовых блоков
читалось как след. Холст прыжка теперь лежит не поверх сайта (z-index 1200), а под
его содержимым и над живым фоном (z-index −1, позже фона в документе): звёзды
прилетают на пустое место, где блок ещё скрыт, и проявившийся блок закрывает их
своей непрозрачной поверхностью — поверх содержимого звёзды не видны вовсе.

**След — настоящая причина (дополнение).** Прыжок впервые снят покадрово: Chrome без
окна, экран входа, вместо главной — подложенные меню, шапка и блоки (60 кадров/с,
без пауз). На кадрах след оказался тёмными точками: при обычном сложении погасшая
звезда (цвет — ноль) оставалась в холсте непрозрачной и закрывала фон под собой;
тот же эффект давал тёмный кружок в центре ядра. Теперь у каждой звезды неба
своя прозрачность (цвет — rgba): гаснущая звезда теряет и свет, и непрозрачность,
погасшая невидима. Сначала вместо этого материалы перестали писать непрозрачность
вовсе (только свет) — в Chrome без окна это работало, а обычный Chrome на Mac такие
пиксели холста не показывает, и 3D на экране входа пропал; откатено. Звёзды больше не ложатся на контур блока
(пунктир висел на прозрачных частях — заголовках колонок), а летят в блок струёй
через его центр, расходятся по нему и гаснут ровно к касанию; блок становится
непрозрачным к их прилёту. Диск ядра заполнен до центра.

**Запасной путь (дополнение).** Если фоновый поток не справлялся (нет WebGL
в потоке — Safari до 17, часть сборок Яндекс Браузера; поток не загрузился;
молчит), холст просто снимался — и 3D на экране входа пропадал. Теперь при ошибке,
отказе или молчании потока дольше 2,5 с на место отданного потоку холста встаёт

## 80. Два режима интерфейса: «Рабочий» и «Презентационный»

**Дата:** 25.09.2026

Наставник хакатона: SkillLink — рабочий инструмент аналитиков, лишний визуал ему
не нужен, на каждом экране сразу должно быть видно, где горит. Визуал дизайнера
(решения 70, 73, 79) при этом готов и нужен для показа. Удалять его не стали —
режим выбирает сам человек.

**Рабочий** (по умолчанию для всех ролей):
- реестры вузов и программ по умолчанию «Список», а не «Бирки»; выбор вида
  по-прежнему запоминается, и запомненный выбор главнее режима;
- на главной нет бегущей строки, колец «Здоровье портфеля» и карты вузов —
  «Требует внимания» и «Приоритетные действия» идут сразу за приветствием
  и полосой «Активно сейчас» (и появляются раньше); ленту событий и список вузов
  для карты главная в этом режиме не запрашивает;
- нет заставки, «рассыпки» букв приветствия, линейки прокрутки, импульсов
  и прорисовки проводов графа связей, «магнитных» кнопок, перекатывания букв
  в меню; живой фон неподвижен (дымка не дышит, свечение не ходит за курсором);
- счётчики, полосы, воронка, радар и бирки не анимируются — как при
  «уменьшить движение».

**Презентационный** — всё как было до этого решения.

**Механика.** Выбор — в `localStorage` (`skilllink.uiMode`, чтение и запись
в try/catch: приватное окно не ломает страницу), копия — атрибут
`data-mode="work|showcase"` на `<html>`. Атрибут ставит встроенный скрипт до
первой отрисовки (`UI_MODE_BOOT_SCRIPT`, по образцу скрипта заставки) — рабочий
режим не мигает визуалом; скрипт заставки идёт следом и в рабочем режиме её
пропускает. Чистые функции — `ui/lib/ui-mode.ts` (с тестом), хуки — `ui/hooks/ui-mode.ts`:
`useUiMode()` (через `useSyncExternalStore`, смена режима сразу видна во всех
компонентах и других вкладках) и `useCalmMotion()` = «уменьшить движение» ИЛИ
рабочий режим. Декоративные компоненты, которые раньше спрашивали только
`usePrefersReducedMotion`, теперь спрашивают `useCalmMotion`. Где проще CSS
(меню, дымка фона) — правило `:global(html[data-mode='work'])`.

**Переключатель** — пара кнопок «Рабочий / Презентационный», как «Бирки / Список»
в реестрах (`ui/layout/UiModeSwitch.tsx`): в шапке рядом с именем пользователя
(на экране от 1081 px), в настройках — раздел «Режим интерфейса», в личном кабинете —
строка в «Настройках» (там его найдёт и представитель вуза, и человек с телефона).

**Не менялось.** Экран входа и 3D-сцена входа (решения 71–76), сборка сайта после
входа, переходы между страницами (View Transitions и перелёт названия, решение 64),
появление блоков — это не украшение, а связь экранов, они уважают только
«уменьшить движение», как раньше. Заставка показывается и на странице входа, поэтому
в рабочем режиме её нет и там. API, контракт и база не менялись.

**Что это ограничивает.** Режим живёт в браузере, а не в профиле: на другом
устройстве человек выберет его заново. Хранить в профиле — поле в базе и эндпоинт
(Тигран), не нужно до защиты.

## 83. Рекомендации и уведомления не говорят неправды о просрочке

**Дата:** 25.09.2026

«Закрыть» убирала рекомендацию «Просрочен этап N» с главной, хотя этап оставался
просроченным, и «Пересобрать» её не возвращала. После завершения или отмены этапа
рекомендация о его просрочке висела «Новой», пересборка отвечала «закрыто 0».
Таблица переходов статусов жила только в интерфейсе: API принимал `DONE → NEW`.
В колокольчике одна просрочка приходила дважды — от срока этапа и от рекомендации.

**Решение.**

- Таблица переходов — `RECOMMENDATION_TRANSITIONS` в `shared/contracts`, одна на сервер
  и интерфейс; остальное — `INVALID_TRANSITION`.
- `DONE` по правилам с проверяемым условием (просрочка, застой, продукт не выбран,
  нет показателей программы) — только когда условие ушло, иначе `CONFLICT` с тем,
  что сделать вместо этого. Не согласен — отклонить с основанием. Проверка —
  та же функция `draftsForCooperation`, что у пересборки: закрытие и пересборка
  не расходятся в том, что считать просрочкой.
- Пересборка закрывает системой открытые, включая принятые, чья проблема ушла,
  и открывает закрытые, чья проблема вернулась, кто бы их ни закрыл. Исключение —
  дефицит навыка, закрытый человеком: действие сделано, дефицит остаётся.
  Отклонённые с основанием не трогаются никогда. Это уточняет решение 56: там
  «решение человека не переписывается», но закрытие человеком при живой проблеме
  теперь невозможно, а закрытое раньше было неправдой о состоянии дел.
- Смена статуса или срока этапа и отметка в чек-листе сразу сверяют открытые
  рекомендации связки: неправда закрывается, правда получает свежий текст. Сверка —
  после транзакции этапа и без исключений наружу: сбой не отменяет смену статуса,
  недосверенное доделает пересборка. Пересчёт одной связки — несколько запросов,
  без очереди и фоновых задач.
- Лента склеивает просрочку по виду события и объекту (связка и номер этапа),
  оставляя пункт срока этапа: он ведёт к самому этапу, и его время не сдвигает
  пересборка. Переоткрытая рекомендация о том же случае проблемы (тот же этап и срок,
  то же последнее движение) сохраняет время создания и не всплывает непрочитанной.
- Не начатый этап за незавершённой контрольной точкой (`isLockedByControlPoint`
  поверх `findBlockingStages`) не даёт ни рекомендации «просрочен», ни уведомлений
  о сроке: начать его нельзя, действие — закрыть точку.

**Расхождение с решением 37.** Оно обещало «просроченных в ленте столько же, сколько
в личной статистике». Теперь в ленте их меньше ровно на запертые контрольной точкой:
счётчики просрочек (главная, реестр связок, личная статистика) не менялись — что в них
считать, решает продукт. Пробник сверяет ленту со статистикой за вычетом таких этапов.

## 87. Подписанный договор сам отмечает пункты этапа 6

**Контекст.** ТЗ Артура беку, п. 4. Подписанный договор («Подписан» в документах)
не отмечал пункты чек-листа этапа 6 «Подписание документов» — подпись вводилась
дважды: статусом документа и тремя галочками. Обратное направление уже работало:
подтверждение вуза в кабинете закрывает пункт этапа 7.

**Решение.**
- Договор (`AGREEMENT`) или лицензия (`LICENSE`) связки переходит в «Подписан» →
  если договор по связке подписан и другие договоры подписи не ждут, отмечаются
  пункты этапа 6, помеченные в конфиге `closedBySignedDocuments` (все три, TEMP).
- Лицензию этап 6 не ждёт: она передаётся на этапе 7, за контрольной точкой,
  и обычно подписывается позже договора. Одна подписанная лицензия при договоре
  на согласовании — не «документы подписаны».
- Правила те же, что у отметки руками (`setTaskDone` под блокировкой связки):
  не на закрытой связке, не на завершённом или отменённом этапе, не за шлагбаумом
  контрольной точки. Отказ здесь — не ошибка: статус документа меняется всегда,
  а ответ говорит, что стало с этапом (`stageChecklist`), интерфейс пишет это
  в сообщении.
- **Отступление от ТЗ:** автор отметки — не «система», а тот, кто подписал
  документ. У отмеченного пункта обязан быть автор (CHECK-ограничение
  и правило `db:verify`); в журнале у отметки `source: "document.signed"`.
- Запасной вариант из ТЗ сделан тоже: у чек-листа этапа 6 строка «Подписано
  по документам: «Договор…», 12.09.2026» — подпись видна, даже если пункты
  не отмечены (этап был за шлагбаумом, когда договор подписали).

**Изменения схемы:** нет. **Затрагивает фронт:** `PATCH /api/documents/:id/status`
отвечает `DocumentStatusChangeDto` с необязательным `stageChecklist`.

**Дата:** 25.09.2026

**25.09:** команда решила — включаем. Код выкладывается выключенным (`AI_ASSIST_PROVIDER=off`,

Правила уже знают, что горит: просрочка этапа, застой, продукт не выбран, нет показателей
программы, дефицит навыка. Но сводку для руководителя, письмо вузу и план на день
менеджер до сих пор пишет руками — пересказывает то, что система уже посчитала.
Помощник делает три черновика: **сводку по связке** (3–5 предложений: где она, что
мешает, что дальше), **письмо вузу по рекомендации** (что нужно от вуза и к какому сроку)
и **«что сделать сегодня»** (3–7 дел с одной строкой «почему»).

**Как это соотносится с запретом «ML-модели и LLM в бизнес-логике» (CLAUDE.md).**
Запрет не нарушается, и устроено всё так, чтобы его нельзя было нарушить:

- модель не принимает решений и не меняет данных. **Что** рекомендовать и **в каком
  порядке** — только правила (`recommendations.rules.ts`, `workflow.rules.ts`). Порядок
  дел на сегодня — та же `compareDraftsByImportance`, что у ленты рекомендаций;
  важность просроченного этапа — тот же `ruleOverdueStage` с теми же порогами;
- модель получает уже посчитанные факты и только переписывает их читаемым текстом.
  Ответ проверяется: пустой, отказ фильтра, письмо без подписи ИТ-Школы, список дел
  с другим числом пунктов — отбрасываются;
- без модели работает всё: тот же текст собирает детерминированный **шаблон из тех же
  фактов**. Выключена, не настроена, ошибка, таймаут, пустой ответ, лимит — шаблон
  и ответ 200. Сбой модели никогда не даёт 500;
- результат — черновик для человека. Ничего не отправляется и не сохраняется само,
  ничего не генерируется при открытии страницы — только по кнопке. Интерфейс всегда
  пишет, кто автор: «Черновик ИИ (YandexGPT) — проверьте перед отправкой» или
  «Шаблон без ИИ: помощник не подключён».

**Решение.**

- Провайдеры — `src/integrations/llm/`: интерфейс `LlmProvider` (system + user → текст),
  `YandexGptProvider` (Yandex Foundation Models, основной), `GigaChatProvider` (запасной),
  `DisabledLlmProvider` (выключено, без сети). Выбор — `AI_ASSIST_PROVIDER`
  (`off | yandexgpt | gigachat`), свой таймаут `AI_ASSIST_TIMEOUT_MS` (15 с), без повторов:
  человек ждёт у кнопки, а шаблон готов сразу. YandexGPT идёт через общий клиент
  интеграций (`requestJson` получил необязательные заголовки — `Api-Key` и `x-folder-id`),
  с заголовком `x-data-logging-enabled: false`. GigaChat — через встроенный `node:https`:
  только так Node принимает сертификат НУЦ Минцифры (`GIGACHAT_CA_CERT_PATH`) без новых
  зависимостей; токен доступа кэшируется до истечения.
- Модуль `src/modules/ai-assist/`: факты — из существующих сервисов (карточка связки,
  лента рекомендаций, `problemStageWhere` главной); шаблоны и сборка промптов — по одной
  функции на каждый черновик; лимит и кэш — в памяти процесса, как у ограничения
  попыток входа (`throttle.ts`).
- **Персональные данные в модель не уходят.** Каждая строка фактов и ответ модели
  проходят очистку (`ai-assist.privacy.ts`): «Ответственный: ФИО» из обоснования
  просрочки вырезается, почта и телефоны заменяются пометкой, ФИО сотрудников
  и контактных лиц вуза — словом «ответственный» или «представитель вуза» в любом
  падеже и с инициалами, «Фамилия И. О.» — даже если человека нет в базе. Официальные
  названия вузов не трогаются. Тест сверяет промпты со всеми ФИО, почтой и телефонами
  демо-набора из `prisma/seed.ts`.
- Лимит: 20 обращений к модели на пользователя в час; кэш одинаковых фактов — 10 минут
  (`AI_ASSIST_LIMITS`, TEMP). Ответ из кэша и шаблон лимит не расходуют.
- Права: сводка и «что сегодня» — `ANALYTICS`, письмо — `WRITE` (действие от имени
  ИТ-Школы). Представитель вуза — 403; чужое и несуществующее — 404, как везде.
- Журнал: `ai.draft` на каждую генерацию — кто, вид, объект, провайдер, модель или шаблон
  и почему. Текст промпта и ответа в журнал не пишется.
- Маршруты: `POST /api/cooperations/:id/ai-summary`, `POST /api/recommendations/:id/ai-letter`,
  `POST /api/ai/today` (docs/API_CONTRACT.md, раздел 10а).

**Почему российская модель.**

- **152-ФЗ, статья 12** — трансграничная передача персональных данных. Даже очищенные
  факты — сведения о работе с вузами; отправлять их за рубеж не нужно. YandexGPT
  и GigaChat работают в дата-центрах в России: **данные не покидают РФ, персональные
  данные в модель не передаются**. Соответствие 152-ФЗ этим не заявляется — это
  по-прежнему предмет отдельного аудита (SECURITY_LIMITATIONS.md).
- **Стенд уже в Yandex Cloud.** YandexGPT — тот же облачный контур, тот же договор

## 98. Четыре решения Артура: рейтинг от нуля, дефициты вне профиля, четыре статуса рекомендаций, права аналитика

**Контекст.** Сводный разбор слабых мест (Д2, Д3, Б2 и решение 7 по рекомендациям);
Артур подтвердил все четыре рекомендации 25.09.

**Рейтинг — нормирование от нуля.** `normalized = value / max` вместо
`(value − min) / (max − min)`: min-max ставил 0,0 программе со 150 заявками и вдвое
ронял рейтинг её вуза. Ноль — только у нуля. Баллы вузов в сценарии: ДГТУ 36,6,
КНИТУ-КАИ 47,7, МТУСИ 50,7, НГТУ 47,6, СПбГУТ 85,7 (было 7,5 / 23,4 / 28 / 22,7 / 79,1);
порядок прежний. Сравнение внутри уровня (бакалавриат с бакалавриатом) — после защиты.

**Дефициты — пометка «вне профиля».** Дефициты считаются против всего рынка, и магистратуре
ИИ «не хватало» Java и JavaScript. Пока профиля направления нет, в разрезе одной программы
непокрытый навык помечается `outOfProfile`, если его не преподаёт ни одна программа той же
укрупнённой группы направлений (первые две цифры кода), а для других категорий, кроме
языков программирования, — и навыки той же категории. Такой дефицит не критический, идёт
в конце, на радар не выносится, в пояснении сказано почему (`SKILL_PROFILE`, TEMP). Сводки
по вузу и по всем программам не меняются — «2 критических дефицита» на главной те же.
Ограничение: на демо-наборе ни одна программа группы 09 не преподаёт Python, поэтому у них
Python — «вне профиля». Профиль направления вручную — после защиты.

**Рекомендации — четыре статуса:** Новая → В работе → Выполнена / Отклонена. «Принята»
упразднена: переходов в неё нет (409), миграция перевела такие записи в «В работе»
со снятием даты решения, `db:verify` следит, чтобы она не появилась снова (27 правил).
Значение перечисления в базе осталось — удаление значения enum в PostgreSQL означало бы
пересоздание типа ради мёртвого значения.

**Аналитик — реальные права.** Новое право `ANALYTICS_WORK` (ADMIN, MANAGER, ANALYST):
пересобрать рекомендации, вести их статусы, загрузить рыночные данные. Раньше аналитик
по правам равнялся наблюдателю. Связки, этапы, документы, справочники и письмо вузу
от имени ИТ-Школы — по-прежнему только ADMIN и MANAGER; наблюдатель — только чтение.

**Изменения схемы:** нет (миграция данных `20260925170000_recommendations_four_statuses`
без изменения структуры). **Затрагивает фронт:** `SkillGapDto.outOfProfile`,

## 99. Настройки администратора: пользователи, журнал, смена пароля, статус ИИ

**Дата:** 25.09.2026 · **Статус:** в main (#100), на стенде с 25.09.
Номера 97 и 98 заняты параллельными ветками.

ТЗ, п. 5: «Администратор — настройка системы: пользователи, роли, справочники».
До этого учётные записи заводились и блокировались только в базе, а журнал действий
отдавался API, но не был виден нигде. Артур выбрал пункты 1, 2, 3 и 6.

**1. Вкладка «Пользователи» (только `ADMIN`).** Новые вкладки встали в «Настройки»
Серёжи в том же стиле — строками (решение 91), колонка разделов показывает их только
администратору. Маршруты: `POST /api/users`, `GET`/`PATCH /api/users/:id`,
`POST /api/users/:id/password-reset`; `GET /api/users` получил фильтр `isActive`
обратно совместимо — формы выбора ответственного не затронуты.

- **Пароль придумывает сервер** и отдаёт один раз: 14 знаков из 54 без похожих
  (`0/O/o`, `1/l/I/i`), `crypto.randomInt`, около 80 бит; в базе — хеш bcrypt.
  Администратор не придумывает пароль сам — «Qwerty123» для всех новичков был бы
  самым вероятным исходом. Ответы `/api/users/*` — `Cache-Control: no-store`
  правилом в `next.config.ts`: заголовок, выставленный в маршруте, общее правило
  `no-cache` перекрывало.
- **Правила — чистыми функциями** (`auth.rules.ts`), сервис собирает факты: себя
  не заблокировать и не лишить `ADMIN`; нельзя оставить систему без действующего
  администратора; `MANAGER`/`ADMIN` с открытыми связками или этапами не переводится
  в роль, которая не может быть ответственной (`RESPONSIBLE_ROLES`) — 409 «сначала
  передайте связки». Блокировать ответственного можно: связки остаются за ним,
  интерфейс предупреждает, сколько их. Правило `assertStaffResponsible` не менялось.
- **«Последний администратор» — в транзакции** с `SELECT … FOR UPDATE` по строкам
  действующих администраторов и изменяемого: два администратора, одновременно
  блокирующие друг друга, иначе оба видели бы «есть ещё один».
- **Вуз**: у представителя обязателен, у остальных запрещён — то же правило, что
  сверяет `db:verify`. Смена роли с представителя снимает вуз сама.
- **Блокировка действует сразу**: `getCurrentUser()` и так читает пользователя из базы
  с `isActive: true` на каждый запрос — выданная сессия перестаёт работать
  со следующего запроса.
- **Свой пароль сбросом не меняется** (409): только в личном кабинете с текущим паролем,
  иначе оставленная открытой сессия администратора давала бы его пароль одним щелчком.
- **Новый пароль снимает блокировку входа** этой учётной записи (`releaseAccount`
  в `throttle.ts`): новый пароль чаще всего просят именно после пяти неудач.

**2. Вкладка «Журнал действий» (только `ADMIN`).** Фильтров API хватило (сотрудник,
действие, тип объекта, период). Добавлено: список действий и типов объектов —
в контракт (`AUDIT_ACTIONS`, `AUDIT_OBJECT_TYPES`), подписи — в `labels.ts`;
тип `AuditAction` журнала теперь берётся из того же списка, поэтому действие без
подписи не соберётся (тест `labels.test.ts`). В записи — `cooperationId` для этапа
и пункта чек-листа: своей страницы у них нет, ссылка ведёт на связку. Подробности —
кратко и без идентификаторов (`settings/audit-view.ts`); персональных данных
в журнале нет по правилу записи.

**3. Смена своего пароля** — `POST /api/me/password`, любая роль, только для себя.
Новый пароль не короче 10 символов, не длиннее 72 байт (предел bcrypt), не равен
текущему и почте. Текущий пароль проверяется через `throttledAttempt` — тот же
счётчик, что у входа: иначе форма стала бы обходом ограничения перебора для того,
кто завладел сессией. Неверный текущий — 422, исчерпаны попытки — 403.

**Признак «пароль временный» без изменения схемы.** Плашку «смените временный пароль»
в кабинете (`passwordTemporary` в `GET /api/me`) даёт последнее событие пароля
в журнале: `user.create`/`user.password.reset` — временный, `user.password.change` —
свой. Поле `password_temporary` в `users` было бы надёжнее (журнал чистится через год,
сбой записи журнала не ломает операцию), но ради необязательной подсказки схему
не трогали — вопрос к Тиграну, если понадобится обязательная смена.

**6. Статус ИИ-помощника** — блок `aiAssist` в `GET /api/integrations/status`:
провайдер, имя, готовность, модель, причина. Берётся из `LlmProvider.info()`,
а не из настроек: ключ и каталог в ответ не попадают — тест ищет в ответе любой
их фрагмент длиной 6 знаков. Прежние поля ответа не менялись.

**Чего нет (SECURITY_LIMITATIONS, раздел 2).** Смена и сброс пароля не завершают
уже выданные сессии: сессия — JWT на 8 часов, отзыва нет. Блокировка их закрывает,
но после разблокировки не истёкшая сессия снова действует. Решение — версия пароля
в токене и в базе; это поле, согласование с Тиграном (закрыто решением 109). Обязательной смены временного
пароля и второго фактора для администратора нет.

**Проверено.** Модульные тесты правил, сервиса и статуса ИИ; пробник — весь путь
через настоящий вход NextAuth: заведение → вход по временному паролю → смена →
старый не подходит → блокировка (вход и сессия не работают) → разблокировка → сброс,
и 403 менеджеру и представителю вуза на каждом маршруте администратора.

эксперты — одновременно и под одними и теми же демо-учётками. Один проверяющий, сменивший

## 100. Проверка «не робот» на входе: задача на вычисление после трёх неудач

**Дата:** 25.09.2026 · **Статус:** ветка `feat/login-captcha`.

**Зачем.** Ограничение перебора (решения 40, 53) закрывает вход после пяти неудач с адреса
и после пятидесяти по учётной записи со всех адресов. Между «первой опечаткой» и
«вход закрыт» ничего не было: перебор с многих адресов шёл по одной учётной записи
с полной скоростью до общего потолка, а на стенде под одной учётной записью входят
все проверяющие (`SHARED_DEMO_ACCOUNTS`, решение 99).

**Что сделано.**
- **Когда.** После трёх неудач подряд по учётной записи с одного адреса или десяти
  по ней со всех адресов за час (`LOGIN_CAPTCHA`, TEMP) вход отвечает кодом
  `captcha_required` — до запроса к базе и bcrypt, без засчитанной неудачи.
  Удачный вход требование снимает. Закрытый вход проверку не просит: человеку важнее
  узнать, что ждать 15 минут. Счётчик адреса по всем учётным записям её не включает —
  за одним адресом бывает целая аудитория.
- **Что за задача.** Сервер (`src/shared/auth/captcha.ts`) загадывает число
  от 0 до 100 000 и отдаёт SHA-256 от «соль + число» с подписью HMAC ключом,
  производным от `AUTH_SECRET`. Браузер перебирает числа в фоновом потоке
  (`captcha.worker.ts`, WebCrypto) — в среднем 50 тысяч хешей, доли секунды на ноутбуке,
  секунда-две на телефоне — и повторяет вход сам: второй раз «Войти» нажимать не нужно.
- **Проверка решения** — один хеш и одна подпись, синхронно: решение помечается
  использованным до первого `await`, два одновременных запроса с одним решением
  не пройдут оба. Срок жизни — 5 минут, внутри соли. Длина срока в соли фиксирована
  (13 цифр) и закрыта точкой: иначе цифру можно было бы перенести из числа в срок
  с тем же хешем и продлить решение в десять раз (известная ошибка такой схемы).
- **Почему своя, а не Yandex SmartCaptcha или reCAPTCHA.** Не нужны ключи и договор,
  данные посетителя никуда не уходят (152-ФЗ, reCAPTCHA — ещё и передача за рубеж),
  вход не зависит от доступности чужого сервиса все две недели проверки стенда.
  Картинок нет — задача доступна и незрячим, и с экранным чтецом.
- **Маршрут** `GET /api/login-challenge` — без входа, `Cache-Control: no-store`.
  Экран входа показывает строку состояния «Проверяем, что вход не автоматический…» →
  «Проверка «не робот» пройдена»; подпись под формой называет правило.

**Честная граница** (docs/SECURITY_LIMITATIONS.md): программа без браузера решает
такую задачу в десятки раз быстрее — задача удорожает перебор, а останавливает его
по-прежнему ограничение попыток. Использованные решения, как и счётчики, живут в памяти
процесса.

**Проверено.** Модульные тесты `captcha.test.ts` (решение, повтор, подделка подписи,
истёкшее, перенос цифры в срок, мусор в поле) и `throttle.test.ts` (когда нужна);
`npm run probe` — три неудачи, затем `captcha_required`, решённая задача пускает к проверке
пароля, повтор и подделка — снова `captcha_required`, пятая неудача закрывает вход.

## 101. Демо-данные во всех статусах; «нет данных по программе» не для отменённых связок

## 102. Личные уведомления в Telegram: «что горит у меня» — в личку

**Дата:** 25.09.2026 · **Статус:** ветка `feat/telegram-notifications`, по умолчанию выключено.
Номер 101 занят параллельной веткой.

**Зачем.** Лента в колокольчике (решение 37) видна, только когда сотрудник открыл систему.
Менеджеру нужно, чтобы просрочка сама пришла туда, где он и так читает сообщения.

**Что сделано.**
- **Привязка без хранения кодов.** «Подключить» в личном кабинете (`POST /api/me/telegram`)
  отдаёт ссылку `t.me/<бот>?start=<токен>`. Токен — 4 байта срока, 12 байт HMAC-SHA-256
  (ключ производный от `AUTH_SECRET`, как у задачи «не робот», решение 100) и id
  пользователя, base64url: 55 символов при пределе Telegram 64 и алфавите `A–Z a–z 0–9 _ -`.
  Живёт 15 минут, подделать чужой или продлить свой нельзя. «Одноразовость» — список
  использованных токенов в памяти процесса до конца их срока (`telegram.link-token.ts`).
  Таблицы кодов нет: хватает подписи.
- **Таблица `telegram_links`** — `user_id` (уникален, CASCADE), `chat_id` (уникален,
  строкой: до 52 бит), `username?`, `linked_at`. Один пользователь — один чат, один чат —
  один пользователь: при новой привязке чат снимается с прежней учётной записи, иначе
  `/today` не знал бы, чью сводку показывать. Привязка без истории, поэтому CASCADE,
  а не SET NULL, как у остальных ссылок на пользователя. Миграция `20260925200000_telegram_links`,
  схема больше не менялась.
- **Вебхук** `POST /api/telegram/webhook`. Подлинность — `X-Telegram-Bot-Api-Secret-Token`
  против `TELEGRAM_WEBHOOK_SECRET`, `timingSafeEqual` по SHA-256 обоих значений; секрет
  не задан — 403 всем. Ответ 200 сразу, команда — после ответа (`after` из `next/server`):
  Telegram, не дождавшись ответа, повторяет обновление. Нераспознанное тело — тоже 200,
  повтор его не исправит. Один `update_id` выполняется один раз (память, 1000 последних).
  Команды: `/start <токен>`, `/today`, `/stop`, остальное — справка; в группах бот не
  работает. Запрос Telegram приходит без `Origin` и проходит `assertSameOrigin` как любой
  не-браузерный — сама проверка не менялась.
- **Сводка — из существующих правил.** Этапы: связки пользователя (ответственный за этап
  или за связку — как «Дела на сегодня» и главная), проблемные по `problemStageWhere`
  (счётчик главной) плюс срок в окне предупреждения; раскладку делают `isOverdue`,
  `isDueSoon`, `isLockedByControlPoint` из `workflow.rules`. Рекомендации — тот же запрос,
  что у «Дел на сегодня» (`findOpenRecommendationsOf`), подписи объектов — `toRecommendationDtos`;
  рекомендация о просрочке уже показанного этапа не дублируется, как в ленте. Текст —
  чистая функция `buildDigest` (`telegram.rules.ts`), до 5 пунктов в разделе
  (`TELEGRAM_DIGEST`, TEMP), ссылки на этап и рекомендацию стенда по `AUTH_URL`
  (иначе `APP_BASE_URL`), адреса страниц — из `src/ui/lib/links.ts`, одно место на систему.
- **Что уходит в Telegram** — только названия вузов, программ, этапов, рекомендаций
  и сроки. Ни ФИО, ни почт, ни телефонов, ни причин блокировки (в них пишут что угодно).
  Формулировка для политики — docs/PRIVACY.md.
- **Рассылка** `npm run telegram:digest` (`--dry-run` — только печать): всем привязанным
  активным сотрудникам с правом аналитики, пустые сводки не шлются. Расписание — cron
  владельца сервера через сервис `migrate` (docs/DEPLOY.md); сам cron не ставился.
- **Доставка** — `src/integrations/telegram`: `sendMessage`, таймаут `INTEGRATION_TIMEOUT_MS`,
  одна повторная попытка на сетевой сбой, 5xx и 429 (пауза по `retry_after`, не больше 5 с),
  403 «бот остановлен» — без повтора. Исключений наружу нет; в журнал — только вид сбоя,
  без токена, текста и чата.
- **Сеть Yandex Cloud.** Оттуда `api.telegram.org` по имени не отвечает, запасной
  `149.154.167.220` — отвечает. `TELEGRAM_API_IP` ведёт соединение на IP, а SNI и Host
  остаются `api.telegram.org`, сертификат проверяется на это имя (проверено вживую:
  по IP с правильным именем TLS проходит, с чужим именем — отказ сертификата).
  Сделано на `node:https` — общий транспорт `src/integrations/https-transport.ts`, прежде
  лежавший в `llm/` для GigaChat, получил параметр `connectAddress`. Пакет undici не нужен.
- **Выключатель.** Бот работает, только когда заданы `TELEGRAM_BOT_TOKEN`,
  `TELEGRAM_BOT_USERNAME` и `TELEGRAM_WEBHOOK_SECRET`. Иначе блок в кабинете пишет
  «Не настроено администратором», ссылка — 502, вебхук ничего не делает, рассылка выходит.
- **Права.** Состояние и отключение — любая роль о себе. Подключение и сводка — право
  `ANALYTICS`: представителю вуза сводки нет (в его кабинете нет ни аналитики, ни
  рекомендаций), блок у него скрыт. Журнал: `telegram.link`, `telegram.unlink` без чата и ника.

**Честные границы** (docs/SECURITY_LIMITATIONS.md): одноразовость токена держится в памяти
одного процесса — после перезапуска токен можно предъявить повторно до конца его
15 минут; кто получил чужую ссылку за эти минуты, привяжет свой чат к чужой учётной
записи (как с любой ссылкой-приглашением). Telegram — иностранный сервис: сводка уходит
за рубеж, поэтому только по действию самого сотрудника и без персональных данных третьих лиц.

**Проверено.** `telegram.test.ts` — токен (срок, подделка подписи, чужой id, продление,
мусор, повтор), секрет вебхука, разбор команд, схема обновления, сборка сводки;

## 103. Пункт вуза в чек-листе: при представителе отмечает вуз, без него — сотрудник с пометкой

**Дата:** 25.09.2026 · **Статус:** ветка `feat/university-item`. Закрывает R-07
в SECURITY_LIMITATIONS.md.

**Проблема.** Пункт этапа 7 «Вуз подтвердил получение материалов» — утверждение второй
стороны. Кабинет вуза сотруднику запись закрыл (право `UNIVERSITY_PORTAL_WRITE`), но через
`PATCH /api/workflow/tasks/:id` сотрудник отмечал этот пункт наравне с остальными — и в
системе выглядело, будто вуз подтвердил.

**Решение.**
- **Признак в данных, а не по заголовку.** `tasks.is_university_item` (миграция
  `20260925210000_task_university_item`) ставится из конфига (`universityItem: true`
  в `workflow.config.ts`) при создании этапов: `buildStages` и сид. Существующим пунктам —
  миграцией по номеру этапа 7 и заголовку. Заголовок хранится копией и может разойтись
  с конфигом — признак от этого не зависит.
- **Правило** (`workflow.rules`: `staffMarkRule`, `assertStaffTaskMark`), в `toggleTask`:
  - у вуза связки есть действующий представитель (`UNIVERSITY_REP`, `isActive`) — сотрудник
    ни отметить, ни снять не может: 403 «Этот пункт отмечает представитель вуза в кабинете
    вуза». Снятие тоже запрещено: снять за вуз его подтверждение — такое же решение за вуз;
  - представителя нет — отметка только с `confirmationNote` 3–500 символов («письмо от
    12.09»), иначе 422 `VALIDATION_ERROR` по полю `confirmationNote`. Снять можно без
    пометки — снятие ничего не утверждает (как у контрольной точки), пометка стирается.
  - Представитель вуза отмечает как раньше — `portal.service.confirmMaterial`, та же
    `setTaskDone`; пометку стирает, если она была.
- **Где пометка.** Отдельная колонка `tasks.confirmation_note`, а не комментарий истории
  этапа. История этапа — это смены статуса (`to_status` обязателен): запись «В работе →
  В работе» с пометкой показалась бы сменой статуса в истории этапа, в ленте событий вуза
  и в уведомлениях представителя, а пометка — внутренний текст. В пункте пометка живёт
  ровно столько, сколько отметка, видна рядом с ней в карточке этапа и проверяется
  `db:verify` одним запросом. CHECK `tasks_confirmation_note_check`: пометка только
  у отмеченного пункта вуза, 3–500 символов.
- **Журнал.** Правило модуля portal: свободный текст в журнал не пишется (в нём бывают ФИО
  и телефоны). Отметка за вуз пишется отдельным действием
  `task.university-item.confirm-by-staff` с `stageNumber` и `noteLength`, без текста.
- **DTO пункта:** `isUniversityItem`, `staffMarkRule` (`ALLOWED` / `NOTE_REQUIRED` /
  `UNIVERSITY_ONLY`) и `confirmationNote` — фронт заранее знает, спросить пометку или
  заблокировать чекбокс. Представителю вуза `confirmationNote` — `null`: внутренняя
  заметка, как комментарий к этапу (решение 9). Наличие представителя берётся тем же
  запросом этапов (`users` вуза, `take: 1`), без отдельного похода на каждый пункт.
- **Групповые операции.** Выпуск версии продукта (`products`) работает с этапом 12:
  добавляет свой пункт и переоткрывает этап, пункты этапа 7 не трогает. Переоткрытие
  этапа 7 (`COMPLETED → IN_PROGRESS`) отметки не снимает. Подпись документов отмечает
  только пункты этапа 6. Других путей отметки пункта вуза нет.
- **Уже отмеченные пункты** (стенд до перезаливки) не представителем — миграция ставит
  честную пометку «Отмечено сотрудником до решения 103: основание не записывалось»,
  а не выдуманное «письмо»: иначе `db:verify` на стенде упал бы на отметках, сделанных
  по прежним правилам.
- **Сид.** У закрытых этапов 7 вузов без представителя — пометка «Подтверждено письмом
  вуза (демонстрационные данные)»; у СПбГУТ пункт отмечен представителем
  (rep@spbgu.example.invalid) с записью `portal.material.confirm` в журнале.
- **Фронт** (`StageCard`): при `NOTE_REQUIRED` отметка открывает окно с полем «Чем
  подтверждено» (существующие `Modal` и `Textarea`); при `UNIVERSITY_ONLY` чекбокс
  неактивен с подписью «Отмечает представитель вуза в кабинете вуза»; пометка показана
  рядом с автором отметки. Подпись ключа `noteLength` во вкладке журнала.

**Проверки.** `db:verify` — два правила: признак стоит ровно у пунктов вуза из конфига;
отмеченный пункт вуза отметил представитель этого вуза или есть пометка. Пробник, шаг
«2в»: сотрудник при представителе — 403 (и на снятие), представитель в кабинете — 200,
у вуза без представителя без пометки — 422 по полю, с пометкой — 200 и пометка в пункте,
в журнале длина без текста, снятие без пометки — 200. Сквозной сценарий отмечает пункт
вуза своей связки с пометкой.

**Ограничения.** Представитель проверяется до очереди связки (`lockCooperation`): заведённый
в ту же секунду может разминуться с отметкой сотрудника. Пометку система не сверяет с
письмом — это слово сотрудника, но теперь записанное и с автором.

## 104. Индексы на все внешние ключи

**Дата:** 25.09.2026 · **Статус:** ветка `db/fk-indexes`, миграция
`20260925210100_fk_indexes`. **На согласование Тиграну** (PROGRESS, «Что дальше», п. 3).

**Зачем.** PostgreSQL не создаёт индекс на колонку внешнего ключа сам. У 14 ключей
из 40 его не было — проверено запросом к `pg_constraint` и `pg_index` (запрос —
DATABASE_SCHEMA, «Индексы на внешние ключи»). Без индекса при удалении строки, на
которую ссылаются, проверка ключа читает ссылающуюся таблицу целиком. На
пользователя ссылаются 13 ключей, у 10 из них индекса не было. Приложение сейчас
пользователей и программ не удаляет (блокировка и архив), но удаляет очистка
`volume.ts` и может удалить ручная операция в базе, а списки документов и встреч
фильтруются по программе (`documents.repo`, `meetings.repo`).

**Решение.** `@@index` на каждую из 14 колонок в `schema.prisma`, одна миграция
из `prisma migrate dev --create-only`: в ней только 14 `CREATE INDEX`, данные
и ограничения не меняются; `prisma migrate diff` после применения пуст. Обычный
`CREATE INDEX`, не `CONCURRENTLY`: миграция идёт в транзакции, на объёме замера
она применилась меньше чем за секунду. Откат — `DROP INDEX` из шапки миграции.

**Замер** на отдельной базе: `volume.ts` на 1000 вузов (4000 программ, 3000 связок,
42 000 этапов) и SQL-вставкой строки в таблицы с этими ключами — 126 000 записей
истории этапов, 126 000 пунктов чек-листа, 15 000 документов, 45 000 записей их
истории, 15 000 встреч, 30 000 участников. Время выполнения по `EXPLAIN ANALYZE`,
медиана 6 прогонов в прогретой сессии; «без индексов» — те же индексы удалены
в откатываемой транзакции:

| Запрос | Без индексов | С индексами |
| --- | --- | --- |
| Встречи программы, сортировка по дате (как `meetings.repo`) | 0,63 мс, полный просмотр 15 000 строк | 0,008 мс, `meetings_program_id_idx` |
| Число документов программы | 0,90 мс | 0,006 мс, только индекс |
| Удаление пользователя без ссылок на него | 19,6 мс (13 проверок ключей) | 0,12 мс |
| Удаление программы без связок | 1,5 мс | 0,05 мс |

`npm run bench` (15 прогонов, тот же собранный сервер до и после миграции): разницы
нет, всё в пределах шума ±4 мс, самый медленный сценарий 20 и 23 мс. Сценарии замера
по этим колонкам не ищут. **Выигрыша по времени страниц на текущем объёме нет**;
смысл — удаления и каскады, фильтры по программе и рост данных. Цена — 3,6 МБ
индексов на объёме замера и запись в 14 индексов при вставке.

**Попутно.** `volume.ts` падал с 24.09 на CHECK `workflow_stages_completed_result_check`:
завершённые этапы заводились без результата. Теперь с результатом.

**Изменения схемы:** 14 индексов. **Затрагивает фронт:** нет.

## 105. Подписка на календарь сроков и встреч (.ics)

**Дата:** 25.09.2026 · **Статус:** ветка `feat/calendar-ics`, только API; кнопку делает фронт.

**Зачем.** Сроки этапов и встречи сотрудник видит только внутри SkillLink. Личная
ссылка-подписка кладёт их в его рабочий календарь рядом с остальными делами, и
календарь сам напоминает о сроке.

**Что сделано.**
- `GET /api/calendar/<токен>.ics` — лента iCalendar **без входа**: календарные приложения
  cookie не шлют. `text/calendar; charset=utf-8`, `Cache-Control: no-store` (и в маршруте,
  и в `next.config.ts` — иначе общее правило `no-cache` перекрыло бы заголовок маршрута).
- В ленте: сроки незавершённых этапов действующих связок, где сотрудник ответственный
  за этап **или** связку, — событие на весь день в московскую дату срока, заголовок
  «Срок: этап N «название» — вуз (краткое имя), программа», у просроченного — «[Просрочен]»,
  у не начатого с прошедшим сроком — «[План сдвинут]» (правила `isOverdue` / `isPlanShifted`,
  как у карточки связки). Контрольный этап 14 не попадает — его закрывает система (как
  в ленте уведомлений). Встречи, где он ответственный или участник: время, тема, формат.
  В `URL` и `DESCRIPTION` — ссылка на карточку связки (с `?stage=`), вуза или программы
  от `AUTH_URL` → `APP_BASE_URL`, не из заголовков запроса.
- **Без ПД**: участники встреч, контакты, ФИО сотрудников, комментарии и результаты
  в ленту не выбираются вовсе (`calendar.repo.ts`), а не вырезаются после.
- `GET`/`POST`/`DELETE /api/me/calendar` — статус (без адреса), выпуск или перевыпуск
  (адрес — один раз, `201`), отзыв. Право `CALENDAR`: ADMIN, MANAGER, ANALYST, VIEWER;
  представителю вуза — 403: сроки этапов для него — внутренняя кухня (решение 9).
- Таблица `calendar_feeds` (`user_id` PK/FK CASCADE, `token_hash` UNIQUE + CHECK
  на 64 hex-знака, `created_at`). Токен — 32 случайных байта base64url, в базе SHA-256.
  Индексы `meetings.responsible_id` и `meeting_participants.user_id` — под выборку встреч.
  Миграция `20260925210200_calendar_feeds`; ждёт согласования с Тиграном.
- Журнал: `calendar.issue` (`payload.replaced`) и `calendar.revoke`, объект `User`, без токена.

**Почему так.**
- **Хеш без соли и без HMAC.** Токен — 256 случайных бит, а не пароль: подбирать по хешу
  нечего, соль ничего не добавляет. Ключ, производный от `AUTH_SECRET` (как у задачи
  «не робот», решение 100), здесь вреден: смена секрета сессий молча сломала бы все
  подписки, а выигрыша нет.
- **Одинаковый 404** на неизвестный, отозванный токен, заблокированного владельца и
  владельца, ставшего представителем вуза: по ответу не узнать, существовал ли токен.
  Ограничения попыток нет — перебрать 2²⁵⁶ нельзя.
- **Генератор свой**, без зависимости: нужен десяток свойств. Проверено тестами: CRLF,
  экранирование `\ ; ,` и переводов строк, свёртка по 75 октетов без разрыва UTF-8,
  пустая лента, стабильные UID (`stage-<id>@skilllink`, `meeting-<id>@skilllink`).
- **Предел 500 событий** (TEMP, `CALENDAR_FEED`): лента собирается на каждый запрос
  календаря. Этапы и встречи выбираются двумя половинами от «сейчас» — при переполнении
  уходят самые далёкие от сегодняшнего дня. Прошедшие встречи — за 60 дней (TEMP),
  длительность встречи — 60 минут (TEMP: конца встречи в системе нет).
- **Флага `canUseCalendar` в `GET /api/me` нет**: новое обязательное поле ломало тест
  фронта (`src/ui/layout/navigation.test.ts`), который трогать нельзя. Фронт показывает
  блок сотрудникам (роль не `UNIVERSITY_REP`); флаг можно добавить вместе с фронтом.

**Ограничения** (SECURITY_LIMITATIONS.md, PRIVACY.md 2.3): ссылка бессрочна до отзыва;
снятие блокировки снова открывает прежнюю ссылку; токен виден в журнале запросов Caddy —
фильтр для `/api/calendar/*` не добавлен; зарубежные календари получают сроки и темы

## 109. Отзыв выданных сессий: версия сессий пользователя

**Дата:** 25.09.2026 · **Статус:** ветка `sec/session-revocation`.

Закрывает P1 из SECURITY_LIMITATIONS «Отзыва выданных сессий при смене пароля»: сессия —
JWT на 8 часов, смена или сброс пароля её не завершали, а после разблокировки ещё не
истёкшая сессия снова действовала.

**Решение.**
- **Поле `users.session_version`** (целое, по умолчанию 0, CHECK ≥ 0). Кладётся в JWT при
  входе (`authorize` → колбэк `jwt`). `getCurrentUser()` и так перечитывает пользователя
  из базы на каждом запросе — тем же запросом берётся версия и сверяется с токеном
  (`isSessionCurrent`, `src/shared/auth/session-version.ts`). Лишнего запроса нет.
- **Версия +1** при смене своего пароля и сбросе пароля администратором (в
  `auth.repo.setPasswordHash`, атомарный `increment` в том же `UPDATE`), при блокировке
  и смене роли (`auth.rules.revokesSessions`, в транзакции `updateWithGuard`). ФИО,
  должность, вуз и разблокировка сессии не трогают; разблокировка не возвращает старые.
- **Отозванная сессия — 401**, текст «Сессия больше не действует: пароль, роль или доступ
  изменились. Войдите заново». Фронт на любой 401 уже снимает cookie и ведёт на
  `/login?reauth=1` (решение 48) — фронт не менялся. **И в демо-режиме:** раньше сессия
  заблокированного или удалённого пользователя в демо-режиме молча становилась
  демо-менеджером (`fromSession` возвращал `null`). Теперь к демо-пользователю уходит
  только запрос без cookie сессии — та же логика, что у «сбой чтения сессии — не
  «сессии нет»». Непрочитываемая cookie (чужой секрет, мусор) по-прежнему считается
  отсутствием сессии: её разбирает NextAuth и возвращает `null`.
- **Токен без версии** (выдан до выкладки) считается версией 0, как и все строки после
  миграции, — выкладка никого не разлогинивает (проверено: токен старого формата →
  `/api/me` 200). Нечисловое значение в токене — −1, не совпадает ни с чем.

**Текущая сессия при смене своего пароля — переоформляется, а не разлогинивается.**
Варианты: (а) честно разлогинить и сказать «войдите с новым паролем»; (б) переоформить
токен на новую версию. Выбран (б) штатным серверным способом NextAuth v5 —
`unstable_update` из маршрута `POST /api/me/password`: он вызывает колбэк `jwt`
с `trigger: 'update'` на cookie текущего запроса и кладёт новую cookie в ответ.
Сложность: тот же колбэк вызывает и клиент (`POST /api/auth/session` с любыми данными),
и если бы колбэк просто перечитывал версию из базы, украденная cookie «продлевала» бы себя
сама. Поэтому данные обновления — **подписанное разрешение** `{ userId, from, to, срок }`
(HMAC-SHA256 секретом `AUTH_SECRET` с отдельной областью подписи, живёт минуту, клиенту не
отдаётся); колбэк меняет версию, только если подпись верна, пользователь тот же и версия
в токене равна `from`. Отказ продления — сбой в сторону «выйти»: ответ `sessionRenewed:
false`, следующий запрос — 401, фронт уводит на вход (вариант (а) как запасной). Пробник
проверяет и продление, и что поддельное обновление от клиента отозванную сессию не оживляет.
`unstable_update` в названии — «нестабильное API» библиотеки (версия зафиксирована
`5.0.0-beta.32`); при обновлении NextAuth проверить шаг пробника «сменивший пароль остаётся
в системе».

**Блокировка отзывает подписку на календарь** (решение 105) — в той же транзакции, что
и снимает доступ: `calendarRepo.remove(id, tx)` через новый параметр `alongside` у
`updateWithGuard`; запись `calendar.revoke` с `{ reason: "user.block" }` от имени
администратора тем же клиентом транзакции. Раньше лента заблокированного отдавала 404
только пока он заблокирован — после разблокировки старая ссылка оживала.
**Место для Telegram:** модуля привязки Telegram в main нет; когда он появится, отвязка
добавляется в тот же колбэк `alongside` в `auth.service.updateUser` (там оставлен
комментарий) — всё, что даёт доступ без сессии, закрывается при блокировке одной транзакцией.

**Что это ограничивает.**
- Версия общая на все сессии пользователя: закрыть одно устройство, оставив другие, нельзя
  (списка сессий нет — это JWT). Для этого нужна таблица сессий — P2.
- `reseed` пересоздаёт пользователей: сессии заведённых пользователей и так отваливаются
  (id другой), общих демо-учёток версия не касается — их пароль, роль и доступ не меняются

- Переоформление — одна вкладка: другие вкладки того же браузера делят cookie и получают

- Короткое окно: запрос той же вкладки, ушедший между записью новой версии и получением
  новой cookie, получит 401 и уведёт на вход. Практически недостижимо из формы смены пароля.

**Изменения схемы:** `users.session_version` + CHECK, миграция
`20260925230000_user_session_version` (откат в комментарии). **Затрагивает фронт:**
`PasswordChangedDto.sessionRenewed` (новое поле, прежнее не менялось); 401 с отозванной
сессией обрабатывается уже существующим `leaveToLogin`.

## 110. Один ключ названия навыка: индекс базы, загрузка рыночных данных, текст рекомендаций

**Дата:** 25.09.2026 · **Статус:** ветка `feat/skills-consistency`, миграция
`20260925230100_skill_name_key_unique` — на согласование Тиграну.

Решение 107 сделало «ML Ops» и «MLOps» одним навыком только в справочнике и только в коде.
Три места жили по другим правилам: база пропускала дубль, записанный в обход сервиса;
загрузка рыночных данных сравнивала названия через `toLowerCase()` — «ML Ops» из источника
уходил в «неизвестные»; после объединения рекомендация дубля до следующей генерации
называла навык, которого в справочнике уже нет.

**1. Уникальность держит база.** Уникальный индекс по выражению `skills_name_key_ci`:

```sql
regexp_replace(lower(normalize(name, NFKC) COLLATE "ru-x-icu"),
               '[\t\n\v\f\r    -     　﻿]', '', 'g')
```

- **Почему не `lower(regexp_replace(normalize(name, NFKC), '\s', '', 'g'))`.** Сверка с
  `skillNameKey` на 54 трудных примерах нашла расхождения. `\s` PostgreSQL зависит от
  сортировки: с ICU он считает пробелом U+0085 и U+001C–U+001F и не считает U+FEFF, в JS
  наоборот; с сортировкой `"C"` кириллица не строчится вовсе. Порядок: код строчит до
  удаления пробелов, и греческая «Σ» в конце слова становится «ς» только пока пробел на месте.
  Итог — выражение подогнано под код, код не менялся: `normalize` → `lower` по ICU с
  русской локалью (как `toLocaleLowerCase('ru')`) → список пробельных знаков, ровно
  `\s` из JavaScript. `normalize`, `lower`, `regexp_replace` в PostgreSQL 16 неизменяемые
  (`IMMUTABLE`), для индекса годятся; база в UTF8 — `normalize` доступна. На всех
  примерах ключи совпали.
- **Проверка расхождения впредь.** Примеры — `skill-name-key.samples.ts`: модульный тест
  сверяет с ними код, `db:verify` — выражение индекса, взятое из каталога базы
  (`pg_get_expr`), на примерах и на всех названиях справочника. Правило `db:verify` «названия
  не повторяются» убрано как лишнее — дубль теперь не запишется; вместо него правило
  «ключ названия в базе совпадает с кодом» (правил по-прежнему 24, с демо-набором 30).
  Проверено: если заменить `skillNameKey` на `toLowerCase()` без NFKC, `db:verify` называет три примера.
- **Prisma.** Индексы по выражению в `schema.prisma` не описываются — у модели `Skill`
  комментарий. `prisma migrate diff --from-config-datasource --to-schema` после применения
  пуст: индекс он не видит и удалить не предлагает; `migrate status` — «up to date».
- **Дубли в данных.** Перед созданием индекса миграция ищет их тем же выражением и падает
  с понятным текстом и списком (до 20 групп), ничего не меняя: какой навык оставить, решает
  человек. На демо-данных дублей нет. Проверено на копии базы с «ML Ops» и «mlops»:
  `migrate deploy` падает с «В справочнике навыков есть названия, совпадающие без учёта
  регистра и пробелов: «ML Ops», «mlops»»; после разбора — `migrate resolve --rolled-back`
  и повторный `deploy` проходят.
- **Блокировка снята.** `pg_advisory_xact_lock` из решения 107 был заменой индекса. Теперь
  код проверяет название до записи (чтобы 409 называл навык, с которым совпало), а
  одновременные запросы, прошедшие проверку оба, останавливает индекс: P2002 превращается
  в тот же 409 с названием сохранённого. Проверено отладочным выводом на шести
  одновременных POST: один 201, пять отказов индекса `skills_name_key_ci` → 409.
  Точный `name UNIQUE` оставлен — удалять его незачем.

**2. Загрузка рыночных данных — тем же ключом.** `loadSkillsByName` строит справочник
по `skillNameKey`, сервис ищет по нему же. Неизвестные навыки перечисляются по ключу один
раз, в написании источника. Модуль импорта CSV (`src/modules/import`) навыков не
сопоставляет — вузы и программы; других мест сопоставления навыка по названию нет.

**3. Текст рекомендаций после объединения — в той же транзакции.** Варианты: пересобрать
рекомендации по навыкам или поправить текст. Пересборка — это генерация целиком: все
правила, закрытие неактуальных, право `ANALYTICS_WORK`, не у справочника. Выбрана правка:
`renameSkillInRecommendation` (recommendations.rules.ts) меняет ровно то, что правило
подставило, — навык в заголовке, фразу «продукт даёт навык «…»» в описании и
`relatedData.skillId`; продукты, программы и обоснование от имени навыка не зависят.
Шаблоны заголовка и фразы — одни на правило и на правку, поэтому результат совпадает
с пересборкой (тест). Прежнее имя берётся из заголовка, а не с навыка; текст не по шаблону
не трогается. Та же правка — при переименовании навыка: иначе после `PATCH` лента
называла бы навык старым именем. Отклонённые рекомендации тоже правятся: это не пересмотр
решения, а имя того же навыка.

**Проверки.** Модульные: ключ на примерах; гонка и прочие ошибки в репозитории с
подменённой базой; перенос рекомендации и текст — до удаления дубля; загрузка с «ML Ops»,
«machine   LEARNING», неразрывным пробелом. Пробник: четыре одновременных создания в
разном написании — один 201, три 409 с названием; два одновременных переименования в одно
название — 200 и 409; демо-навык временно переименован в «СЕТЕВЫЕТехнологии» — загрузка
демо-источника сопоставляет «Сетевые технологии», неизвестных и новых строк нет;
демо-навык с рекомендацией объединён в пробный — рекомендация называет пробный и ссылается
на него; пробный переименован обратно — текст прежний.

**Изменения схемы:** уникальный индекс по выражению `skills_name_key_ci` на `skills`.
**Затрагивает фронт:** полей не меняет. `unknownSkills` синхронизации без повторов;
рекомендации по навыку после объединения и переименования приходят с новым текстом сразу.

## 111. Учёт правового основания обработки ПД контактов вузов и согласий

**Дата:** 25.09.2026 · **Статус:** ветка `feat/consent-tracking`, только API — экран делает фронт.

**Контекст.** SECURITY_LIMITATIONS, P1: «Фиксации согласия субъекта ПД нет» — концепция
обещала «факт и дата согласия субъекта фиксируются». PRIVACY.md, раздел 3, оценивает основание
для контактов вузов как **законный интерес оператора по договору с вузом** (п. 7 ч. 1 ст. 6):
сторона договора — вуз, не контакт. Значит, согласие — не общий случай, а одно из оснований.
Учёт честно строится вокруг основания, а согласие — его частный случай.

**Модель.** У `contacts` восемь колонок: `legal_basis` (`LEGITIMATE_INTEREST` п. 7,
`CONTRACT` п. 5, `CONSENT` п. 1, `OTHER`; NULL — не зафиксировано), `consent_status`
(`NONE`/`OBTAINED`/`WITHDRAWN`), `consent_obtained_at`, `consent_form` (письменное,
электронное, устное с подтверждением письмом), `consent_withdrawn_at`, `basis_reference`,
`withdrawal_reference` (где лежит документ — не файл), `basis_updated_at`. Согласованность
держат четыре CHECK; `db:verify` — три правила сверх них. Таблица `contact_basis_history`:
«было → стало» по основанию и статусу, даты, форма, `reference_changed`, `anonymized`, автор, время.

- **`CONTRACT` в демо не используется**, хотя задание называло его: договор с вузом — это
  п. 7, а не п. 5; назвать его «договором» значило бы записать в систему неверное основание.
  `CONTRACT` оставлен для контакта, который сам сторона договора с ИТ-Школой.
- **Документ-основание обязателен для любого основания**: доказывает оператор (ч. 3 ст. 9).
- **В истории нет свободного текста.** Комментарий не хранится, текст документа не копируется —
  только признак `reference_changed`. История переживает обезличивание и служит основанием
  акта; свободный текст — главный неуправляемый канал ПД (PRIVACY.md, 2.1).

**Отзыв согласия → немедленное обезличивание**, а не пометка «обезличить в 30 дней».
ч. 5 ст. 21 требует прекратить обработку и уничтожить ПД «в срок, не превышающий 30 дней» —
это предел, а не отсрочка. Согласие у нас — единственное основание (одно поле); если
у оператора есть другое (ч. 2 ст. 9), его фиксируют до отзыва, и отзывать становится нечего.
Пометка потребовала бы исполнителя по расписанию, а cron в проекте не включён даже для
сроков журнала (решение 88) — пометка без исполнителя стала бы пропущенным сроком.
Обезличивание — тот же `ANONYMIZED_CONTACT_FIELDS`, что у `anonymize`, в одной транзакции
с записью отзыва и истории; дата и форма согласия и оба документа остаются — это основание
акта. Цена: действие необратимо и доступно менеджеру (у `anonymize` — только ADMIN). Защита —
обязательный документ отзыва, 409 для всего, что не действующее согласие, и подтверждение
в интерфейсе. `TODO: PM DECISION` — оставить отзыв менеджеру или сузить до ADMIN (одна строка
в `permissions.ts`).

**Параллельность.** Изменение идёт в транзакции под `FOR UPDATE` строки контакта, план
строится чистым правилом (`planBasisChange`, `planConsentWithdrawal`) по перечитанной строке:
два одновременных отзыва не пишут две истории.

**Доступ (согласовано с решением 106).** Право `CONTACT_BASIS` — ADMIN и MANAGER: видеть
основание целиком, фиксировать, отзывать, открывать историю. ANALYST, VIEWER и представитель

## 112. Полная Content-Security-Policy: скрипты только по nonce запроса

**Дата:** 25.09.2026 · **Статус:** ветка `sec/csp-nonce`. Номера 109–111 заняты параллельными ветками.

**Контекст.** CSP была частичной (`frame-ancestors`, `object-src`, `base-uri`, `form-action`):
директив для скриптов не было, внедрённый скрипт исполнился бы (SECURITY_LIMITATIONS, P1
«при выкладывании наружу»). Статичный заголовок из `next.config.ts` не годится: Next
вставляет встроенные скрипты (данные для гидратации), и без nonce строгая политика их режет.

**Решение.**
- `src/shared/http/csp.ts` — `createNonce()` (16 случайных байт, base64, только веб-API —
  middleware работает в edge-среде) и `buildContentSecurityPolicy({ nonce, dev, https })`.
- `src/middleware.ts` на каждый пропущенный запрос страницы выдаёт свой nonce: политика
  уходит в ответ браузеру и в заголовки запроса дальше — `content-security-policy` (из него
  Next сам берёт nonce для своих скриптов и стилей, `get-script-nonce-from-header`)
  и `x-nonce`. Присланные клиентом одноимённые заголовки перезаписываются. Перенаправления
  на вход политики не несут — у них нет тела.
- Корневой `layout.tsx` читает `x-nonce` через `headers()` и ставит его на два встроенных
  скрипта (режим интерфейса и заставка). Чтение заголовков делает все страницы
  динамическими — это обязательно: у заранее собранной страницы nonce один на всех,
  и он не совпал бы с заголовком ответа. `connection()` не понадобился. На этих двух
  тегах `suppressHydrationWarning`: браузер прячет значение nonce от страницы (атрибут
  читается пустым), и React в режиме разработки жаловался на расхождение при гидратации.
- Политика: `default-src 'self'; script-src 'nonce-…' 'strict-dynamic'; style-src 'self'
  'unsafe-inline'; img-src 'self' data: blob:; font-src 'self'; connect-src 'self';
  worker-src 'self' blob:; manifest-src 'self'; frame-src 'none'; frame-ancestors 'none';
  object-src 'none'; base-uri 'self'; form-action 'self'` и `upgrade-insecure-requests`.
- `'strict-dynamic'`: куски приложения Next догружает скриптом с nonce — они разрешены
  по цепочке; список адресов браузер при этом не смотрит.
- `'unsafe-eval'` — только вне `NODE_ENV=production`: `next dev` исполняет модули через eval.
- `upgrade-insecure-requests` — только в боевой сборке **и** когда посетитель пришёл по
  HTTPS (`X-Forwarded-Proto: https` от Caddy или https-адрес запроса). Отступление от
  «только в production» сознательное: стенд без домена (Caddy на `:80`) и запасной ноутбук
  (`http://localhost:3100`) работают по http, и директива заставила бы браузер тянуть все
  файлы по https — страница не открылась бы. Подделать заголовок снаружи нельзя: Caddy
  выставляет его сам; при прямом доступе подделка вредит только самому подделавшему.
- Стили: `'unsafe-inline'` оставлен. React пишет `style="…"` во многих компонентах
  (графики, полоски, анимации), Next и `next/font` кладут `<style>`; nonce на атрибуты
  `style` не распространяется в принципе. Через стиль код не выполняется. Остаточный риск
  — в SECURITY_LIMITATIONS, P2. Nonce в `style-src` не добавлен намеренно: при nonce
  браузер игнорирует `'unsafe-inline'`, и все `style="…"` перестали бы работать.
- Общая часть политики в `next.config.ts` осталась для API, файлов сборки и значков:
  на страницах заголовок middleware её заменяет — в ответе одна политика (проверено).
- Caddy ничего не меняет: `X-Forwarded-Proto` он уже передаёт, CSP не трогает.

**Фоновые потоки.** 3D-сцена входа (`constellation.worker`) и проверка «не робот»
(`captcha.worker`) — файлы сборки с нашего адреса, `worker-src 'self'`. Политика самого
потока приходит заголовком его файла (общая часть, без `script-src`), так что three.js
внутри потока ничем не ограничен.

**Проверка.** Боевая сборка (`next build` + `next start`), Playwright: Chromium (headless
shell) и WebKit × менеджер, администратор, представитель вуза × «Рабочий» и
«Презентационный» режимы × все страницы (главная, вузы, карточка вуза, программы,
карточка программы, связки, карточка связки, рекомендации, документы, аналитика,
IT-продукты, все вкладки настроек, профиль, отчёт руководителю с печатью, кабинет вуза,
`/privacy`, `/presentation`) + аноним (вход, `/privacy`, `/presentation`) + вход по паролю
с тремя неудачами и проверкой «не робот». Собирались сообщения консоли «Refused to…»
и события `securitypolicyviolation`: **ноль нарушений**. Сцена входа рисуется в потоке,
прыжок и сборка главной после входа идут, заставка уходит, печать и PDF отчёта работают.

**Тесты.** `csp.test.ts` — состав политики, отсутствие `unsafe-eval` и `unsafe-inline`
для скриптов в боевой политике, `upgrade-insecure-requests` только за HTTPS, формат nonce
совпадает с тем, что ищет Next. `middleware.test.ts` — политика с nonce у страниц
(в том числе открытых), nonce уникален на запрос, тот же nonce уходит к Next, клиентский
`x-nonce` заменяется, без `unsafe-eval` при `NODE_ENV=production`. Пробник — `script-src`
с nonce и `strict-dynamic`, все `<script>` страницы несут nonce из заголовка, nonce разный
у двух ответов. `scripts/deploy/check.sh` — то же на стенде плюс `upgrade-insecure-requests`

**Цена.** Страницы рендерятся на запрос, а не отдаются готовыми. Каркас данных не
содержит и в базу не ходит, так что нагрузка — рендер React-каркаса.

**Изменения схемы:** нет. **Затрагивает фронт:** новый встроенный `<script>` должен

## 114. Копии базы вне сервера: шифрование на сервере, Object Storage, ключ без права удаления

**Дата:** 25.09.2026 · **Статус:** подготовлено, включает владелец сервера (DEPLOY.md, раздел 9).

**Проблема.** Ночные копии (cron в 03:15, 14 суток) лежат на той же машине, что и база:
от ошибки спасают, от потери машины — нет (SECURITY_LIMITATIONS, раздел 2).

**Решение.** `scripts/deploy/backup-offsite.sh` из cron владельца в 03:45 берёт свежую
ночную копию и кладёт её в приватный бакет Yandex Object Storage (`ru-central1`, холодное
хранение). Восстановление — `restore-offsite.sh`, только в новую базу. Общее —
`offsite-lib.sh`.

- **Шифрование на сервере, а не на стороне хранилища.** Копии содержат ПД. Шифрование
  Object Storage ключом KMS защищает от чужого доступа к носителю, но расшифровывает
  любому, у кого есть доступ к бакету, — и завязано на ещё один сервис облака.
  `openssl enc -aes-256-cbc -pbkdf2 -iter 200000` есть на любой Ubuntu и на любом
  компьютере владельца: копию можно открыть и без сервера, и без облака. Пароль —
  `BACKUP_ENCRYPTION_PASSPHRASE` в `.env.cloud` и в менеджере паролей владельца.
  В openssl пароль уходит через окружение (`-pass env:`), не аргументом.
- **CBC без проверки подлинности** — поэтому рядом с шифром лежит его SHA-256: при
  восстановлении отличает «испорчено при передаче» от «не тот пароль». Подмену
  злоумышленником с доступом к бакету это не ловит (сумма лежит там же); защита от
  неё — ключ без права удаления и версионирование бакета, если владелец его включит.
- **Ключ может только загружать и читать** (`storage.uploader` на один бакет). Копии
  старше 30 суток удаляет правило жизненного цикла, а скрипт каждую ночь проверяет,
  что оно сработало (код 2, если в бакете есть копии старше 33 суток). Скрипт,
  удаляющий старое сам, требовал бы ключа с правом удаления — такой ключ, украденный
  с сервера, стирает все копии.
- **Копия проверяется до отправки целиком**: `pg_restore -l` и `pg_restore -f /dev/null`.
  Одного `-l` мало: копия, оборванная на 80–99%, его проходит (проверено) — оглавление
  лежит в начале файла. Затем шифр расшифровывается обратно и сверяется с исходником.
- **Ничего не ставится на сервер**: aws-cli — образ `amazon/aws-cli` на время команды
  (с пределом памяти 512 МБ), `pg_restore` и `psql` — в контейнере базы. Ключ передаётся
  в контейнер окружением (`-e ИМЯ` без значения) — в `ps` его нет.
- **Настройки читаются из `.env.cloud` построчно** (`env_get`), файл не исполняется.
  Тест покрытия `.env.example` теперь учитывает и переменные, которые так читают
  скрипты сервера.

**Альтернативы.** `curl --aws-sigv4` вместо образа aws-cli — без 700 МБ на диске, но
разбор XML списка объектов и подпись загрузки пришлось бы писать и сопровождать самим.
`restic`/`borg` — дедупликация и своё шифрование, но это установка пакета на сервер
и ещё один формат, который владельцу надо уметь открывать. Для сотен килобайт в сутки
не окупается.

**Проверено.** `offsite-selftest.sh`: 25 проверок на локальной базе с заглушкой вместо
aws-cli. Отдельно — настоящий `amazon/aws-cli` 2.37.4 против локального S3
(`rclone serve s3`) и `docker exec` в `postgres:16-alpine`: загрузка, проверка,
восстановление в новую базу — 22 таблицы совпали построчно, 12 колонок с `ru-x-icu`
на месте; неверный ключ — понятный сбой, секрета в журнале нет. С настоящим Object
Storage не проверялось — бакета ещё нет.

**Изменения схемы:** нет. **Затрагивает фронт:** нет.

## 115. Журнал действий с защитой от подмены: цепочка хешей и печати

**Дата:** 25.09.2026 · **Статус:** ветка `sec/audit-chain`; API, база и скрипты — экран делает фронт.

**Проблема.** SECURITY_LIMITATIONS: «`audit_log` — обычная таблица, её можно изменить из базы;
журнал не является доказательством». Роль приложения с решения 89 уже не может изменить
и удалить запись, но владелец базы (и любой, кто получил сервер) — может, и никто этого не увидит.

**Решение.** Три слоя.

1. **Только дописывается — для всех.** Триггеры `audit_log_append_only` и `…_no_truncate`
   запрещают UPDATE, DELETE и TRUNCATE журнала, печатей и точек чистки любой роли, включая
   владельца. Обход — `SET LOCAL skilllink.allow_audit_purge = 'on'` в транзакции: так
   работают стирание адреса клиента и чистка по сроку (`db:retention`) и перезаливка демо.
   Это защита от неаккуратной правки и ORM, а не от злоумышленника-владельца: флаг может
   поставить кто угодно. Поэтому у роли приложения дополнительно нет самих прав
   (`create-app-role.sql`), а чистку (`audit_purge_before`) ей не вызвать.
2. **Цепочка хешей.** У записи — `chain_seq` (1, 2, 3… без пропусков), `prev_hash`,
   `row_hash = SHA-256(hex(prev_hash) или 'GENESIS' | каноническая запись)`. Считает триггер
   BEFORE INSERT: ни приложение, ни скрипт, ни psql его не обходят, значения из INSERT
   перезаписываются. Номер выдаётся под `pg_advisory_xact_lock` (ключ — 115 и oid таблицы),
   блокировка держится до конца транзакции — следующая вставка видит эту запись уже
   зафиксированной, цепочка не ветвится. Порядок — по `chain_seq`, а не по `id` (cuid,
   порядка не несёт) и не по `created_at` (его приложение ставит до вставки).
3. **Печать.** Цепочка сама не видит, что ей отрезали хвост или пересчитали историю
   целиком. Печать — номер и хеш головы на момент снятия (`audit_seals`, `npm run audit:seal`);
   проверка сверяет с каждой печатью строку её номера. Копия печати вне базы
   (сообщение владельцу; отправка — отдельная задача ops/owner-alerts) ловит и владельца
   базы, удалившего хвост вместе с печатями: `npm run audit:verify -- --expect-seq N --expect-hash H`.

**Каноническая запись** — `json_build_array('v1', chain_seq, id, user_id, action, object_type,
object_id, payload::text, created_at)::text`, а не строка через разделитель: у разделителя
«a|b» + «c» и «a» + «b|c» совпали бы. Время — `to_char(…US"Z")` (колонка без часового пояса,
от TimeZone сеанса не зависит). Первый элемент — версия формата: сменить канон можно, не
потеряв проверяемость старых записей.

- **Адрес клиента (`payload.address`) в хеш не входит.** Его стирают через 90 дней
  (решение 88), и каждый стёртый адрес иначе ломал бы цепочку. Альтернатива — «легальный
  пересчёт» после стирания — переписывала бы каждые сутки последние 90 дней цепочки и
  обесценила бы все печати. Цена: подмену адреса проверка не видит.
- **Чистка по сроку не требует пересчёта.** `audit_purge_before()` удаляет только начало
  цепочки — записи до первой не старше срока — и пишет точку чистки (`audit_chain_cuts`:
  номер и хеш последней удалённой). Проверка начинает цепочку с неё. Запись старше срока,
  вставшая в цепочку после более свежей (долгая транзакция), удаляется следующим запуском.
  Голова не удаляется никогда: следующей вставке нужен её хеш. Функции «пересобрать цепочку»
  нет: единственный её сценарий — после легальной чистки — закрыт точкой чистки, а в
  остальных случаях пересборка и есть подделка.
- **Две независимые проверки.** `audit_verify_chain()` в базе (STABLE — один снимок) и
  `chain.rules.ts` в приложении по строкам, прочитанным встроенными средствами PostgreSQL
  (`(payload - 'address')::text`, `to_char`, `encode`) — в одной транзакции REPEATABLE READ
  READ ONLY. Пройдено — только если обе «да» и итоги совпали до номера и хеша; иначе
  `engines_disagree`. Владелец базы может переписать функцию проверки на «всегда да», а
  код приложения и встроенные функции (без суперпользователя) — нет. Приём тот же, что
  у ключа навыка (решение 110). Эталонный вектор из PostgreSQL 16 — в `chain.test.ts`:
  если обновление PostgreSQL изменит вывод jsonb, тест скажет об этом до стенда.
- **Автор записи журнала — `ON DELETE RESTRICT`**, а не SET NULL: обнуление автора — правка
  журнала, триггер её всё равно не пропустил бы, только с непонятной ошибкой. Пользователей
  и так не удаляют — блокируют и обезличивают.
- **Существующие записи** получают номера в миграции в порядке (`created_at`, `id`); таблица
  на это время закрыта на запись (`LOCK … EXCLUSIVE`), иначе строка, вставленная между
  заполнением и триггером, осталась бы без номера. CHECK `audit_log_chain_check` не даёт
  записи без номера и хеша.

**API и скрипты.** `GET /api/audit/verify` и `GET /api/audit/seals` — только ADMIN, под
существующим `/api/audit` (отдельного пространства `/api/admin` в проекте нет, права —
через `assertCan(user, 'ADMIN')`, как у журнала). Нарушение — ответ 200 с `ok: false`,
`code`, `brokenAt`, `reason`; факт проверки пишется в журнал (`audit.verify`, без хешей).
`npm run audit:verify` (код 1 — нарушение, 2 — не удалось проверить), `npm run audit:seal`
(JSON на stdout); `auditSeal()` — чистая функция для отправки владельцу. Правило в
`db:verify`, шаг пробника (права, запись о проверке, рост цепочки).

**Проверки.** `chain.test.ts` — 34 модульных теста (канон и хеш против эталона PostgreSQL,
экранирование, все коды нарушений, печати, точка чистки, внешняя печать). `chain.db.test.ts` —
16 тестов на настоящей базе во временной схеме с теми же триггерами (`audit_chain_install`):
обе проверки согласны; значения цепочки из INSERT перезаписываются; UPDATE/DELETE/TRUNCATE
без обхода отклоняются; стёртый адрес цепочку не ломает; UPDATE с обходом и с отключённым
триггером → `row_modified`; DELETE середины → `rows_missing`; пересчитанная история →
`history_rewritten` по печати; удалённый хвост → `tail_removed`; удалённые вместе с хвостом
печати → ловит печать вне базы; чистка по сроку и продолжение цепочки; 20 параллельных
вставок → номера 1–21 без дыр. Отдельно проверено: без блокировки тест гонки падает
(повтор номера). Роль приложения по `create-app-role.sql`: вставка, печать, проверка — да;
UPDATE, DELETE, чистка, запись точки чистки — «permission denied». Без `TEST_DATABASE_URL`
набор пропускается, в CI — отдельный шаг.

**Ограничения.** Хеш без секрета: владелец базы, удаливший хвост и печати в базе, не виден
без копии печати вне сервера — а её отправка пока не включена. Хвост после последней
печати не виден никак — печать снимать часто. Подпись ключом вне сервера и внешнее
хранилище (WORM) — не сделаны. Записи журнала идут по одной: запись журнала в середине
долгой транзакции задерживает остальные и может дать взаимную блокировку — журнал пишется
последним действием транзакции. Невыполненная запись журнала (сбой при записи не ломает
операцию) цепочкой не ловится. Восстановление из копии с `--data-only` прогнало бы строки
через триггер и перенумеровало бы их — копии проекта полные (`pg_dump -Fc`), там триггеры
создаются после данных.

**Изменения схемы:** миграция `20260926000000_audit_hash_chain` — **на согласование Тиграну**.
**Затрагивает фронт:** новые `AuditChainVerifyDto`, `AuditSealDto`, `AUDIT_CHAIN_BREAK_CODES`,
подписи `AUDIT_CHAIN_BREAK_LABELS`, действие журнала `audit.verify`. Прежние поля не менялись.
