## Соглашения, принятые в схеме

- **Первичные ключи** — `cuid()`, тип `text`.
- **Удаления нет.** Вузы и программы архивируются (`archived_at`), связи на них `RESTRICT`.
  Сотрудничество длится годами, история — основная ценность системы.
- **Незаполненный показатель — NULL, а не 0.** Ноль это значение, NULL это «Нет данных».
  Требование раздела 10 ТЗ, на нём держится вся объяснимость аналитики.
- **`is_mock`** отмечает демонстрационные записи. Выдавать их за реальные запрещено.
- **Происхождение обязательно.** У показателей набора есть `metrics_source`
  и `metrics_updated_at`, у рыночных данных — `source`, `period`, `confidence`, `is_mock`.
  Без них показатель нельзя подписать источником.

## Требует вашего согласования

### 1. Таблица `contacts` — расширение относительно ТЗ

В разделе 11 ТЗ её нет: контактное лицо перечислено как поля карточки вуза (раздел 7.3).

**Вынесена в отдельную таблицу**, потому что контактов у вуза бывает несколько и на них
ссылаются участники встреч (`meeting_participants`). В карточке вуза отдаётся
`primaryContact` плюс полный список.

Поля: `university_id` (CASCADE), `full_name`, `position?`, `email?`, `phone?`,
`is_primary`, `notes?`.

### 2. `recommendations.resolution_comment`

Миграция `20260921074512_recommendation_resolution_comment`.

`justification` — обоснование системы, почему рекомендация появилась.
`resolution_comment` — комментарий сотрудника при закрытии.

Изначально было одно поле, и комментарий человека затирал обоснование системы —
причина появления рекомендации терялась навсегда.

### 3. `documents.content` и `documents.template_key`

Миграция `20260921082617_document_template_content`.

Концепция обещает сборку пакета документов из шаблонов с автоподстановкой реквизитов.
Без хранения собранного текста генерация не оставляет после себя ничего.

**Это текст, а не файл.** Загрузка файлов остаётся P2 по решению 14.

### 4. Рейтинг считается в приложении, а не представлениями СУБД

Концепция обещала представления и агрегирующие запросы на стороне базы.

Сейчас рейтинг программ и дефицит навыков считаются чистыми функциями в приложении.
Причина: формулы ещё не утверждены — все веса помечены `TEMP` и ждут решения Артура.
Менять коэффициент в настройках дешевле, чем переписывать представление и миграцию.

**Когда формулы утвердят** — расчёт можно перенести в представления без изменения
контракта API. Это ваше решение, я к нему готов.

### 5. Нет уникальности на тройку «вуз — программа — продукт»

Намеренно. По концепции у одного вуза параллельно идёт несколько независимых связок
с разными продуктами и статусами.

Если считаете, что ограничение нужно — скажите, какое именно.

## Производительность

Проверено на отдельной базе с объёмом, близким к реальному:

| | |
| --- | --- |
| Вузов | 120 |
| Программ | 480 |
| Связок | 360 |
| Этапов | 5 040 |
| Задач чек-листов | 10 440 |

Результат: все страницы отвечают **быстрее 40 мс**, генерация 360 рекомендаций — 0,3 с,
групповая операция по 360 связкам — 0,2 с.

Индексы расставлены по полям фильтрации и сортировки: статусы, регионы, города,
внешние ключи, сроки этапов, периоды рыночных данных.

**На что посмотреть, если будете грузить больший объём:** список связок тянет все этапы
каждой связки, чтобы посчитать текущий этап и процент выполнения. На объёме MVP это
дёшево, на порядок большем — стоит проверить план.

## Загрузка реальных данных

Писать SQL не нужно — есть загрузка из CSV с предпросмотром:

```bash
# Сначала посмотреть, что получится (ничего не пишет)
curl -X POST "http://localhost:3000/api/import?dataset=universities" \
  -H 'content-type: text/csv' --data-binary @universities.csv

# Потом применить
curl -X POST "http://localhost:3000/api/import?dataset=universities&mode=apply" \
  -H 'content-type: text/csv' --data-binary @universities.csv
```

| Раздел | Обязательные колонки | Необязательные |
| --- | --- | --- |
| `universities` | Название, Город, Регион | Краткое название, Направлений, Студентов, Сайт |
| `programs` | Вуз, Программа, Уровень | Код, Направление, Длительность мес., Заявки, Обучающихся, Групп |

Особенности, которые стоит знать:

- Колонки ищутся **по названию**, а не по порядку — можно менять местами в Excel.
- Записи опознаются по названию (программа — по паре «вуз + программа»), поэтому
  **повторная загрузка не создаёт двойников**.
- Строка с ошибкой **не отменяет остальные**, её номер совпадает с номером строки в Excel.
- Пустая ячейка — «Нет данных», нечисловое значение — ошибка строки, а не тихий ноль.
- Вуз при загрузке программ **не создаётся** — опечатка в названии породила бы двойника.

Формат совпадает с выгрузкой (`GET /api/export?dataset=…`), так что цикл
«выгрузил → поправил в Excel → загрузил обратно» работает без переименований.

## Одно ограничение, о котором нужно знать

**Политик доступа на уровне строк (RLS) нет.** Концепция их обещает.

Сейчас разграничение доступа работает проверками в сервисах и общим фильтром по вузу
в репозиториях — это проверено отдельным набором тестов. Но прямое подключение к базе
мимо приложения ограничение обходит.

Полноценный RLS требует прогонять каждый запрос через транзакцию с установкой переменной
сессии, то есть переделать все репозитории. Решение отложено осознанно и честно описано
в `docs/SECURITY_LIMITATIONS.md`. Если считаете, что нужно к защите — скажите.
