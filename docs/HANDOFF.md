Серверная часть готова и проверена. Этот документ — то, что нужно знать, чтобы начать
работать: Ване и Серёже для фронта, Тиграну для базы, Артуру для приёмки.

## Запуск за пять минут

```bash
git clone <репозиторий> && cd skilllink
npm install
cp .env.example .env          # правьте только DATABASE_URL
npm run db:migrate
npm run db:seed
npm run dev
```

Проверка: `curl http://localhost:3000/api/health` → `{"data":{"status":"ok",...}}`

Нужен PostgreSQL 16+. Если его нет — `docker compose up -d` поднимет из репозитория
(если 5432 занят: `POSTGRES_PORT=5433 docker compose up -d`).

### Или целиком в контейнерах

```bash
export AUTH_SECRET="$(openssl rand -base64 32)"
docker compose up -d postgres
docker compose --profile migrate run --rm migrate
docker compose --profile app up -d app
```

Образ проверен: собран, запущен, сквозной сценарий и пробник против него проходят
полностью. Сборка не требует ни базы, ни секретов — они нужны только на запуске.

## Ване и Серёже — фронт

### С чего начать

1. **`docs/openapi.json`** — машиночитаемая спецификация. По ней генерируется типизированный
   клиент, руками описывать запросы не нужно. Живой сервер отдаёт её по
   `GET /api/openapi.json`.
2. **`docs/API_CONTRACT.md`** — поля каждого ответа, коды ошибок, примеры curl.
3. **`docs/DESIGN_INTEGRATION.md`** — какой эндпоинт питает какой блок экрана.

### Правила, которые сэкономят вам время

**Типы — только из `@/shared/contracts`.** Импортировать что-либо из `@/generated/prisma`
нельзя: это структура таблиц, она меняется вместе со схемой.

```ts
import type { CooperationDto, UniversityListItemDto } from '@/shared/contracts'
```

**Русские подписи к статусам — тоже оттуда.** API отдаёт коды (`IN_PROGRESS`), словари
подписей лежат рядом с типами. Не пишите свои: бэкенд теми же словами пишет обоснования
рекомендаций, ленту событий и выгрузку CSV, и ваши надписи с ними разойдутся.

```ts
import { STAGE_STATUS_LABELS, COOPERATION_STATUS_LABELS } from '@/shared/contracts'
STAGE_STATUS_LABELS[stage.status]   // «В работе»
```

Тест следит, чтобы у каждого значения перечисления была подпись: новое значение без неё
уронит сборку, а не покажет пользователю пустоту.

**Формат ответа всегда один.** Успех — `{ data }`, список — `{ data, meta }`,
ошибка — `{ error: { code, message, details } }`. Текст `message` уже на русском,
его можно показывать пользователю как есть.

**Показатели — объекты, а не числа.** `metrics.studentCount.value` может быть `null`
при `basis: "none"` — это «Нет данных», а не ноль. Показывать ноль вместо прочерка нельзя:
это прямое нарушение требования ТЗ.

**`isMock` обязателен к показу.** Все демо-данные помечены; выдавать их за подтверждённую
статистику запрещено разделом 4 ТЗ.

**Права приходят готовыми.** `GET /api/me` отдаёт `permissions` — по ним решайте, какие
разделы рисовать. Матрицу доступа у себя дублировать не надо.

**Ответ на изменение — целиком.** `PATCH` этапа и задачи возвращает этап целиком,
`PATCH` связки — связку целиком. Второй запрос за свежими данными не нужен.

### Что обязательно предусмотреть в интерфейсе

| Ситуация | Что придёт | Что показать |
| --- | --- | --- |
| Завершение этапа | 422, если нет `result` | форму с полем «Результат» |
| Завершение этапа | 409, если открыты обязательные пункты | сколько пунктов осталось |
| Блокировка этапа | 422 без `blockingReason` | обязательное поле «Причина» |
| Отмена или переоткрытие этапа | 422 без `comment` | обязательное поле «Основание» |
| Этап 14 | `isAutoManaged: true` | только чтение, без кнопок |
| Двойной клик по кнопке | 409 «изменено другим пользователем» | «обновите страницу» |
| Миграции не применены | `/api/health` отдаёт 503 и `schema: "missing"` | не поднимать интерфейс |
| Архивирование вуза со связками | 409 с `details.openCooperations` | понятный текст, не «ошибка» |

### Экраны, которых, скорее всего, нет в ваших макетах

API под них готов и проверен:

- **Кабинет представителя вуза** — `/api/portal/*`. Отдельная роль, другой набор данных,
  скрытые внутренние комментарии.
- **Экран входа** — NextAuth, `signIn('credentials', { email, password })`.
- **Раздел рекомендаций** — `/api/recommendations` с основанием у каждой.
- **Лента событий вуза** — `/api/universities/:id/events`.
- **Выгрузка в CSV** — `/api/export?dataset=…`.

**Нужно от вас:** положите экспорт макетов в `docs/design/`. Пока их нет,
`DESIGN_INTEGRATION.md` составлен по экранам ТЗ, а не по вашим — расхождения вскроются
на этапе подключения, в самое дорогое время.

## Тиграну — база данных

### Что смотреть

- **`prisma/schema.prisma`** — 21 таблица, snake_case через `@map`.
- **`docs/DATABASE_SCHEMA.md`** — решения, которых не видно из кода, и раздел
  «Что обсудить» в конце.
- **`prisma/migrations/`** — три применённые миграции.

### Требует вашего согласования

| Что | Зачем понадобилось |
| --- | --- |
| Таблица `contacts` | В разделе 11 ТЗ её нет, контакт был полем вуза. Вынесена: контактов бывает несколько, и на них ссылаются участники встреч |
| `recommendations.resolution_comment` | Комментарий сотрудника отдельно от обоснования системы — иначе первый затирал второе |
| `documents.content`, `documents.template_key` | Текст, собранный из шаблона. Это текст, а не файл: загрузка файлов остаётся P2 |
| Расчёт рейтинга в приложении | Концепция обещала представления СУБД. Пока формулы не утверждены, менять коэффициент в конфиге дешевле, чем переписывать представление |
| Отсутствие уникальности на тройку (вуз, программа, продукт) | По концепции у вуза параллельно идёт несколько независимых связок |

### Проверено на объёме

На отдельной базе: 120 вузов, 480 программ, 360 связок, 5040 этапов, 10440 задач.
Все страницы отвечают быстрее 40 мс, генерация 360 рекомендаций — 0,3 с.

Индексы расставлены по полям фильтрации и сортировки. Если будете грузить реальный объём —
посмотрите планы запросов на списке связок: он тянет все этапы каждой связки,
чтобы посчитать текущий этап и процент.

### Команды

```bash
npm run db:migrate    # создать и применить миграцию (разработка)
npm run db:deploy     # применить существующие (промышленный контур)
npm run db:seed       # демо-данные, полностью очищает таблицы
npm run db:studio     # визуальный редактор
```

Роли приложения нужен `CREATEDB` только для `prisma migrate dev` (теневая база).
В промышленном контуре достаточно `migrate deploy`.

## Демонстрационный сценарий

Раздел 18 ТЗ проходит целиком, воспроизводится командой `npm run smoke`.

Демо-пользователи и общий пароль `skilllink` выводит `npm run db:seed`:

| Роль | Почта | Что показывает |
| --- | --- | --- |
| MANAGER | `manager@skilllink.demo` | основной сценарий работы |
| ANALYST | `analyst@skilllink.demo` | аналитика без права изменения |
| UNIVERSITY_REP | `rep@spbgu.example.invalid` | кабинет вуза, закрытая аналитика |
| ADMIN | `admin@skilllink.demo` | журнал действий |

Роли переключаются и без пароля: cookie `skilllink_user` с идентификатором
(пока включён `DEMO_AUTH_ENABLED`).

Демо-данные специально устроены так, чтобы было видно всё: программы без показателей,
просроченные и заблокированные этапы, отменённый этап, связка без выбранного продукта,
застоявшаяся связка, два критичных дефицита навыков, документы во всех статусах.
Срабатывают все пять правил рекомендаций.

## Перед выкладыванием наружу

Стенд сейчас рассчитан на демонстрацию. Для любого доступного извне контура обязательно:

1. `DEMO_AUTH_ENABLED=false` — иначе вход без пароля по cookie остаётся открытым.
2. `AUTH_SECRET` из `openssl rand -base64 32`.
3. Сменить демонстрационные пароли: сейчас у всех учётных записей он одинаковый.
4. HTTPS и защищённые cookie.

Полный список — `docs/SECURITY_LIMITATIONS.md`, раздел «Что нужно до промышленной
эксплуатации».
